\section{Noarr Library}\label{chap:noarr}

\xxx{Micro-motivation}

The Noarr library, first introduced in~\cite{vsmelko2022astute}, is a \cpp library that provides layout-agnostic abstractions for representing and manipulating multidimensional data structures and their traversals.

Formally, the abstractions are based on partial functions on the index space and memory space of multidimensional arrays. Each such partial function is represented by a primitive building block called a \emph{proto-structure} --- examples of proto-structures include \texttt{scalar} that represents a single value, \texttt{array} that represents a contiguous array of elements represented by another structure, or \texttt{into\_blocks} that represents a view of another structure that divides one of its dimensions into blocks of a given size.

The composable design of Noarr bears resemblance to views in the ranges library in \cpp20 (TODO cite); however, while being composable in a hierarchical manner, Noarr structures allow better flexibility and type-safety for multidimensional data structures by representing the index space using named dimensions that are resolved at compile time.

Since the index space is represented using named dimensions, all queries on the structure, such as obtaining the size of a dimension, or the memory offset of an element at a given index, are type-safe and checked at compile time. In contrast to traditional positional indexing of multidimensional arrays (e.g., \lstinline{data[i][j]}) that is prone to errors due wrong pairing of indices to dimensions, type-safe indexing using named dimensions (e.g., \lstinline{data[idx<'x'>(i) + idx<'y'>(j)]}) ensures that the indices are paired with the correct dimensions. This also ensures that the API of memory accesses is self-documenting and independent of the actual layout of the data in memory.

Noarr structures are immutable abstractions representing multidimensional data structures built by composing primitive proto-structures in a hierarchical manner as depicted in \cref{fig:noarr-structure-composition}. Each proto-structure represents a transformation of the index space and memory space of the nested \emph{sub-structure}; thus, if the sub-structure represents a multidimensional array with dimensions \lstinline{'y'} and \lstinline{'z'}, then wrapping it in an \texttt{array} proto-structure with dimension \lstinline{'x'} results in a three-dimensional array with dimensions \lstinline{'x'}, \lstinline{'y'}, and \lstinline{'z'}. The composition in this example simply adds a new dimension to the index space, extending it from two to three dimensions accordingly; however, other proto-structures may perform more complex transformations of the index space, such as splitting a dimension into multiple dimensions (e.g., \texttt{into\_blocks}, which consumes one dimension and produces two new dimensions) or reordering the logical hierarchy of dimensions (e.g., \texttt{hoist}).

The composition of proto-structures is done using \cpp template meta-programming and, in the Noarr library, it is represented by the \lstinline{^} operator. Since each proto-structure represents a partial function on the index space and memory space of the sub-structure, the composition of proto-structures is naturally associative. This is a powerful property that allows defining more complex transformations from simpler ones, and applying them simultaneously, and possibly to multiple data structures.

Proto-structures can have multiple input dimensions and multiple output dimensions. If a dimension is not mentioned in the proto-structure, it is passed through unchanged from the sub-structure to the resulting structure. If a dimension appears as an input dimension but not as an output dimension, it is \emph{consumed} by the proto-structure; similarly, if a dimension appears as an output dimension but not as an input dimension, it is \emph{produced} by the proto-structure. Any produced dimensions are removed in the sub-state passed to the sub-structure and all consumed dimensions are added. This principle strengthens the type-safety of Noarr structures by ensuring that a dimension is not propagated unexpectedly.

\xxx{TODO (not sure where/whether to add this): One further property of proto-structures that operate on multiple input dimensions is that if there are dependencies between the input and output dimension lengths (e.g., the input dimension of \texttt{into\_blocks} can be expressed as the product of the two output dimensions), the Noarr library automatically infers these dependencies and propagates them when querying dimension lengths, issuing static assertions on ambiguous constructions --- e.g., all three lengths of the dimensions of \texttt{into\_blocks} are specified.}

Querying a specific feature of a Noarr structure, such as obtaining the memory offset of an element at a given index, is expressed as a function that takes the formal arguments of the query and a \emph{state} argument representing the index space, i.e., the lengths of the dimensions and the input indices (thus, an offset query takes no formal arguments, only the state). The proto-structure defines how the state is propagated to the sub-structure (\emph{sub-state}) and the result of the query is dependent on the formal arguments and the contents of the state, and further queries on the sub-structure using the sub-state (if needed). Some proto-structures generalize this idea by having multiple sub-structures (e.g., the \texttt{tuple} proto-structure), choosing the appropriate sub-structure based on the state.

For example, querying the offset of an element in an \texttt{array} proto-structure with size~$N$, dimension~\lstinline{'x'}, and a sub-structure~$S$, given an index state $s$, depicted in \cref{fig:noarr-structure-offset} proceeds as follows:

\begin{enumerate}
  \item Extract the index~$i$ for dimension~\lstinline{'x'}
  \item Compute the sub-state~$s'$ by removing dimension~\lstinline{'x'} from~$s$
  \item Query the size~$sz$ of the sub-structure~$S$ using the sub-state~$s'$
  \item Compute the offset as $i \cdot sz + \text{offset}_S(s')$, where $\text{offset}_S(s')$ is a query of the offset on the sub-structure~$S$ using the sub-state~$s'$
\end{enumerate}

\xxx{Since sub-structure queries always use sub-states, we can conceptually define each query on a Noarr structure as a composition of the features of the sub-structure (the propagation of the sub-state is implicit), formal arguments, and the contents of the state. The sub-state is defined as a transformation of the state.}

The notion of sub-structure and (sub-)state provides a clean framework for defining all queries on Noarr structures. In the Noarr library, most of the queries are implemented as templated member functions of the structure classes.

\xxx{Many proto-structures define only the sub-state, and just pass the queries to their sub-structure(s) without any additional logic. Examples include \texttt{set\_length} that defines the length of a dimension, \texttt{rename} that renames a dimension of the sub-structure, \texttt{span} that restricts the iteration space of a dimension to a given range. Some proto-structures, like \texttt{into\_blocks} that divides a dimension into blocks of a given size, define only some queries, and pass the rest to the sub-structure (\texttt{into\_blocks} defines custom logic only for length queries).}

The second main feature of Noarr structures is their \emph{signature}. A signature is a representation of the hierarchy of the dimensions of the structure. It is a necessary component for specifying intended traversals of the structures and they also allow for improved type-safety of the structures.
A signature can be interpreted as a tree where each node represents a dimension and its children represent nested dimensions.
The signature of a given Noarr structure results from a transformation of the signature of its sub-structure(s) based on the semantics of the proto-structure. For example, the signature of an \texttt{array} structure is represented by a root node representing the array dimension, with a single child representing the signature of the sub-structure as shown in \cref{fig:noarr-structure-signature}.

\xxx{Note that consumed and produced dimensions affect the signature accordingly (in the inverse way than they affect the state) --- consumed dimensions are removed from the signature of the sub-structure and produced dimensions are added as new nodes in the signature tree (usually at the place of the consumed dimensions; however, different proto-structures may define different semantics).}

\begin{figure}[htbp]
  \centering
  \includegraphics[width=.8\linewidth]{img/noarr-structure-signature.eps}
  \caption{Signature of \lstinline{scalar<int>() ^ array<'x'>(N) ^ array<'y'>(M)} structure.}%
  \label{fig:noarr-structure-signature}
\end{figure}

Since layouts are most often used as mappings to memory, Noarr provides \emph{bag} wrapper that represents a pointer to a memory buffer containing the data represented by the nested given structure. The \lstinline{bag} wrapper provides methods for obtaining references to elements at given indices as well as other utility methods. An example of creating a Noarr structure representing a two-dimensional matrix of size $N \times M$ is shown in \cref{lst:noarr-matrix-structure}.

\begin{lstlisting}[language=C++, caption={Creating a matrix structure using Noarr.}, label=lst:noarr-matrix-structure]
auto matrix = bag(scalar<int>() ^ array<'x'>(N) ^ array<'y'>(M));

// Accessing element at (i, j)
matrix[idx<'x'>(i) + idx<'y'>(j)] = i + j;

// Getting size of dimension 'x'
auto size_x = matrix | get_length<'x'>();
auto size_y = matrix | get_length<'y'>();
\end{lstlisting}


\subsection{Noarr Traversers}\label{sec:noarr-traversals}

\xxx{This will probably cite pure C++ approach~\cite{klepl2024pure}.}

Noarr traversers are wrapper abstractions over one or multiple Noarr structures that provide an interface for performing actions over their index spaces. In the simplest case, creating a Noarr traverser over a single Noarr structure and invoking its \texttt{for\_each} method with a callable object results in invoking the callable for each point in the index space of the structure.

\begin{lstlisting}[language=C++, caption={Creating and using a Noarr traverser over a single structure.}, label=lst:noarr-traverser-single-structure]
auto matrix = bag(scalar<int>() ^ array<'x'>(N) ^ array<'y'>(M));
traverser(matrix).for_each([&](auto state) {
  auto [i, j] = get_indices<'x', 'y'>(state);
  matrix[state] = i + j;
});
\end{lstlisting}

The single argument passed to the callable is a state object (TODO ref) containing the named indices for all dimensions of the structure. The traverser follows the signature of the structure to determine the order of iteration over the dimensions; thus, for signatures that form non-linear hierarchies (there are at least two child sub-signatures for some parent dimension), the callable is invoked in a depth-first manner for all points corresponding to the leaf nodes of the signature tree.

Similarly to Noarr structures, Noarr traversers can be further transformed using proto-structures that modify the index space and the signature. For example, the following snippet creates a traverser over the same matrix structure as before, but divides both dimensions into blocks of given sizes.

\begin{lstlisting}[language=C++, caption={Creating a Noarr traverser with blocked traversal.}, label=lst:noarr-traverser-blocked]
auto trav = traverser(matrix)
  ^ into_blocks<'x', 'X'>(block_size_x)
  ^ into_blocks<'y', 'Y'>(block_size_y)
  ^ hoist<'X', 'Y'>();
trav.for_each([&](auto state) { /* ... */ });
\end{lstlisting}

When the traverser is created over multiple Noarr structures, the resulting index space is the cover of the index spaces of all structures constructed using the leftmost structure as the base and extending its index space by adding the uncovered dimensions of the second structure, and so on. This construction is represented by the traverser signature that is formed by taking the signature of the leftmost structure and iteratively prepending the uncovered dimensions of the other structures in the order they appear. If it is created over two two-dimensional structures with dimensions \lstinline{'x'}, \lstinline{'y'} and \lstinline{'y'}, \lstinline{'z'}, respectively, the resulting index space is three-dimensional with dimensions \lstinline{'x'}, \lstinline{'y'}, and \lstinline{'z'} as depicted in \cref{fig:noarr-traverser-multiple-structures}.

Noarr traversers have a similar relationship to Noarr structures as iterators and range algorithms in the \cpp20 ranges library (TODO cite) have to ranges. The main difference is that Noarr traversers operate on multidimensional index spaces inferred from the Noarr structures, while range algorithms operate on one-dimensional sequences of elements.

Similarly to iterators in \cpp algorithms, Noarr traversers can be used to run the given callable objects in parallel using the given backend. Noarr currently supports parallel execution using OpenMP, Intel TBB, \cpp standard threads, and CUDA\@. The following snippet shows binding four dimensions of the traverser to CUDA thread blocks.

We have shown similar results for parallel implementations of the kernels using \xxx{OpenMP, TBB, and CUDA backends}. The main advantage of using Noarr in this context is the ability to easily change the data layouts and traversal orders without having to modify the computation logic or memory access expressions. A secondary advantage is that all memory accesses are type-safe and checked at compile time, preventing many common programming errors related to multidimensional array indexing.

\subsection{Noarr MPI extension}\label{sec:noarr-mpi}

\xxx{This will probably cite MPI layouts~\cite{klepl2024abstractions}.}

\xxx{Introducing layout-agnostic abstractions to distributed communication over MPI proved to be an interesting avenue of research.} The MPI type system is compatible with layout-agnosticism, since MPI datatypes are for the purposes of communication equivalent whenever their signatures\footnote{MPI datatype signature is a sequence of base element types in the semantic order, disregarding their displacements in memory.} are the same. This characteristic is similar to the notion of layout-agnosticism in Noarr structures, where semantic order of elements is specified by the named dimensions; thus, given a linearization of the named dimensions in a Noarr structure, a Noarr structure corresponds to a specific MPI datatype (disregarding different ways of constructing it). As described in (TODO ref), such linearization can be represented by a Noarr signature. % TODO: choose a different term than linearization

In our work (TODO ref), we have introduced the Noarr MPI extension that leverages that traversers can be created over multiple Noarr structures simultaneously. This provides a clean API that builds on top of the Noarr traversers to express communication patterns involving multiple Noarr structures that may have different layouts as shown in \cref{fig:noarr-mpi-communication}, allowing each computation step connected by communication with other computation steps to use its own preferred layout without having to modify the communication logic. We showcase the proposed approach on a distributed matrix multiplication example, with \lstinline{broadcast} and \lstinline{scatter}/\lstinline{gather} communication patterns. Experimental evaluation shows that the automatized generation of MPI datatypes from Noarr structures and traversers introduces negligible overhead compared to hand-crafted MPI datatype definitions over the same layouts regardless of the data layout used.

  \centering

Since two corresponding Noarr structures at the sender and receiver side (with same dimensions, but possibly different layouts) correspond to many different MPI datatypes depending on the linearization of the dimensions, some possibly performing better than others, using Noarr traversers to express the semantic order of the communicated data brings the opportunity to explore different MPI datatype linearizations by adjusting the traverser signatures --- Noarr offers proto-structures, such as \texttt{hoist} (TODO ref), that can be used to safely reorder the dimensions of the traverser signature without affecting the correctness of the communication.

In our work, we have also applied the layout-agnostic MPI datatype construction approach to Kokkos views (TODO ref) and mdspan (TODO ref), that offer efficient multidimensional array abstractions. However, as these abstractions do not provide named dimensions or otherwise encode the semantic order of elements in their type system, such application relies on careful pairing of positional indices to appropriate dimensions. The tuning capability available in the approach leveraging Noarr traversers may be used in this context by providing a permutation of the positional dimensions that controls the layout linearization; however, such approach, without named dimensions, generalizes poorly to more intricate data structures and communication patterns.


\subsection{\xxx{How noarr saves the world}}\label{sec:noarr-saves-world}

% We need to add some concluding remarks here: why is Noarr important? What does it enable? Who cares?

The works described in this section show that layout-agnostic and traversal-agnostic abstractions, such as those provided by the Noarr library, can be used to express the logic of computations and communications in HPC applications in a way that allows for separation of concerns between the logic of the computation and communication and the data layout and traversal order. This separation of concerns allows for introducing more flexibility in the design and implementation of HPC applications, allowing the developers to easily change the data layout and traversal order by swapping transformations applied to the structures (i.e., proto-structures in Noarr) and adjusting any tile sizes or other tunable parameters, without having to modify the logic of the computation and communication.

This flexibility, combined with possibility to infer sizes of co-dependent dimensions and to introduce type-safety of memory accesses and transformations (as exemplified by the Noarr library) allows for more easier exploration of the design space of HPC applications, enabling developers to find better-performing implementations. This improves performance portability of HPC applications across different hardware architectures, as we have shown in our work that the approach is applicable to a wide range of programming models and hardware architectures, including CUDA-enabled GPUs, and MPI-based distributed systems.
