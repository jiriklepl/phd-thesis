In our research towards enabling developers to easily design high-performance algorithms for parallel computing on CPU and GPU architectures, we have introduced the concepts of layout-agnostic and traversal-agnostic design, which had not been extensively studied prior to our work.

% We consider an algorithm design to be concern-agnostic (e.g., layout-agnostic) if it does not encode specific assumptions about the concern, thus supporting separation of concerns in the given application. For example, a layout-agnostic algorithm does not access a data structure using explicit memory offsets; instead, it relies solely on the logical structure of the data (its index space).

The first two sections introduce these concepts in more detail, and the remaining sections present our consecutive peer-reviewed contributions in the area of native abstractions for this design style in HPC.


\section{Layout-agnostic design}\label{sec:layout-agnostic-design}

Layout-agnostic design separates the logical structure of the data (the index space defined by the dimension names) from its physical layout in memory (types and offsets of value elements). Consider \cref{lst:non-agnostic-copy} as an example of a non-layout-agnostic copy algorithm for 2D arrays in \cpp.

\begin{lstlisting}[style=C++, caption={A non-layout-agnostic copy algorithm in \cpp}, label={lst:non-agnostic-copy}]
float* source = new float[__M * __N];
float* destination = new float[__M * __N];

for (size_t i = __0; i < __M; ++i) {
  for (size_t j = __0; j < __N; ++j) {
    destination[i*__N + j] = source[j*__M + i];(*@\label{line:non-agnostic-copy}@*)
  }
}
\end{lstlisting}

This implementation of the algorithm assumes a specific layout of the data in memory (column-major and row-major for \lstinline{source} and \lstinline{destination}, respectively; encoded by the indexing expressions in \cref{lst:non-agnostic-copy}, \cref{line:non-agnostic-copy}), and special care must be taken to ensure that the indexing logic correctly reflects the layout of the data. This is usually not desirable and explicit indexing expressions
% (e.g., \texttt{i*N + j} and \texttt{j*M + i})
are replaced with abstractions of the data layouts (e.g., \lstinline{source(i, j)} and \lstinline{destination(i, j)}). Using such abstractions, the algorithm only prescribes the logical structure of the data (the 2D index space), while the actual physical layout of the data is modifiable separately from the algorithm.

% The logic of the copy algorithm does not actually rely on the individual physical layouts of the source and destination data --- it simply copies the elements from one representation of the data to another; as such, it requires the two data structures to share the same logical structure (index space; in this case, a 2D space with size $M \times N$), but the actual physical layout of the data in memory may differ.

\begin{lstlisting}[style=C++, caption={A layout-agnostic copy algorithm}, label={lst:layout-agnostic-copy}]
// column-major layout:
auto source = make_matrix<float, 'N', 'M'>(__N, __M);
// row-major layout:
auto destination = make_matrix<float, 'M', 'N'>(__M, __N);

for (size_t i = __0; i < __M; ++i) {
  for (size_t j = __0; j < __N; ++j) {
    // a point in the M by N index space:
    auto point = idx<'M', 'N'>(i, j);
    // same indexing logic:
    destination[point] = source[point];
  }
}
\end{lstlisting}

\Cref{lst:layout-agnostic-copy} shows a layout-agnostic version of the copy algorithm that is implemented using an abstraction based on our approach. The data structures are indexed using the same logical index \lstinline{idx}, and thus, they are interchangeable with any other structure that shares the $M \times N$ logical structure, regardless of the actual physical layout.

% Syntactically, the logical layout of the data can be expressed in many different ways. For example, the \lstinline{std::mdspan} abstraction encodes different dimensions as positional arguments (e.g., \lstinline{my_mdspan(i, j)} passes iteration variable $i$ as the index in the first dimension and $j$ as the index in the second dimension), while our approach encodes different dimensions as named arguments --- \lstinline{idx<'M', 'N'>(i, j)}\footnote{\lstinline{'M'} and similar dimension names are given as \cpp character literals; alternatively, \lstinline{noarr::dim<V>()} is a more extensible way to specify a dimension name, with \lstinline{V} being an arbitrary literal value.} explicitly associates $i$ with the dimension \lstinline{'M'} and $j$ with the dimension \lstinline{'N'}.
Syntactically, the logical layout of the data can be expressed in many different ways. Our approach encodes different dimensions as named arguments --- \lstinline{idx<'M', 'N'>(i, j)} explicitly associates $i$ with the dimension \lstinline{'M'} and $j$ with the dimension \lstinline{'N'}, which avoids many indexing mistakes and is more robust in cases where different data structures have unrelated index spaces compared to the more common positional approach with forms such as \lstinline{source[i, j]} used in \lstinline{std::mdspan}~\cite{trott2022mdspan} or \lstinline{Kokkos::View}~\cite{trott2021kokkos}.

% Although this approach is generally more verbose compared to forms such as the positional approach used with mdspan or Kokkos Views (\lstinline{source[i, j]})~\cite{trott2022mdspan,trott2021kokkos}, it can prevent many indexing mistakes, as any association between an index and a dimension is explicit. Furthermore, the approach of encoding dimensions as named arguments is more robust in cases where different data structures have unrelated index spaces (e.g., accessing a structure with an unrelated index space leads to a compile-time error rather than a hidden logic error). It also reduces the reliance on implicit conventions, such as the broadcasting rules known from frameworks that choose the positional approach, such as NumPy~\cite{harris2020array}.

\section{Traversal-agnostic design}\label{sec:traversal-agnostic-design}

Traversal-agnostic design builds on top of layout-agnostic design by separating the traversal order from the algorithmic operation performed at each logical point.
% This concept is related to \cpp ranges, their views, and associated algorithms, which rely on iterability and dereferenceability without assuming unnecessary characteristics of the traversed range. A range algorithm is, in this sense, a traversal-agnostic abstraction that only assumes directly relevant and queryable characteristics of the traversed range (or view); for example, a sorting algorithm assumes random-access iteration.

In our work, we express traversal-agnostic design using the concept of \emph{index spaces} with encoded traversal order. In our proposed abstractions  following this paradigm, we represent these ordered index spaces via objects called \emph{traversers}, which generalize the concept of a \texttt{for\_each} algorithm. For the simplest case, the traverser offers a \lstinline{for_each} method that generates points in the index space of the traversed data structure, as shown in the following example of a traversal-agnostic initialization algorithm.

\begin{lstlisting}[style=C++, caption={A traversal-agnostic initialization algorithm}, label={lst:traversal-agnostic-initialization}]
// M by N array:
auto data_structure = make_matrix<float, 'M', 'N'>(__M, __N);
// traverser with the M by N index space:
auto traverser = make_traverser(data_structure);

traverser.for_each([&](auto point) {
  data_structure[point] = init_value(point);
});
\end{lstlisting}

This algorithm makes no assumptions about either the layout of the data structure or the traversal order of the algorithm --- it simply specifies an assignment for each element in the data structure. The actual traversal order is encoded in the traverser, which may be given as a parameter to the algorithm just like the data structure itself.

A \emph{traverser} is a view of one or more traversed data structures, and its derived index space is equivalent to the Cartesian product of the unique dimensions occurring in the traversed data structures. The generated points are then applicable to all traversed data structures, as they contain all expected dimensions.

This approach offers expressiveness and flexibility, which allows it to handle many different algorithms and their optimizations.

\section{Core abstractions for agnostic design}\label{sec:abstractions}

Since the first three contributions in this line of research (\cref{sec:astute-approach,sec:pure-cpp-approach,sec:cpp-abstractions}) are closely related and subsequent contributions re-evaluate abstractions from the earlier work, we present them in this thesis abstract together in this section with a common summary of the results (\cref{sec:abstractions-results}) to provide more compact and coherent context for the reader.


\subsection{Layout abstractions}\label{sec:astute-approach}

In the first contribution of this line of research, we have proposed abstractions for layout-agnostic data structures as the first milestone towards the goal of exploring design patterns for layout-agnostic and traversal-agnostic algorithms in HPC. We have presented this work in \contribref{smelko2022astute}.

The main goal of this work was to demonstrate the feasibility of designing composable layouts for layout-agnostic algorithms usable in HPC, which requires that the abstractions do not introduce significant overhead compared to hand-written code. This is a non-trivial requirement that necessitates the use of metaprogramming techniques to achieve zero-overhead abstraction and to allow compile-time constant expressions in the indexing logic of the data structures, so that the compiler can make more aggressive optimizations.

The abstractions comprise of Noarr structures (representing layouts) and proto-structures (representing transformations of layouts). The base Noarr structure is \lstinline{noarr::scalar<T>()}, which represents a single value of type \lstinline{T} with no dimensions. This structure can be extended using proto-structures like \lstinline{noarr::array<__D, __S>()}, which adds a dimension \lstinline{__D} of compile-time size \lstinline{__S} to the layout or using \lstinline{noarr::vector<__D>(__S)}, which adds a dimension \lstinline{__D} of size \lstinline{__S} that is modifiable at runtime. An example of a proto-structure that transforms only the logical structure is \lstinline{noarr::into_blocks<__D, __B>(__S)}\footnote{\lstinline{noarr::into_blocks} was introduced in later versions of the library, but provides a good example for the purpose of this discussion.}, which transforms a dimension \lstinline{__D} into blocks of size \lstinline{__S} enumerated by a new dimension \lstinline{__B}.

We can express these layouts using the proposed abstractions as shown in \cref{lst:matrix-layouts}, composing base structure \lstinline{noarr::scalar<float>()} with proto-structures using the \lstinline{^} operator\footnote{This example uses syntax consistent with later iterations of the library.}.

\begin{lstlisting}[style=C++, caption={Noarr representations of the layouts in \cref{fig:matrix-layouts}}, label={lst:matrix-layouts},float={htbp}]
// row-major layout:
auto row_major = noarr::scalar<float>()
               ^ noarr::array<'M', __M>()
               ^ noarr::array<'N', __N>();
// column-major layout:
auto col_major = noarr::scalar<float>()
               ^ noarr::array<'N', __N>()
               ^ noarr::array<'M', __M>();
// tiled row-major layout:
auto tiled_row_major = row_major
                     ^ noarr::into_blocks<'M', 'm'>(__M/2)
                     ^ noarr::into_blocks<'N', 'n'>(__N/2);
\end{lstlisting}

The proposed abstractions allow for defining data structures represented using \lstinline{noarr::bag}, which then can be indexed as shown in \cref{lst:layout-agnostic-copy}.

The Noarr structures and their derived data structures also allow for querying the properties of the data structures, such as the size of a given dimension (in bytes), length of a given dimension (in elements), or the offset of a particular element in memory, as shown in \cref{lst:layout-agnostic-query}.

\begin{lstlisting}[style=C++, caption={Querying properties of a data structure}, label={lst:layout-agnostic-query}]
auto size = row_major | noarr::get_size();
auto length = row_major | noarr::get_length<'M'>();
auto point = idx<'M', 'N'>(i, j);
auto offset = row_major | noarr::offset(point);
\end{lstlisting}

\subsection{Traversal abstractions}\label{sec:pure-cpp-approach}

After demonstrating the feasibility of layout-agnostic design in HPC, we have focused on extending the same separation principle to traversal orders, improving the expressiveness beyond layout optimization to also include traversal optimization and parallelizability, which we have presented in \contribref{klepl2024pure}.

The key concepts we introduced in this work were \emph{traversers} and transformations applicable to layouts and traversers alike. We have observed that both can be achieved by extending the concept of data layout composition, with traversers being a thin abstraction on top of their corresponding data layouts.

This required extending the design of the abstractions to encode the traversal order as well, which we achieved by introducing \emph{signatures} --- compile-time constants that specify the hierarchy of the dimensions for traversal purposes.
% In simple terms, the signature can be viewed as a tree structure that encodes the loop nesting structure of the corresponding traversal of a given data structure (or a traverser).
For example, a signature of the traversers in \cref{lst:traversal-agnostic-initialization} could be $\text{\lstinline{'M'}} \to \text{\lstinline{'N'}} \to \text{\lstinline{void}}$, which encodes \lstinline{M} as the outer dimension and \lstinline{N} as the inner dimension of the traversal (forming a loop nest), \lstinline{void} denoting the end of the hierarchy (replaced with associated element type in data structure signatures).

% To express traversal transformations and derived views of data structures, we have introduced building blocks that, instead of being just for data layout construction, can be used for defining various sub-layouts (such as submatrices), renaming dimensions, and reordering the logical hierarchies of the dimensions.
This allows for defining derived views of data structures and traversers, such as submatrices, or traversers with restricted, reordered, or renamed dimensions. The paper artifact documents how these building blocks can be extended by users of the proposed abstractions, allowing them to define their own transformations and views of data structures and traversers, including domain-specific ones.

\subsection{Results}\label{sec:abstractions-results}

We have evaluated the proposed abstractions on a set of algorithms from various areas of scientific computing included in the PolyBench/C benchmark suite~\cite{polybench4.2.1} by systematically reimplementing the algorithms using the proposed abstractions and comparing them against the original C implementations.


\subsubsection{Performance of layouts and traversals}\label{sec:abstractions-performance}

The experimental evaluation of the proposed abstractions showed that the abstractions achieve performance comparable to hand-written code while improving the flexibility of algorithm design. \Cref{fig:polybench-c} shows the wall-clock runtime of Noarr-based implementations relative to the corresponding original C implementations. For most cases, the performance matches; there are some outlier cases, mostly caused by the compiler choosing different optimization paths, that ballance out (visualized using the geometric \texttt{MEAN}).

For GPUs in particular, we have used the methodology used in \cref{sec:abstractions-performance} on the PolyBench/GPU benchmark suite~\cite{grauergray2012autotuning}.

\section{Distributed computing extensions}\label{sec:layout-agnostic}

High-performance computing often relies on distributed parallelism to scale computations across multiple nodes; thus, we therefore studied whether the proposed abstractions can be efficiently integrated with MPI, which is the predominant programming model for inter-node communication in scientific computing~\cite{mpi-5.0,laguna2019large}. We have presented this work in \contribref{klepl2025layout}.

The work shows that the proposed abstractions can be efficiently integrated with MPI datatype construction, which enables layout-agnostic communication of data structures across different nodes. We have also shown that the proposed approach can be applied to other abstractions that, to some extent, also abstract away the layout of data structures, such as the \cpp \lstinline{std::mdspan} abstraction or the Kokkos \lstinline{Kokkos::View} abstraction.

The paper presents a study comparing the proposed approach with prior works that aim to facilitate MPI communication of data structures with various layouts. We have shown that the studied prior works do not provide the full flexibility necessary for the layout-agnostic design of distributed algorithms, while the abstractions from the previous contributions have the necessary properties for this purpose. Among the most challenging properties for prior approaches was the expressiveness required to support various logically equivalent structures with different memory layouts, and automatically translating between layouts without modifying the communication logic, which is the key property for layout-agnostic communication.


\subsection{Results}\label{sec:layout-agnostic-results}

The experimental evaluation showed that the proposed approach, combined with the abstractions from the previous contributions, achieves performance comparable to equivalent hand-written code, regardless of the layout of the involved data structures, while studied prior works in many cases did not achieve the same performance.

For the evaluation, we performed a case study on distributed matrix multiplication with each of the three matrices in row-major or column-major layout. The computation started by scattering inputs corresponding to tiles of the output to available nodes from a chosen root node, followed by local computation of the output tiles, and finally gathering the results back to the root node. The results are visualized in \cref{fig:noarr-mpi}.

The visualization shows two extreme cases --- small matrices (\texttt{MINI}) and large matrices (\texttt{EXTRALARGE}). The \texttt{MINI} case should highlight how well the different approaches handle the communication overhead (MPI type construction and the communication itself), while the \texttt{EXTRALARGE} case should highlight how well the different approaches handle the local computation of the output tiles. In both cases, the Noarr-based implementation achieves performance matching the hand-written MPI implementation.

\section{Abstractions for stencil computations}\label{sec:stencil-computations}

After demonstrating the feasibility and practicality of these principles in HPC for higher-level algorithm design, we focused on applying them to iterative stencil computations on finite state spaces --- \emph{cellular automata} (CA), which are widely used in scientific computing; for example, when simulating physical and biological processes~\cite{mohebbi2020implementation,babu2021modeling,valentim2023cellular}. We have presented this work in \contribref{brabec2025cellato}.

% CA operate on multidimensional grids, applying a fixed neighborhood-based computation pattern (the stencil) with a limited state space to each \emph{cell} of the grid. The stencil is typically applied iteratively, where the output of one iteration becomes the input for the next iteration. For this class of algorithms, spatial and temporal locality are crucial for performance, and thus, many approaches already exist for transforming the computation order into blocks, in both space and time, to improve efficiency~\cite{afanasyev2021gridtools,christen2011patus,matsumura2020an5d}. However, CA also allow for stronger representation-level optimizations via \emph{bit-packing} techniques, which store multiple cell states in a single machine word and compute them in a bit-parallel fashion. To our knowledge, no prior works have proposed abstractions that would allow such optimizations to be applied generically, independently of data layout and traversal order.

CA apply fixed neighborhood-based computations (stencils) to each \emph{cell} of a multidimensional grid, where the output of one iteration becomes the input for the next iteration. For this class of algorithms, spatial and temporal locality have been shown to be crucial for performance and can be applied in a decoupled way~\cite{afanasyev2021gridtools,christen2011patus,matsumura2020an5d}. However, CA also allow for stronger representation-level optimizations via \emph{bit-packing} techniques, which store multiple cell states in a single machine word and compute them in a bit-parallel fashion. The novelty of this work lies in the application of layout-agnostic and traversal-agnostic design principles to automatically enable spacial and temporal blocking, as well as bit-packing and bitwise evaluation of the computational logic.

% This work applies the design principles from our earlier contributions at a deeper level, as it directly targets the computational logic of stencil computations.
In this work, we have proposed a \cpp-embedded domain-specific language (DSL), Cellato, that allows the user to express the computational logic of CA in a way that is independent of both the traversal order of the algorithm and the layout of the data, including the specifics of state encoding. Similarly to previous contributions, this is achieved by using metaprogramming capabilities of \cpp to achieve zero-overhead abstractions that enable
%  specialization of the computational logic for different layouts and traversal orders while allowing for aggressive optimization by the compiler.
efficient evaluation of the computational logic for the given architecture and evaluation strategy.

The abstractions support running the computations expressed in the proposed DSL on both CPU and GPU architectures, and allow applying the optimizations and parallelization in a decoupled way, without modifying the computational logic. The primitives that enable these optimizations are designed to be applicable to any stencil computation expressed in the proposed DSL\@.

\section{Summary}\label{sec:abstractions-summary}

We have presented the concept of layout-agnostic and traversal-agnostic design and shown that these design principles can be applied to HPC via abstractions that rely solely on the metaprogramming capabilities of \cpp.
% This shows that the proposed approach is directly applicable to real-world HPC applications, as the proposed abstractions fit existing \cpp toolchains and do not require any custom compiler or runtime support.
Throughout the series of contributions studying these design principles, we have shown their main benefits on CPU-based and GPU-based parallel computing, distributed computing, and domain-specific applications such as cellular automata (CA).

The novelty of this line of research lies in developing a general-purpose native abstraction for unified layout-agnostic and traversal-agnostic design in HPC, and in the application of these principles to CA with added support for domain-specific optimizations such as bit-packing and bitwise evaluation of the computational logic. Together with the explored autotuning techniques, this allows for automated optimization of the algorithms for a given target architecture, while keeping the complexity of the developed algorithms manageable.

This area still has many open questions and challenges, including its applicability to other specialized domains, support for sparse data structures, and the combination of abstractions for general computational logic with data layout and traversal abstractions, which would open up further optimization opportunities.
