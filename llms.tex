\section{Human-directed code optimization with LLMs}\label{sec:human-directed-code-optimization}

In our first contribution in the area of application of LLMs to algorithm design, we have explored the potential of LLMs under human direction to design efficient code for GPUs using the CUDA programming model. We have presented this work in \xxx{\fullcite{brabec2025tutoring}}.

The work was motivated by the \xxx{then current} ability of LLMs to generate simple code snippets, including code for GPUs, but their inability to make more complex design decisions, such as choosing appropriate data structures, layouts, and \xxx{parallelization decisions}. We have made a case study on three algorithms representing different areas of scientific computing~--- histogram computation representing a reduction problem, Game of Life simulation representing a discrete stencil computation, and k-Nearest Neighbors (kNN) search representing a search problem. The three algorithms represent different levels of complexity and different design decisions that need to be made to achieve efficient GPU execution.

The histogram computation was a simple character counting problem for a large text file. The Game of Life simulation was given as a standard brute-force implementation, where each cell of a sufficiently large grid (with states alive or dead) is updated in discrete time steps based on the states of its neighbors. The kNN search was given as a brute-force implementation on a 2-dimensional dataset with many query points, where the goal was to find the k closest points (using the standard Euclidean distance) in the dataset for each query point for $k$ values ranging from $32$ to $1024$.

Histogram computation presented the least complex and most straightforward case, where the main improvement comes from efficient privatization of the intermediate results (histogram bins) to avoid contention between threads. Game of Life simulation presented a more complex case, where the main improvement comes from efficient bit-packing of the grid (each state of a cell can be represented with a single bit) and efficient use of bitwise operations to compute multiple cells at once. The kNN search presented the most complex case, as efficient GPU implementation for the expected input sizes and dimensions requires efficient use of block-level shared memory and warp-level primitives for updating the intermediate results (nearest neighbors) using a parallel reduction with many synchronization points.

In our experiments, we have confirmed that the LLM (represented by the \xxx{GPT-o4-mini-high}, which scored within a margin of error on many benchmarks commonly used to evaluate LLMs) understood the problem and was able to reliably generate correct code for all three algorithms for if the prompts simply asked to implement the algorithm for a specific hardware (GPU\@) and there were no strict requirements on the performance of the generated code (for the kNN search, the correctness rate was by far the lowest out of the three cases, at \xxx{60\%}). However, as per the motivation, we have then attempted to guide the LLM to generate code matching an expert-written reference implementation in terms of runtime performance, by providing increasingly more specific prompts (tutoring) that dictated specific design decisions necessary to achieve the expected performance.

Our findings have shown that, for certain complexity levels of algorithms, LLMs failed to produce efficient code with general prompts suggesting to optimize the code for specific hardware. However, with increasingly more specific prompts, the solutions generated by LLMs more and more matched the expected runtime performance of the algorithms. At the time of the study, the complexity threshold allowed to observe this behavior on the histogram computation and Game of Life simulation, but the kNN search case was too complex for the LLMs to reliably generate correct and efficient implementations, even with very specific prompts.

We have explored two approaches to prompting LLMs for code optimization~--- one based on providing specific instructions on how to optimize the code in a singular prompt (where we studied different prompts of increasing specificity), and another based on an iterative process of generating code, analyzing it, and providing feedback to the LLM using pre-planned scenarios where each milestone corresponded to a prompt in the first approach. The observed behavior was similar for both approaches in all three cases, including LLMs' failure to generate correct and efficient code for the kNN search regardless specificity of the prompts.

At the time of presenting the results at the Euro-Par 2025 conference, the threshold had already increased for newer LLMs, which showed this behavior for the kNN search. For the simpler algorithms, the newer LLMs had surpassed the need for specific prompts, generating very efficient implementations even with general prompts. \xxx{(The threshold has continued to increase with newer LLMs).}


\section{\xxx{LLMs and abstractions}}\label{sec:llms-and-abstractions}

Following our work on abstractions for user-directed code optimization presented in \cref{chap:abstractions} and our experiments with LLMs for code optimization, as well as their increasing capabilities, we have explored the interoperability of LLMs with various abstractions for user-directed code optimization, including the ones we have introduced. We have presented this work in \xxx{\fullcite{klepl2026shifting}}.

The work was motivated by two main research questions. The first one was whether the abstractions optimized for human users that enable expressing various code optimizations such as data layout and traversal transformations separately from the algorithmic logic also benefit LLMs, which have skill-sets and characteristics different from human users. The second one was how the correctness and performance of code generated by LLMs is affected by the choice of abstractions used (or their lack of). We have formalized these two motivational question into five more specific and measurable research questions presented in the paper.

For our experiments, we have used the PolyBench benchmark suite, which we had previously used for evaluating our abstractions, and which was also used by prior work on LLMs for code optimization~\cite{merouani2025agentic}. As a representative LLM, we have used the newest version (at the time of the study) of the GPT family of models developed by OpenAI\@, similarly to our previous work. To limit the scope of our experiments to fit our budget options, we have focused solely on generic multicore CPU code generation, as the simplest use case allowing for parallelism.

The methodology of our experiments consisted of combining prompts of varying specificity of optimization goals (such as suggesting focus on parallelism, cache locality) with different abstractions (Halide, Exo, and Noarr, our own abstractions for user-directed code optimization) or no abstractions at all. The considered prompts included a na\"{\i}ve prompt that just directed the LLM to optimize for a multi-core CPU and comparing this with different prompts that either directed the LLM to consider various optimization goals or directed it to choose from such goals itself. It is important to note that, in contrast to our work presented in \cref{sec:human-directed-code-optimization}, the more specific prompts were not designed to dictate specific design decisions for the specific algorithms, but they suggested optimization strategies that are generally applicable to a wide variety of algorithms, thus shifting from tutoring to more general guidance, following the motivation for this study.

We have also considered an alternative approach that splits the optimization process into two steps. First, the LLM was directed to formalize the characteristics of the algorithm and the optimization strategy, and then, in the second step, the LLM was directed to generate code according to the provided optimization plan.

Our findings have shown that the abstractions optimized for human users generally hindered both the correctness and performance of code generated by LLMs. More importantly, the results of our study showed that the specificity of the prompts used to guide the LLMs had a greater impact on the performance of the generated code than the choice of abstractions or the alternative approach of splitting the optimization process into two steps.

These results suggest that, while the contemporary abstractions for user-directed code optimization can be beneficial for human users and formal validation of optimization transformations, they also restrict the design space of code that can be generated by LLMs, increasing its error rate and hindering its performance, when the LLM attempts to generate efficient implementations for the studied algorithms.


\section{Summary}\label{sec:llms-summary}

In our contributions in the area of application of LLMs to algorithm design, we have explored the potential of LLMs under human direction to design efficient code for GPUs, and the interoperability of LLMs with abstractions for user-directed code optimization. Our findings show two main insights. First, the performance of code generated by LLMs significantly depends on the specificity of the prompts used to guide the LLMs, especially for more complex algorithms. Second, the contemporary abstractions for user-directed code optimization, while beneficial for human users, and great for formal validation of optimization transformations, generally hinder the capabilities of LLMs to generate correct and efficient code. Future research in this area should explore the design of abstractions or other mechanisms that are more suitable for LLMs, as well as building scaffolding tools that can automatically generate specific prompts for LLMs to guide them towards generating efficient code for a wide variety of algorithms and hardware architectures.
