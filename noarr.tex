\section{Noarr Library}\label{chap:noarr}

The Noarr library, first introduced in~\cite{vsmelko2022astute}, is a \cpp library that provides layout-agnostic abstractions for representing and manipulating multidimensional data structures and their traversals.

Formally, the abstractions are based on partial functions on the index space and memory space of multidimensional arrays. Each such partial function is represented by a primitive building block called a \emph{proto-structure} --- examples of proto-structures include \lstinline{scalar}, which represents a single value; \lstinline{array}, which represents a contiguous array of elements represented by another structure; or \lstinline{into_blocks}, which represents a view of another structure that divides one of its dimensions into blocks of a given size.

The composable design of Noarr bears resemblance to views in the ranges library in \cpptwenty~\cite{niebler2018one}; however, while being composable in a hierarchical manner, Noarr structures allow better flexibility and type-safety for multidimensional data structures by representing the index space using named dimensions that are resolved at compile time.

Since the index space is represented using named dimensions, all queries on the structure, such as obtaining the size of a dimension or the memory offset of an element at a given index, are type-safe and checked at compile time. In contrast to traditional positional indexing of multidimensional arrays (e.g., \lstinline{data[i][j]}), which is prone to errors due to wrong pairing of indices to dimensions, type-safe indexing using named dimensions (e.g., \lstinline{data[idx<'x'>(i) + idx<'y'>(j)]}) ensures that the indices are paired with the correct dimensions. This also makes the memory access API self-documenting and independent of the actual layout of the data in memory.


\subsection{Noarr Structures}\label{sec:noarr-structures}

\begin{figure}[htbp]
  \centering
  \includegraphics[width=.8\linewidth]{img/noarr-structure-composition.eps}
  \caption{The principle of composition of Noarr structures. Each proto-structure is a wrapper adapting the interface of its sub-structure, creating a composite structure with a modified index space and memory space.}%
  \label{fig:noarr-structure-composition}
\end{figure}

Noarr structures are immutable abstractions representing multidimensional data structures built by composing primitive proto-structures in a hierarchical manner as depicted in \cref{fig:noarr-structure-composition}. Each proto-structure represents a transformation of the index space and memory space of the nested \emph{sub-structure}; thus, if the sub-structure represents a multidimensional array with dimensions \lstinline{'y'} and \lstinline{'z'}, then wrapping it in an \lstinline{array} proto-structure with dimension \lstinline{'x'} results in a three-dimensional array with dimensions \lstinline{'x'}, \lstinline{'y'}, and \lstinline{'z'}.

The composition in this example simply adds a new dimension to the index space, extending it from two to three dimensions accordingly. However, other proto-structures may perform more complex transformations of the index space, such as splitting a dimension into multiple dimensions (e.g., \lstinline{into_blocks}, which consumes one dimension and produces two new dimensions) or reordering the logical hierarchy of dimensions (e.g., \lstinline{hoist}).

The composition of proto-structures is done using \cpp template meta-programming and, in the Noarr library~\cite{vsmelko2022astute}, it is represented by the \lstinline{^} operator. Since each proto-structure represents a partial function on the index space and memory space of the sub-structure, the composition of proto-structures is naturally associative. This is a powerful property that allows defining more complex transformations from simpler ones, applying them simultaneously, and reusing them with multiple data structures. This mirrors the principle of composability of views in the ranges library via the \lstinline{operator|} operator, but with better support for multidimensional data structures and type-safety of transformations on the index space.

Proto-structures can have multiple input dimensions and multiple output dimensions. If a dimension is not mentioned in the proto-structure, it is passed through unchanged from the sub-structure to the resulting structure. If a dimension appears as an input dimension but not as an output dimension, it is \emph{consumed} by the proto-structure; similarly, if a dimension appears as an output dimension but not as an input dimension, it is \emph{produced} by the proto-structure.

The intermediate state (most notably, lengths and indices of the named dimensions) is passed from the outermost proto-structure to the innermost sub-structure in a \emph{state} argument; just like each proto-structure represents a partial function (transformation) on the index space and memory space, it equally represents a partial function on the state in the reverse direction. Any produced dimensions are removed in the sub-state passed to the sub-structure and all consumed dimensions are added. This principle strengthens the type-safety of Noarr structures by ensuring that a dimension is not propagated unexpectedly.

One further property of proto-structures that operate on multiple input dimensions (or multiple output dimensions) is that if there are dependencies between the input and output dimension lengths (e.g., the input dimension of \lstinline{into_blocks} can be expressed as the product of the two output dimensions), the Noarr library automatically infers the unspecified lengths and indices from these dependencies. It propagates them when querying dimension lengths, issuing static assertions on ambiguous constructions --- e.g., when all three lengths of the dimensions of \lstinline{into_blocks} are specified.

This property allows specifying the lengths either from the underlying untiled structure or from the tiled transformation, and vice versa. This comes in handy when some of the dimensions are freely tunable and others are fixed by the logic of the computation or by hardware constraints (e.g., specifying the tile size of a dimension based on the number of available threads).

Querying a specific property of a Noarr structure, such as obtaining the memory offset of an element at a given index, is expressed as a function that takes the formal arguments of the query and a \emph{state} argument representing the index space, i.e., the lengths of the dimensions and the input indices (thus, an offset query takes no formal arguments, only the state). The proto-structure defines how the state is propagated to the sub-structure (\emph{sub-state}), and the result of the query depends on the formal arguments, the contents of the state, and further queries on the sub-structure using the sub-state (if needed). Some proto-structures generalize this idea by having multiple sub-structures (e.g., the \lstinline{tuple} proto-structure), choosing the appropriate sub-structure based on the state.


\begin{figure}[htbp]
  \centering
  \includegraphics[width=.8\linewidth]{img/noarr-structure-offset.eps}
  \caption{The principle of querying a property of a Noarr structure. The query propagates the state and the formal arguments through the proto-structure to the sub-structure(s) and the result is propagated back to the caller.}%
  \label{fig:noarr-structure-offset}
\end{figure}

For example, querying the offset of an element in an \lstinline{array} proto-structure with size~$N$, dimension~\lstinline{'x'}, and a sub-structure~$S$, given an index state $s$, depicted in \cref{fig:noarr-structure-offset} proceeds as follows:

\begin{enumerate}
  \item Extract the index~$i$ for dimension~\lstinline{'x'}
  \item Compute the sub-state~$s'$ by removing dimension~\lstinline{'x'} from~$s$
  \item Query the size~$sz$ of the sub-structure~$S$ using the sub-state~$s'$
  \item Compute the offset as $i \cdot sz + \text{offset}_S(s')$, where $\text{offset}_S(s')$ is a query of the offset on the sub-structure~$S$ using the sub-state~$s'$
\end{enumerate}

The notion of sub-structure and (sub-)state provides a clean framework for defining all queries on Noarr structures. In the Noarr library, most of the queries are implemented as templated member functions of the structure classes.

Many proto-structures define only the sub-state, and just pass the queries to their sub-structure(s) without any additional logic. Examples include \lstinline{set_length} that defines the length of a dimension, \lstinline{rename} that renames a dimension of the sub-structure, \lstinline{span} that restricts the iteration space of a dimension to a given range. Some proto-structures, like \lstinline{into_blocks} that divides a dimension into blocks of a given size, define only some queries, and pass the rest to the sub-structure (\lstinline{into_blocks} defines custom logic only for length queries). This means that in such cases a definition of offset queries is equivalent to \lstinline|[this](auto state) { return sub_structure(state).offset(sub_state(state)); }|, where the sub-structure and sub-state are defined by the proto-structure accordingly.

\xxx{(SIDENOTE)} Formally speaking, since sub-structure queries always use sub-states, we can conceptually define each query on a Noarr structure as a composition of the properties of the sub-structure (the propagation of the sub-state is implicit), formal arguments, and the contents of the state. For example, in the case of a vector proto-structure, we could define \lstinline{offset = index<'x'> * size + offset} and \lstinline{size = length<'x'> * size}, where all left-hand-side arguments refer to properties of the resulting structure and all right-hand-side arguments refer to state parameters or sub-structure properties dependent on the sub-state specified separately (e.g., \lstinline{state = state.without<'x'>()}), where the left-hand-side refers to the sub-state and the right-hand-side refers to the state of the current structure (since states are propagated in the reverse direction compared to the queried structure properties). This allows for a cleaner definition of proto-structures, but is only partially implemented in the Noarr library. Currently, this principle drives the design of proto-structures and their queries, but is left for further development either when language features allow for higher-level abstractions (for example, using reflection and compile-time code generation) or when the design principles are used to develop a framework separated from the design restrictions of the \cpp language. However, this design principle allows for developing formal proofs of the properties of proto-structures and their compositions --- only some of them are currently implemented in the Noarr library via static assertions.

The second main feature of Noarr structures is their \emph{signature}. A signature is a representation of the hierarchy of the dimensions of the structure. It is a necessary component for specifying intended traversals of the structures and also allows for improved type-safety. Some proto-structures can be used to change the signature and thus the intended traversal of the structure; for example, \lstinline{hoist} moves a dimension up in the hierarchy, specifying that the corresponding traversal iterates it in the outermost loop.

A signature can be interpreted as a tree where each node represents a dimension and its children represent nested dimensions.
The signature of a given Noarr structure results from a transformation of the signature of its sub-structure(s) based on the semantics of the proto-structure. For example, the signature of an \lstinline{array} structure is represented by a root node representing the array dimension, with a single child representing the signature of the sub-structure as shown in \cref{fig:noarr-structure-signature}.

% Signatures partially resemble the notion of types in lambda calculus, where the signature of an \lstinline{array} proto-structure roughly corresponds to a function type taking the new dimension and returning the sub-structure signature, and the signature of the \lstinline{fix<'x'>(i)} proto-structure (which fixes the index of dimension \lstinline{'x'} to a given value~$i$) roughly corresponds to application in this analogy. Proto-structures such as \lstinline{into_blocks} are better interpreted on the tree representation, where the path through the consumed dimension is replaced by a new subtree representing the newly produced dimensions.

Note that consumed and produced dimensions affect the signature accordingly (in the reverse way compared to dimension consuming in states) --- consumed dimensions are removed from the signature of the sub-structure and produced dimensions are added as new nodes in the signature tree (usually at the place of the consumed dimensions; however, different proto-structures may define different semantics).

\begin{figure}[htbp]
  \centering
  \includegraphics[width=.8\linewidth]{img/noarr-structure-signature.eps}
  \caption{Signature of \lstinline{scalar<int>() ^ array<'x'>(N) ^ array<'y'>(M)} structure.}%
  \label{fig:noarr-structure-signature}
\end{figure}

Since layouts are most often used as mappings to memory, Noarr provides a \emph{bag} wrapper that represents a pointer to a memory buffer containing the data described by the given structure. The \lstinline{bag} wrapper provides methods for obtaining references to elements at given indices as well as other utility methods. An example of creating a Noarr structure representing a two-dimensional matrix of size $N \times M$ is shown in \cref{lst:noarr-matrix-structure}.

\begin{lstlisting}[language=C++, caption={Creating a matrix structure using Noarr.}, label=lst:noarr-matrix-structure]
auto matrix = bag(scalar<int>() ^ array<'x'>(N) ^ array<'y'>(M));

// Accessing element at (i, j)
matrix[idx<'x'>(i) + idx<'y'>(j)] = i + j;

// Getting size of dimension 'x'
auto size_x = matrix | get_length<'x'>();
auto size_y = matrix | get_length<'y'>();
\end{lstlisting}


\subsection{Noarr Traversers}\label{sec:noarr-traversals}

Noarr traversers~\cite{klepl2024pure} are wrapper abstractions over one or multiple Noarr structures that provide an interface for performing actions over their index spaces. In the simplest case, creating a Noarr traverser over a single Noarr structure and invoking its \lstinline{for_each} method with a callable results in invoking the callable for each point in the index space of the structure.

\begin{lstlisting}[language=C++, caption={Creating and using a Noarr traverser over a single structure.}, label=lst:noarr-traverser-single-structure]
auto matrix = bag(scalar<int>() ^ array<'x'>(N) ^ array<'y'>(M));
traverser(matrix).for_each([&](auto state) {
  auto [i, j] = get_indices<'x', 'y'>(state);
  matrix[state] = i + j;
});
\end{lstlisting}

The single argument passed to the callable is a state object containing the named indices for all dimensions of the structure. The traverser follows the signature of the structure to determine the order of iteration over the dimensions; thus, for signatures that form non-linear hierarchies (where at least two child sub-signatures share a parent dimension), the callable is invoked in a depth-first manner for all points corresponding to the leaf nodes of the signature tree.

Similarly to Noarr structures, Noarr traversers can be further transformed using proto-structures that modify the index space and the signature. For example, the following snippet creates a traverser over the same matrix structure as before, but divides both dimensions into blocks of given sizes.

\begin{lstlisting}[language=C++, caption={Creating a Noarr traverser with blocked traversal.}, label=lst:noarr-traverser-blocked]
auto trav = traverser(matrix)
  ^ into_blocks<'x', 'X'>(block_size_x)
  ^ into_blocks<'y', 'Y'>(block_size_y)
  ^ hoist<'X', 'Y'>();
trav.for_each([&](auto state) { /* ... */ });
\end{lstlisting}

When the traverser is created over multiple Noarr structures, the resulting index space is the cover of the index spaces of all structures, constructed using the leftmost structure as the base and extending its index space by adding the uncovered dimensions of each subsequent structure. This construction is represented by the traverser signature, formed by taking the signature of the leftmost structure and iteratively prepending the uncovered dimensions of the other structures in the order they appear.

For example, if it is created over two two-dimensional structures with dimensions \lstinline{'x'}, \lstinline{'y'} and \lstinline{'y'}, \lstinline{'z'}, respectively, the resulting index space is three-dimensional with dimensions \lstinline{'x'}, \lstinline{'y'}, and \lstinline{'z'} as depicted in \cref{fig:noarr-traverser-multiple-structures}.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=.8\linewidth]{img/noarr-traverser-multiple-structures.eps}
  \caption{Creating a Noarr traverser over two structures with different signatures results in a traverser with a signature that is the cover of the signatures of the structures.}%
  \label{fig:noarr-traverser-multiple-structures}
\end{figure}

Noarr traversers have a similar relationship to Noarr structures as iterators and range algorithms in the \cpptwenty ranges library~\cite{niebler2018one} have to ranges. The main difference is that Noarr traversers operate on multidimensional index spaces inferred from the Noarr structures, while range algorithms operate on one-dimensional sequences of elements.

Similarly to iterators in \cpp algorithms, Noarr traversers can be used to run the given callable objects in parallel on a chosen backend. Noarr currently supports parallel execution using OpenMP, Intel TBB, \cpp standard threads, and CUDA\@. The following snippet shows binding four dimensions of the traverser to CUDA thread blocks.

% TODO: fix the syntax
\begin{lstlisting}[language=C++, caption={Using a Noarr traverser to run a computation on CUDA-enabled GPU.}, label=lst:noarr-traverser-cuda]
auto cuda_trav = cuda_threads<'X', 'x', 'Y', 'y'>(trav);
kernel<<<cuda_trav.grid_size(), cuda_trav.block_size()>>>(cuda_trav.inner());
\end{lstlisting}

In our work~\cite{klepl2024pure}, we have shown that careful use of Noarr structures and traversers can express the code logic in PolyBench/C kernels in a layout-agnostic and traversal-agnostic manner, without sacrificing performance compared to the original implementations. We have shown similar results for parallel implementations of the kernels using OpenMP, TBB, and CUDA backends. The main advantage of using Noarr in this context is the ability to easily change the data layouts and traversal orders without having to modify the computation logic or memory access expressions.

A secondary advantage is that all memory accesses are type-safe and checked at compile time, preventing many common programming errors related to multidimensional array indexing.


\subsection{Noarr autotuning extension}\label{sec:noarr-autotuning}

In our subsequent work~\cite{klepl2024abstractions}, we have introduced an autotuning extension to the Noarr library that allows expressing tunable parameters controlling data layouts and traversal orders using Noarr structures and traversers directly in \cpp code. The tunable parameters can represent choices such as data layout permutations (e.g., row-major vs.\ column-major order), tiling sizes, and parallelization strategies.

Since these parameters are expressed within the Noarr abstraction layer, changing them does not require modifying the computation logic in kernels, which remains layout-agnostic and traversal-agnostic. The autotuning extension then exposes these parameters to an external autotuning framework (such as OpenTuner~\cite{ansel2014opentuner}) that systematically explores the space of possible configurations to find the best-performing combination for the target hardware.

The tuning is independent of Noarr structures and traversers, but is designed to work seamlessly with them. It is implemented directly in \cpp and any tuning specification is expressed in an enclosed section of the target source code. It allows to define tunable scalar parameters that can be used as first-class \cpp variables in the code as well as choices between different Noarr transformations (proto-structures) that can be applied to the structures and traversers.

\subsection{Noarr MPI extension}\label{sec:noarr-mpi}

The MPI type system is compatible with layout-agnosticism, since MPI datatypes are equivalent for the purposes of communication whenever their signatures\footnote{An MPI datatype signature is a sequence of base element types in their semantic order, disregarding their displacements in memory.} are the same. This characteristic is similar to the notion of layout-agnosticism in Noarr structures, where the semantic order of elements is specified by the named dimensions; thus, given a linearization of the named dimensions in a Noarr structure, a Noarr structure corresponds to a specific MPI datatype (disregarding different ways of constructing it). As described in \cref{sec:noarr-structures}, such linearization can be represented by a Noarr signature. % TODO: choose a different term than linearization?

In our work~\cite{klepl2024abstractions}, we have introduced the Noarr MPI extension that leverages the fact that traversers can be created over multiple Noarr structures simultaneously. This provides a clean API built on top of Noarr traversers to express communication patterns involving multiple Noarr structures that may have different layouts, as shown in \cref{fig:noarr-mpi-communication}. Each computation step connected by communication with other steps can use its own preferred layout without having to modify the communication logic.

We showcase the proposed approach on a distributed matrix multiplication example, with \lstinline{broadcast} and \lstinline{scatter}/\lstinline{gather} communication patterns. Experimental evaluation shows that the automated generation of MPI datatypes from Noarr structures and traversers introduces negligible overhead compared to hand-crafted MPI datatype definitions, regardless of the data layout used.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=.9\linewidth]{img/noarr-mpi-communication.eps}
  \caption{Two matrices with different layouts transformed according to the common traverser \lstinline{T = traverser(A, B)} into matching MPI types for communication. Numbers indicate the offsets of elements in memory.}%
  \label{fig:noarr-mpi-communication}
\end{figure}

Since two corresponding Noarr structures at the sender and receiver side (with same dimensions but possibly different layouts) correspond to many different MPI datatypes depending on the linearization of the dimensions, using Noarr traversers to express the semantic order of the communicated data brings the opportunity to explore different MPI datatype linearizations by adjusting the traverser signatures. Noarr offers proto-structures, such as \lstinline{hoist} (see \cref{sec:noarr-structures}), that can be used to safely reorder the dimensions of the traverser signature without affecting the correctness of the communication.

In our work, we have also applied the layout-agnostic MPI datatype construction approach to Kokkos views~\cite{trott2021kokkos} and mdspan~\cite{trott2022mdspan}, which offer efficient multidimensional array abstractions. However, as these abstractions do not provide named dimensions or otherwise encode the semantic order of elements in their type system, such application relies on careful pairing of positional indices to the appropriate dimensions.

The tuning capability available in the Noarr-based approach could be replicated in this context by providing a permutation of the positional dimensions that controls the layout linearization. However, without named dimensions, such an approach generalizes poorly to more intricate data structures and communication patterns.


\subsection{Summary}\label{sec:noarr-summary}

% We need to add some concluding remarks here: why is Noarr important? What does it enable? Who cares?

The works described in this section show that layout-agnostic and traversal-agnostic abstractions, such as those provided by the Noarr library, can express the logic of computations and communications in HPC applications in a way that separates concerns between the computation/communication logic and the data layout and traversal order.

This separation of concerns introduces more flexibility in the design and implementation of HPC applications, allowing developers to easily change the data layout and traversal order by swapping transformations applied to the structures (i.e., proto-structures in Noarr) and adjusting tile sizes or other tunable parameters, without modifying the logic of the computation and communication.

This flexibility, combined with the ability to infer sizes of co-dependent dimensions and to enforce type-safety of memory accesses and transformations (as exemplified by the Noarr library), allows for easier exploration of the design space of HPC applications, enabling developers to find better-performing implementations. This improves performance portability of HPC applications across different hardware architectures, as we have shown that the approach is applicable to a wide range of programming models and hardware architectures, including CUDA-enabled GPUs and MPI-based distributed systems.
