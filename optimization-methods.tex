As discussed in \cref{chap:code-optimization}, code optimization is crucial for achieving efficient execution of programs on modern hardware architectures such as multi-core CPUs and GPUs. In this chapter, we outline several prominent optimization methods and frameworks that have been developed to facilitate (automated) code optimization in high-performance computing applications, putting particular emphasis on those that are relevant to our work targeting data layout and traversal optimizations.

Code optimization methods can target different points in the compilation and execution pipeline --- some methods operate above the source code level, providing high-level abstractions or domain-specific languages (DSLs) that allow developers to express computations in a way that is amenable to more powerful optimizations. Other methods perform optimizations at the source code level, possibly using annotations or pragmas to guide the optimization process. More low-level methods operate on intermediate representations (IRs) or directly on the generated machine code, applying transformations to improve performance based on static analysis or empirical measurements. Some methods may also involve runtime systems that adaptively optimize code during execution based on observed performance characteristics; in such cases, methods like just-in-time (JIT) compilation techniques may be employed to generate optimized code on-the-fly based on the current execution patterns.

We primarily focus on abstractions and frameworks that operate above or at the source code level, as these are most relevant to our work. However, we also briefly discuss the wider landscape of optimization methods to provide context for our contributions.

Compiler optimizations are a fundamental aspect of modern compilers. In high-performance computing, compilers such as LLVM~\cite{lattner2004llvm} and GCC~\cite{gcc} implement a wide range of optimization techniques to improve the performance of source code, starting from basic optimizations that remove abstractions and redundant computations, inline functions, perform sub-expression elimination, etc. More advanced optimizations include loop transformations (e.g., loop unrolling, loop fusion, invariant code motion), vectorization, and inter-procedural optimizations that analyze and optimize across function boundaries.

In the context of typical high-performance (scientific computing) applications with quite simple control flow and heavy numerical computations, these optimizations mainly allow using higher-level abstractions (e.g., \cpp templates, mdspan, \ldots) without significant performance penalties (most notably, when using so-called zero-cost abstractions~\cite{stroustrup2012foundations}). They can also optimize arithmetic expressions, eliminate redundant computations, and perform some basic loop transformations. However, these optimizations by themselves are often insufficient to achieve optimal performance on modern hardware architectures, especially for complex loop nests and data access patterns.

Some compilers and frameworks, such as MLIR~\cite{lattner2021mlir}, provide extensible intermediate representations that allow for custom representation and optimization passes to be implemented --- some of them targeting specific domains or hardware architectures. This is particularly useful for domain-specific languages (DSLs) that can leverage MLIR to implement their own optimization pipelines, including polyhedral optimizations, autotuning, and other transformations that are not typically part of general-purpose compilers. While it is built on top of traditional SSA-based IRs, it allows for defining custom dialects, and facilitates all boilerplate such as parsing, code generation, and so on. % Note: Halide and Tiramisu do NOT use MLIR; they have their own IRs. MLIR is used by e.g., IREE, Torch-MLIR, Polygeist~\cite{moses2021polygeist}.

Workloads comprising nested loops with affine bounds and affine memory accesses (Static Control Parts, or SCoPs) are common in high-performance computing applications (see, e.g., \citeauthor{bacon1994compiler}~\cite{bacon1994compiler}). To target such applications, \citeauthor{feautrier1992some}~\cite{feautrier1992some} and others pioneered the use of the polyhedral model to represent and optimize computations in loop nests. Polyhedral optimization frameworks, such as Polly~\cite{grosser2012polly}, GRAPHITE~\cite{trifunovic2010graphite}, and PLuTo~\cite{bondhugula2008pluto}, use the powerful mathematical framework of polyhedral model (provided by libraries such as ISL~\cite{verdoolaege2010isl}) to represent the computations in loops in a more compact and analyzable form compared to traditional compiler IRs such as Static Single Assignment (SSA) forms. Polyhedra offer a way to represent data layouts, loop iteration spaces, and dependencies between computations in a unified manner.

Polyhedral optimization is application of integer linear algebra to optimize loop nests with affine bounds and affine memory accesses. The main idea is to represent the iteration space of loops, as well as memory accesses and dependencies, using polyhedra. This representation allows, for example, to find hyperplanes orthogonal to data dependencies, that can represent parallelizable loops; or to find transformations of the iteration space that improve data locality or enable vectorization.

Flexible abstractions allowing manipulation of data layouts and iteration orders have been the subject of extensive development. They provide a means to optimize performance to different hardware architectures without needing to change the core algorithmic logic. These abstractions can also represent flexible API layers for libraries (such as linear algebra libraries; TODO cite).

We can broadly categorize these abstractions into the following groups:

\begin{description}
  \item[Domain-specific languages (DSLs):]\label{des:dsl} These are specialized programming languages designed to express computations in specific domains, such as image processing (Halide~\cite{ragan2013halide}), polyhedral code generation (Tiramisu~\cite{baghdadi2019tiramisu}), or array programming (Futhark~\cite{henriksen2017futhark}). They rely on sophisticated compilers or runtime systems to generate optimized code for the target hardware. These DSLs often sacrifice some generality for better analysis and optimization opportunities --- for example, Halide has a fixed computation model based on pipelines of processing stages that has limited expressivity for nested control flow or data-dependent computations.
  \item[Annotation-based tools:]\label{des:annotation-based-tools} These tools, relying on compiler extensions or external preprocessors, allow developers to annotate their code with optimization directives. Examples include OpenMP for parallelization and pragmas for loop transformations. Compared to DSLs, these tools operate on top of the target language (e.g., C/\cpp) and maintain higher generality, or at least compatibility with the host language. However, they may be also limited by specific semantics of the host language. % TODO: remove contradictions etc

  \item[Parallelization frameworks and libraries:]\label{des:parallelization-frameworks} These frameworks provide abstractions enabling developers to run computations in parallel using high-level constructs. These abstractions play a crucial role in optimizing applications for modern high-performance computing, as the scale and complexity of diverse hardware architectures continue to grow and traditional low-level optimization techniques are not sufficient to achieve optimal performance. The abstractions enable developers to apply optimizations based on domain knowledge, empirical performance data, or autotuning techniques. Compared to hand-tuned low-level code, maintainability and portability of high-level abstractions is significantly better and the development time is reduced. Many of these abstractions also support advanced validation of correctness of the code transformations.


\subsection{Domain-specific languages (DSLs)}\label{sec:dsls}

Halide~\cite{ragan2013halide} is a \cpp-embedded DSL with a custom compiler and runtime system that primarily targets image and array processing applications (including regular stencil computations). It is based on defining pipelines of processing stages, where each stage represents a computation that can be optimized independently. The resulting computation pipeline is a directed acyclic graph (DAG) of stages that are subject to various transformations, such as tiling, fusion, and parallelization. These transformations can be guided by the developer using a scheduling language or by autotuning techniques. The Halide compiler performs various checks to ensure that each transformation preserves the semantics of the original computation. It uses interval analysis, which is a less expressive but more powerful (for the target domain) representation than the polyhedral model. Halide's design allows for a high degree of optimization at the cost of expressivity, as it is not suitable for more complex computations, such as those that contain imperfectly nested loops or data-dependent control flow, or non-rectangular iteration spaces.

OpenMP~\cite{openmp_6.0_spec} is a widely used API for parallel programming in C, C++, and Fortran\@. It provides a set of compiler directives, library routines, and environment variables that allow developers to specify parallelization and synchronization of code regions, as well as to control data sharing or privatization between threads. It supports various loop transformations such as loop unrolling, tiling, and vectorization via \lstinline{#pragma omp} directives. Loopy~\cite{namjoshi2016loopy} is an annotation-based tool that allows developers to express affine transformations of loop nests by specifying mappings of the schedules of the statements in nested loops as shown in the following example:

\begin{lstlisting}
for (i = 0; i < N; i++) {
  for (j = 0; j < N; j++) {
    Init: C[i][j] = 0;

    for (k = 0; k < N; k++) {
      Mult: C[i][j] += A[i][k] * B[k][j];
    }
  }
}

realign(Init, Mult, 0)
affine(Mult, {[i, j, k] -> [i, k, j]})
affine(Mult, {[i, j, k] -> [i1, j1, k1, i2, j2, k2]:
  i1 = [i/64] and j1 = [j/64] and k1 = [k/64] and
  i2 = [i%64] and j2 = [j%64] and k2 = [k%64]})
\end{lstlisting}

This performs loop interchange and tiling transformations on the original loop nest (the two \lstinline{affine} directives); the \lstinline{realign} directive is used to specify that the two statements should be treated as two separate loop nests (with data dependencies between them preserved), as the third argument ($0$ in this case) specifies the number of loops that should be shared between the two statements after the transformation. This allows the subsequent directives to be applied to each statement independently. The framework performs correctness checks to ensure that the transformations preserve the semantics of the original computation,

\subsection{Native tools and libraries}\label{sec:native-tools}

Cutlass~\cite{thakkar2023cutlass} CuTe is a collection of \cpp template abstractions that can hierarchically represent multidimensional layouts of threads and data. They are specifically designed for representing and optimizing computations on NVIDIA GPUs\@. The multidimensional layouts can represent a wide range of dense linear algebra computations, and they also allow for functional composition of layouts like in Noarr\@, which is particularly useful for common transformations such as tiling or partitioning \xxx{(cite the cute wiki)}.

GridTools~\cite{afanasyev2021gridtools} is a \cpp-embedded DSL that targets stencil computations on structured grids, primarily in the context of weather and climate modeling. The stencil computations are represented as a composition of abstract stages implemented as \cpp functors. The framework supports backends for various hardware architectures, including many-core CPU systems and GPUs\@. Since the stencil stages are represented in a high-level manner, the framework can apply various hardware-specific optimizations depending on the target backend. \xxx{continue from here.}

MDSpans~\cite{trott2022mdspan} are a \cpp abstraction for representing multidimensional arrays with flexible data layouts. The mapping of multidimensional indices to linear memory addresses and the element access policy that translates the resulting linear index to element references are both customizable, which allows for representing a wide range of data layouts and special memory types. The predefined layouts include row-major, column-major, and generic strided layouts, but the abstraction itself allows for defining custom memory layouts as well --- however, it does not provide any built-in mechanism for hierarchical composition of layouts or their analysis beyond recognizing the predefined ones and retrieving their strides and extents.

MDSpans are sufficient for representing simple data layouts, and the user-definable policies allow for using them beyond that as well. However, in such cases, they do not provide any benefits other than providing a uniform interface for accessing elements, which is not much different from using raw pointers and manual index calculations. In particular, they do not introduce any type safety or correctness guarantees and their interface is reliant on the user to correctly implement the access policies and communicate the intended semantics of the layout dimensions and the mapping to memory addresses by other means if they are not using the small set of predefined layouts. This is usually sufficient as long as the design of an optimized computation performs transformations such as tiling or transposition of the dimensions, which are supported by the \lstinline{submdspan} constructor and the predefined \lstinline{layout_transpose} policy adaptor.

Kokkos~\cite{trott2021kokkos} is a \cpp library that provides abstractions for parallel execution and data management across different hardware architectures, its primary focus is providing a performance-portable programming model for multi-core CPUs and GPUs\@. It provides the \lstinline{Kokkos::View} abstraction for representing multidimensional arrays with flexible data layouts and memory spaces (e.g., host memory, device memory, \ldots). The expressiveness of the \lstinline{Kokkos::View} abstraction, when it comes to representing data layouts, is similar to that of MDSpans\@, with the same predefined layouts and user-definable mapping policies --- and the two abstractions can be easily interconverted. However, Kokkos views also allow specifying the memory space where the data is allocated, and they provide automatic data movement between memory spaces when necessary. Kokkos views also support shared ownership semantics similar to \cpp shared pointers. Kokkos provides a set of parallel algorithms (e.g., \lstinline{parallel_for}, \lstinline{parallel_reduce}, \ldots) that can run the user-defined computations in parallel on the target backend.

To support multidimensional parallelism, Kokkos provides the \lstinline{MDRangePolicy} abstraction, which allows for defining parallel execution policies over multidimensional index spaces. The \lstinline{MDRangePolicy} parallelizes the execution of a user-defined computation in tiles of configurable sizes. To support more flexible parallelization strategies, Kokkos also provides the \lstinline{TeamPolicy}, which allows for defining teams of threads that can cooperate on executing a user-defined computation with synchronization and shared memory capabilities (team scratch memory). The \lstinline{ThreadVectorRange} can be used to express vector-level parallelism within a team (or warp/wavefront on GPU\@). These policies are composable, allowing for expressing multilevel parallelism. Furthermore, the computation can be queued to a specific execution stream on the target backend, which allows for overlapping computation and data movement.

RAJA~\cite{beckingsale2019raja} is another \cpp library that provides abstractions for platform portability for high-performance computing applications. It abstracts data layouts via the \lstinline{RAJA::Layout} class, which represents a dense multidimensional array layout, defaulting to row-major order but allowing for arbitrary permutations of the dimensions. The library also provides the \lstinline{RAJA::OffsetLayout} class, which differs in that it represents layouts with arbitrary integer offsets for each dimension --- this simplifies, for example, definition of stencil computations that expect padding around the data. Both of these layout abstractions can be used to define a \lstinline{RAJA::View}, which is a multidimensional array abstraction that provides an interface for accessing elements based on the defined layout. The expressiveness of these abstractions is lower than that of MDSpans or Kokkos views, but they allow for the inverse mapping of linear indices to multidimensional indices.

While RAJA provides much weaker abstractions for data layouts, it provides more flexible abstractions for parallel execution compared to Kokkos\@. In particular, it allows for defining representing complex loop nests via the \lstinline{RAJA::kernel} abstraction that can be applied to a kernel execution policy that is defined as a composition of compile-time constructs representing statements via template metaprogramming. The two main statement building blocks for defining the kernel execution policies are \lstinline{RAJA::For} and \lstinline{RAJA::Lambda} constructs, which represent a single loop level and a computation to be executed at that loop level, respectively. RAJA provides a wide range of statement building blocks that can represent tiling, running the nested statements in a CUDA or HIP kernel, or performing reductions, among others. These building blocks can be given an execution policy that defines how the represented loop level is parallelized (e.g., sequentially, via OpenMP, mapping to a CUDA block or grid dimension, \ldots). The resulting kernel execution policy represents a complex loop nest parallelized according to the specified execution policies, that is then used by the \lstinline{RAJA::kernel} abstraction to execute user-defined computations with the supplied parameters as shown in the following example:

% https://raja.readthedocs.io/en/develop/sphinx/user_guide/tutorial/kernel_nested_loop_reorder.html
\begin{lstlisting}[morekeywords={RAJA}]
RAJA::TypedRangeSegment<KIDX> KRange(kmin, kmax);
RAJA::TypedRangeSegment<JIDX> JRange(jmin, jmax);
RAJA::TypedRangeSegment<IIDX> IRange(imin, imax);

RAJA::OffsetLayout<3> layout = RAJA::make_permuted_offset_layout
  ({{imin, imax}, {jmin, jmax}, {kmin, kmax}}, {2, 0, 1});
RAJA::View<double, RAJA::OffsetLayout<3>> view(data, layout);

using KJI_EXECPOL =
  RAJA::KernelPolicy<
    RAJA::statement::For<2, RAJA::seq_exec,    // 2: k
      RAJA::statement::For<1, RAJA::seq_exec,  // 1: j
        RAJA::statement::For<0, RAJA::seq_exec,// 0: i
          RAJA::statement::Lambda<0>
  > > > >;

RAJA::kernel<KJI_EXECPOL>(
  RAJA::make_tuple(/*0*/ IRange, /*1*/ JRange, /*2*/ KRange),
  [=] (/*0*/ IIDX i, /*1*/ JIDX j, /*2*/ KIDX k) {
    view(i, j, k) = i + j + k;
  });
\end{lstlisting}

In the above example, we define a 3D loop nest with iteration spaces defined by the \lstinline{KRange}, \lstinline{JRange}, and \lstinline{IRange} segments that operates on a 3D array represented by the \lstinline{RAJA::View} abstraction with a custom layout defined by the \lstinline{RAJA::OffsetLayout} class with a specific permutation of the dimensions. The view is a multidimensional array that can be accessed using the indices defined by $($\lstinline{IRange}$\times$\lstinline{JRange}$\times$\lstinline{KRange}$)$; $k$ is the majormost dimension, followed by $i$ and $j$ as the minor dimensions.
