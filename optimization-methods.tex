\chapter{Optimization methods}\label{chap:optimization-methods}

As discussed in~\cref{chap:background}, code optimization is crucial for achieving efficient program execution on modern high-performance platforms, such as clusters equipped with multi-core CPUs and GPUs.

In this chapter, we outline several prominent optimization methods and frameworks that have been developed to facilitate automated or user-guided code optimization in high-performance computing applications. We put particular emphasis on methods that are relevant to our work: data layout and traversal optimizations for parallel workloads.

The shared theme among the discussed optimization methods is enabling developers to use higher-level and hardware-agnostic designs without sacrificing performance on specific hardware platforms, often with further features such as separating different design choices (e.g., data layouts and traversal orders) from the core algorithmic logic, or allowing users to express desired optimizations separately from the algorithm definition.

For example, compiler optimizations allow users to write well-structured code separated into functions and expressed using high-level constructs such as loops and data structures. Then, the structured code is analyzed by the compiler and, following some heuristic rules (such as replacing repeated computations with temporary variables), transformed into lower-level code that is more efficient to execute. Compiler optimizations and similar methods are often bound by strict rules that preserve the semantics of the original code; thus, they are often important components of other optimization methods, either enabling them or being used in conjunction with them to verify the optimizations.

Other methods, such as abstractions, allow users to express the algorithm more concisely and to change specific design choices, such as the underlying data layouts of data structures, without modifying the logic of the algorithm. Such methods are often designed to allow users to direct optimizations via various directives or policies, improve the expressiveness and readability of the code, or enable techniques such as automatic tuning (autotuning), which searches for optimal parameters (e.g., tile sizes or loop orders) based on empirical performance measurements.

More advanced methods, such as LLM-based optimization, also allow users to express desired optimizations in natural language, providing even greater flexibility and ease of use~\cite{mahmud2023autoparllm,merouani2025agentic}. This area of optimization methods is comparatively recent and open, and it can complement more traditional methods because LLMs can learn and generalize complex patterns from data.


\section{Compiler optimizations}

Compiler optimizations are a fundamental aspect of modern compilers and code development as a whole. In high-performance computing in \cpp, which is the most prevalent language for such applications, compilers such as LLVM~\cite{lattner2004llvm} and GCC~\cite{gcc} implement a wide range of optimization techniques to improve the performance of source code, starting from basic optimizations that remove redundant computations, inline functions, or reorder instruction sequences. More advanced optimizations also include loop transformations (e.g., loop unrolling, loop fusion, invariant code motion), vectorization, and inter-procedural optimizations that analyze and optimize across function boundaries.

Compiler optimizations also allow developers to use higher-level abstractions (e.g., \cpp templates) and more structured code without significant performance penalties, as compilers can interpret these abstractions and optimize them effectively, particularly when using so-called zero-cost abstractions~\cite{stroustrup2012foundations}. This allows developers to write more expressive and manageable code while still achieving high performance.

However, compilers have limitations in their ability to optimize code --- they are often bound by the incomplete information available at compile time, so they have to operate under conservative assumptions about the program's behavior, follow heuristic rules, and apply transformations only when they preserve the observable behavior of the original code for any feasible execution path.
Examples of mitigating these limitations include profile-guided optimization (PGO), autotuning techniques~\cite{ansel2014opentuner}, user-directed optimizations, custom compilation pipelines~\cite{kruse2018user}, and cost models based on machine learning~\cite{baghdadi2021deep}.


\subsection{Polyhedral model}\label{sec:polyhedral-model}

A particularly powerful tool that can be part of a compilation pipeline is the polyhedral model~\cite{feautrier1992some}. The polyhedral model is a mathematical framework for representing and optimizing loop nests in programs. It is particularly effective for scientific computing applications, where performance-critical code often consists of nested loops operating on multidimensional arrays in a regular pattern.

The approach is based on representing the iteration spaces of loops, as well as data accesses and their dependencies, as polyhedra in a high-dimensional space. All relations are represented as affine functions (i.e., linear functions with a constant term) of iteration variables and any parameters constant during the runtime of the optimized code parts (e.g., sizes of arrays). The optimization process draws on concepts from linear algebra and integer linear programming to find transformed iteration spaces that optimize certain performance metrics (e.g., data locality and parallelism opportunities) while preserving the semantics of the original code.

The polyhedral model has been successfully applied across various compilers and frameworks, such as Polly~\cite{grosser2012polly} (a polyhedral optimization framework for LLVM), PluTo~\cite{bondhugula2008pluto} (a tool for automatic parallelization and locality optimization of loop nests), GRAPHITE~\cite{trifunovic2010graphite} (a polyhedral optimization framework for GCC), and many others.

Many works extend the basic polyhedral model to broaden its applicability or improve the optimization results by combining it with cost models, heuristics, or machine learning techniques (e.g., \citeauthor{baghdadi2021deep}~\cite{baghdadi2021deep}) to evaluate transformations proposed by the polyhedral model and find good parameters for these transformations (e.g., tile sizes). Other works show the benefits of combining polyhedral optimization based on cost models or heuristics with autotuning~\cite{chelini2020automatic} or human insights~\cite{zinenko2014clint,bagneres2016opening}.


\section{Abstractions for data layouts and traversals}\label{sec:abstractions}

Flexible abstractions allowing manipulation of data layouts and traversal orders have been the subject of extensive development~\cite{ragan2013halide,trott2022mdspan,trott2021kokkos,beckingsale2019raja}. They provide a means to change certain design choices (e.g., data layouts and traversal orders) or apply optimizations separately from specifying the core algorithmic logic.

We can broadly categorize these abstractions based on whether they stand completely separate from the source language (represented by \emph{domain-specific languages}), extend the source language with directives or transformation rules (\emph{annotation-based approaches}), or are implemented directly in the source language (\emph{native abstractions}).

% These three categories are not mutually exclusive --- for example, some native abstractions can be expressive enough to be used as DSLs, and many annotation-based approaches and DSLs overlap in how a user can express optimizations.


\subsection{Domain-specific languages (DSLs)}\label{sec:dsl}

DSLs are specialized programming languages designed for specific computing domains, such as deep learning, stencil computations, or image processing. By providing domain-specific constructs, they can offer more concise and readable syntax compared to general-purpose \cpp code, as well as a high level of expressiveness and optimization potential based on domain-specific knowledge. However, they require a separate compilation pipeline or runtime system to execute the code written in the DSL. They also require users to learn DSL-specific concepts, which may not translate well to other domains.

There are many DSLs with varying characteristics and design principles that have been developed for optimizing code in various domains of high-performance computing applications. A common theme among the prominent DSLs is the strict separation of the algorithmic logic from the optimization, together with guarantees or checks that the optimization steps do not change the semantics of the original code.

In many such DSLs~\cite{ragan2013halide,baghdadi2019tiramisu,chen2018tvm,zhang2018graphit}, these two aspects are separated into an \textit{algorithm} specification and a \textit{schedule}. The algorithm specification describes the computations to be performed in a high-level, declarative manner; while the schedule is a list of optimization directives that specify how the computations should be executed, which may include specifying traversal orders, caching strategies, and parallelization.

The main advantage of separating the algorithm definition from the optimization is that a single algorithm can be optimized in multiple ways for different target hardware architectures. Since the framework typically ensures that the optimizations do not change the semantics of the original code, users can also experiment with different optimization strategies without worrying about breaking the correctness of the computation. This allows such DSLs to serve as a basis for automatic optimization techniques that can search for the best optimization strategy by iteratively modifying the schedule and evaluating the performance of the resulting code~\cite{ragan2013halide,chen2018tvm,merouani2025agentic}.

Prominent examples of DSLs include Halide~\cite{ragan2013halide} (a DSL for image processing and stencil computations), TVM~\cite{chen2018tvm} (which adapts the scheduling-based approach to deep learning workloads), and Tiramisu~\cite{baghdadi2019tiramisu} (which targets a wider range of affine loop nests, covering general scientific computing applications).
% Halide and TVM are based on a more restricted version of the polyhedral model (called interval analysis), while Tiramisu is based on the full polyhedral model.

DSLs can also be designed to be user-extensible, allowing support for new optimizations and target hardware architectures. An example of this is the Exo~\cite{ikarashi2022exocompilation} DSL, which follows similar separation principles but is designed to allow users to specify new optimization transformations and hardware instructions by describing their semantics as Python functions.

% DSLs offer the highest level of flexibility and optimization potential and the prominent examples all also offer powerful verification capabilities for the optimization directives.


\subsection{Annotation-based approaches}\label{sec:annotation}

Annotation-based approaches allow users to express optimizations by adding optimization directives to the original code written in \cpp. These directives, such as pragmas, direct the compiler or optimization pipeline to perform specific transformations while relying mostly on constructs already familiar to \cpp users. Some such directives are supported even by major compilers (e.g., OpenMP pragmas for parallelization~\cite{openmp_6.0_spec} and unroll pragmas for loop unrolling).

In a typical annotation-based approach, users write optimization directives that refer to code elements (e.g., loops, statements, data structures) and specify their transformations. This offers a more flexible and less restrictive way to express optimizations compared to DSLs, at the cost of lower control over the structure of the optimized code. These transformations are often based on representations such as the polyhedral model~\cite{namjoshi2016loopy,chen2008chill,hartono2009annotation}, as these models provide powerful and verifiable frameworks for users to express optimizations.

CHiLL~\cite{chen2008chill} and similar tools use semantic directives, such as \lstinline{tile} or \lstinline{permute}, that directly express the intended transformation, whereas tools such as Loopy use more flexible mathematical syntax.
In Loopy~\cite{namjoshi2016loopy}, users can express loop transformations as affine mappings over iteration variables; for example, interchanging two loops in a loop nest with iteration variables \lstinline{i}, \lstinline{j}, and \lstinline{k} corresponds to mapping the iteration order from \lstinline{[i, j, k]} to \lstinline{[i, k, j]}.

While annotation-based approaches are prominent in the context of parallelization (especially OpenMP pragmas), they do not offer significant characteristics that would not be covered by DSLs.

% The design space for annotation-based approaches is more limited than for DSLs, annotation-based framework are often tightly integrated with the existing toolchains for the source language (such as OpenMP pragmas in \cpp), which allows users to easily integrate them into their existing codebases; and the annotated code is still interpretable by users and tools built for the source language.


\subsection{Native abstractions}\label{sec:native-abstractions}

Native abstractions are implemented directly in the source language and do not require any custom compilation pipelines. This allows full integration with existing \cpp toolchains, most notably compilers and debugging tools, and makes algorithms using native abstractions easier to compose with other \cpp constructs and libraries. They are most relevant to our work, as the majority of our contributions fall into this group.

While the design space for efficient native abstractions is more limited than for the above alternatives, well-designed native abstractions can still offer powerful optimization capabilities thanks to the metaprogramming capabilities of \cpp.

The native abstractions form three non-exclusive categories depending on what aspect of the design they abstract~--- \emph{layout-agnostic multidimensional arrays} that allow users to change the data layout without modifying the algorithmic logic; \emph{hierarchical views} that allow users to express more complex or transformed layouts by composing simpler building blocks; and abstractions for \emph{separating computational logic} from concrete data layouts and traversal orders, which allow users to express the core algorithmic logic in a way that is agnostic to the layout and traversal optimizations (working from the opposite direction of the previous two categories toward the same goal).

While these categories are not exhaustive, they cover the most prominent approaches that can be used to enable layout and traversal optimizations in a way that is decoupled from the core algorithmic logic. Most notably, we do not discuss approaches for specific data management strategies and other concerns that do not directly relate to data layouts and traversals.


\subsubsection{Layout-agnostic multidimensional arrays}\label{sec:layout-agnostic-multidim-arrays}

The most prominent abstraction for data layout and traversal optimizations is a multidimensional array view that abstracts the data layout. Implementation examples of this abstraction include the \texttt{mdspan} abstraction~\cite{trott2022mdspan} in standard \cpp, and Kokkos and RAJA Views~\cite{trott2021kokkos,beckingsale2019raja}. These abstractions separate the logical structure of the data (e.g., the number of dimensions and their sizes) from the physical layout in memory, enabling users to change the layout without modifying the array indexing in algorithms. Commonly, the physical layout is defined by an affine mapping from the multidimensional logical indices to the one-dimensional physical memory addresses, parameterized by the strides and sizes of the dimensions.

The strides and sizes can be encoded as compile-time constants to allow for more aggressive optimizations. Different implementations combine this principle with policies for memory management or other concerns of accessing the data (e.g., policies for special load and store instructions).

A crucial feature shared by most of the implementations is the ability to express sub-arrays by slicing the index space of the original array (restricting each index dimension to a specific range), which is useful for expressing traversal optimizations such as tiling. For example, an algorithm processing an $N \times N$ matrix of independent elements can be broken down into tiles of size $T \times T$ by slicing the original matrix into $\frac{N}{T} \times \frac{N}{T}$ sub-matrices that are then passed to the algorithm as independent arrays.

A notable example of multidimensional array abstractions is the CuTe layout system in the Cutlass library~\cite{thakkar2023cutlass}. CuTe differs from other implementations in that it defines a layout algebra based on interpreting the layouts as mathematical functions from linearized indices to element offsets. CuTe defines how indices of layouts are linearized into a single index and, thus, each layout may be used as a function mapping some integer intervals $f: \left[0, N\right) \to \left[0, M\right)$. These functions are composable as long as the domain of one and the range of the other are compatible, allowing users to express more complex layouts by combining simpler ones, or to express transformations of layouts. This composition principle will be further explored in the next section on hierarchical views.


\subsubsection{Hierarchical views}\label{sec:hierarchical-views}

Another powerful abstraction for data layout and traversal optimizations is the notion of hierarchically defined views, where a complex layout is built from simpler ones via hierarchical composition. A good and intuitive example of such an abstraction for traversals is the Ranges library~\cite{niebler2018one} in standard \cpp, which allows users to express various traversal transformations (e.g., tiling, reversing) on linear ranges, such as \lstinline/std::vector<int>{1, 2, 3, 4} | views::reverse | views::chunk(2)/, which creates a view of the original vector with reversed order and tiled into chunks of size 2, which can be used as a regular range of two-element sub-ranges (i.e., \lstinline/{{4, 3}, {2, 1}}/).

For data layouts, C and many other languages natively support hierarchical composition of types (e.g., arrays of arrays, record types containing arrays, etc.). However, these abstractions are not suitable for layout-agnostic programming, as the indexing logic is tightly coupled with the data structure definition.

MPI datatypes~\cite{mpi-5.0} stand out as a layout abstraction that shows characteristics of layout-agnosticism,
%  --- any two datatypes representing logically equivalent data layouts can be given to opposite communication endpoints. Even though datatype definitions are hierarchical, semantic equivalence of different layouts is based on the number and logical order of elements, not the particular hierarchical structure of the definition.
as they separate the logical structure from the physical layout. Any two datatypes representing logically equivalent data layouts\footnote{Logically equivalent MPI datatypes have the same number of base elements, such as integers or floating-point numbers, in the same logical order.} can be given to opposite endpoints of a communication primitive (e.g., a send-receive operation) regardless of their physical layout, which is defined by offsets of their base elements in memory.
% For example, \lstinline{MPI_Type_vector(N, __1, stride, type, &new_type)} can be used to define a row vector \lstinline{new_type} in row-major layout for a matrix ($M \times N$ of elements of \lstinline{type}) by using unit strides, while a row vector in column-major layout can be defined by using strides equal to the number of rows in the matrix ($M$), both constructions being logically equivalent and interchangeable in communication operations.

For example, we can define an MPI datatype that enumerates the first column of a matrix in row-major layout and another datatype that enumerates the corresponding (contiguous) column in column-major layout. A send-receive operation using these datatypes on opposite endpoints can communicate the same logical sequence of elements while reading from and writing to different physical layouts. If we perform this operation for each corresponding pair of columns, we can effectively convert between the row-major and column-major physical layouts using MPI communication. Thanks to the hierarchical composition of datatypes, we can extend each of the two datatypes to enumerate the whole matrix column by column in their respective layouts, and perform the conversion using a single communication operation.


\subsubsection{Separating computational logic}\label{sec:separating-computational-logic}

% The \cpp template system allows for powerful abstractions that can be used to separate the core algorithmic logic from other aspects of the design, including data layout and traversal.

\cpp has generic programming capabilities that allow defining algorithms in such a way that they are agnostic to the data layouts and traversal orders. A central language feature allowing for this principle without sacrificing performance is the template system, which allows for algorithms to be parameterized by types and values that are interpreted at compile time, enabling the compiler to optimize the code for specific arguments and, thus, allowing for zero-cost abstractions~\cite{stroustrup2012foundations}.

When using these abstractions, it is a common practice to define some design choices, such as traversal orders and parallelization strategies, using policies passed via the template parameters. For example, many standard \cpp algorithms separate algorithmic logic from concrete containers through iterators or ranges; some also accept execution policies that select the execution strategy.

Other, more advanced examples of this approach are stencil computations in the GridTools library~\cite{afanasyev2021gridtools} and kernel definitions in the RAJA library~\cite{beckingsale2019raja}. GridTools stencils are defined using abstract computation stages that are oblivious to the data layout and traversal, and RAJA kernels are nested templates representing loop nests that can be instantiated with different execution policies that define the traversal order and parallelization strategy.


\section{Data-driven optimization approaches}\label{sec:soft-computing-approaches}

% Recently, machine learning (ML) techniques, including large language models (LLMs), have been increasingly applied to various aspects of code optimization. The main motivation for using these techniques is their flexibility and ability to learn and generalize complex patterns from data, which can overcome limitations of traditional optimization methods that rely on hand-crafted heuristics or analytical models.

So far, we have discussed various formal methods for optimization and methods that allow users to direct optimizations or express algorithms in such a way that different design choices can be more easily optimized.

In this section, we discuss various data-driven approaches that can be used to optimize code based on empirical performance measurements or to generalize patterns from learned data (for predicting various performance characteristics or even generating optimized code).

We distinguish autotuning and LLM-directed approaches from general machine learning-based (ML-based) approaches and discuss them in more detail, as we have made contributions related to these two areas.


\subsection{Autotuning}\label{sec:autotuning}

Autotuning is a powerful technique for parameter optimization even outside the context of high-performance computing, but it is particularly relevant in this context. It searches a space of possible parameter configurations (the \emph{search space}) to optimize a given \emph{objective function} (e.g., code performance) by iteratively evaluating different configurations and using the results to guide the search for better configurations. The search space can include various parameters, such as tile sizes for tiling transformations, loop orderings, choices between different algorithms, and even compiler flags.

Simple autotuning techniques include random search and grid search, with grid search being practical for exhaustive exploration of small discrete search spaces. These methods are commonly used in black-box optimization settings where little structure is known about the objective function. If the objective function is not very complex and not too stochastic, local optimization methods (e.g., hill climbing or the Nelder--Mead method) may perform much better, as they can quickly converge to a local optimum.

For objective functions that are expensive to evaluate (as is often the case when evaluating algorithm performance), surrogate-based optimization methods (e.g., Bayesian optimization) are often used. These methods build an approximate (surrogate) model of the objective function based on previous evaluations and use this model to guide the search for optimal parameters.
% The more advanced autotuning techniques explore the search space based on the observed performance of the configurations, which can lead to much faster convergence to optimal parameters compared to simple techniques such as random search or grid search.
This can help avoid evaluating configurations that are likely to perform poorly, thus reducing the number of evaluations needed to find optimal parameters.

% Perhaps one of the most prominent applications of ML techniques in code optimization is autotuning. Autotuning techniques are powerful and versatile methods for (among many other uses) optimizing performance of applications based on empirical performance measurements or cost models. While methods such as linear programming can find optimal parameters for certain objective functions, situation is much more complex in more difficult-to-model optimization problems. Many autotuning techniques are specifically designed to address black-box optimization problems or functions that may be expensive to evaluate, non-continuous, and stochastic (among other characteristics making them unfit for analytical approach) --- performance of code is one such function.

In a scenario of optimizing data layouts and traversals, the search space may comprise categorical parameters (e.g., the order of loops in a loop nest, the choice of data layout) and numerical parameters (e.g., tile sizes). Categorical parameters typically do not follow any obvious ordering, while the ranges of numerical parameters can be very large, each benefiting from different exploration techniques.

Since the search space usually contains combinations of categorical and numerical parameters, and the performance function may follow complex patterns with stochastic behavior, many works combine different exploration techniques using various meta-strategies to achieve better results. One prominent example of this is the OpenTuner framework~\cite{ansel2014opentuner}, which was designed to tune compiler optimization flags but can be applied to a wide range of optimization problems.

Autotuning techniques are particularly effective in conjunction with other optimization methods, such as the polyhedral model, DSLs, and annotation-based approaches, when their compilation pipeline verifies that the optimizations do not change the semantics of the original code. This has been shown to be effective in the Halide autoscheduler~\cite{ragan2013halide,adams2019learning}.

\subsection{ML-based code optimization}\label{sec:ml-based-code-optimization}

There have been many different approaches to using ML techniques for code optimization, such as using genetic programming to evolve compiler heuristics~\cite{stephenson2003meta} or using various supervised learning techniques to predict the performance of code based on its features~\cite{ashouri2017micomp,adams2019learning,fursin2011milepost}, which can speed up iterative compilation pipelines (similar to autotuning, controlling optimization passes) by avoiding expensive performance evaluations for unpromising configurations.

Some works have proposed encoding program representations at various abstraction levels (machine instructions, intermediate representations, or abstract syntax trees) into vector embeddings and using deep learning methods to predict performance-related properties or optimization choices~\cite{venkatakeerthy2020ir2vec,mou2016convolutional,ben2018neural}.

Deep learning methods have also been used to build cost models that can guide exploration of the search space for autotuning or scheduling transformations based on analyzing the structure of the code~\cite{baghdadi2021deep,adams2019learning}. Similarly, ML-based cost models have been used to improve the performance of polyhedral optimization techniques~\cite{park2013predictive}.

The area of ML-based code optimization is quite broad, so the rest of this section focuses on the use of LLMs for code optimization, a more recent area with many open questions and the subject of some of our contributions.


\subsection{LLM-directed optimization}\label{sec:llm-directed-optimization}

Recently, LLMs have emerged as promising tools for both directing code optimization and generating optimized code. The main motivation for using LLMs for these tasks is their ability to learn and generalize complex patterns from large codebases without requiring explicit feature engineering, as well as their ability to understand and generate natural language, which enables more intuitive specification of the optimization goals and any constraints. Their capabilities can complement more traditional optimization methods that rely on hand-crafted heuristics, analytical models, or pre-built building blocks for transformations.


\subsubsection{Generating optimization directives}\label{sec:llm-generating-directives}

Various works have explored the use of
% off-the-shelf LLMs or fine-tuned (or even trained from scratch)
LLMs for generating directives used to optimize code, such as OpenMP directives for parallelization~\cite{nichols2024hpc} and scheduling directives for frameworks such as Halide or Tiramisu~\cite{merouani2025agentic}.

% Just like autotuning techniques, earlier approaches to LLM-directed optimization used the LLMs to generate optimization directives that might be applied via the framework and easily verified.
Using LLMs to generate optimization directives for a framework (such as those discussed in~\cref{sec:dsl,sec:annotation}) has the added benefit that the framework can validate the applicability or correctness of many proposed optimizations. Thus, even if the LLM is not reliable enough to generate optimized code directly, it can use its learned patterns to propose optimizations, similar to autotuning techniques enhanced with surrogate cost models.

For example, HPC-Coder~\cite{nichols2024hpc} shows that fine-tuning LLMs on HPC code can enable them to generate expected OpenMP directives for parallelization with high accuracy, as well as generate parallel code snippets for MPI-based distributed parallelization. ComPilot~\cite{merouani2025agentic} uses an LLM agent as a search driver when exploring the search space of transformation directives, effectively performing LLM-accelerated autotuning.


\subsubsection{LLM code generation and transformation}\label{sec:llm-code-generation}

Direct code generation goes further, allowing the model to make more fundamental changes to the code. This has only recently become more viable, as the proficiency of LLMs in code generation has improved. Since LLMs are generally trained on large codebases, and only a relatively small part of generally available code falls into the HPC domain, the performance of off-the-shelf LLMs on HPC code has become a serious research target comparatively recently, following general code-generation milestones such as Codex~\cite{chen2021evaluating} and more recent evaluations of parallel and GPU code generation~\cite{nichols2024can,godoy2024large}.

Fully unsupervised generation of reliably optimized HPC code remains difficult, so several works use LLMs for translation between a more interpretable language and a programming model such as CUDA~\cite{palkowski2024gpt,dearing2024lassi}. One of these works, LASSI, defines a self-correcting pipeline where the LLM proposes a solution and can then respond to feedback from the compiler or verifier.

\section{Summary}\label{sec:methods-summary}

We have outlined various methods for optimizing code relevant to our work. Techniques such as compiler optimizations are necessary assumptions for our work on native abstractions for data layouts and traversals (\cref{chap:abstractions}), and autotuning techniques then allow automated decision-making on the best design choices for a given target architecture.

In our more recent contributions, we explore the use of LLMs for code optimization (\cref{chap:llms}). In one of the contributions, we evaluate whether various abstractions (Halide, Exo from \cref{sec:dsl}, and our own native abstractions) can benefit LLMs in generating optimized code.
