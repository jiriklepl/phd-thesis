\chapter{LLM-directed code optimization}\label{chap:llm-directed-code-optimization}

Recent advances in large language models (LLMs) have demonstrated their growing potential for code generation and optimization~\cite{chen2021evaluating}. While initial efforts focused primarily on general-purpose coding, several works have since explored the application of LLMs specifically in the context of high-performance computing (HPC), including automatic parallelization~\cite{mahmud2023autoparllm,nichols2024can}, GPU kernel generation~\cite{ouyang2025kernelbench,palkowski2024gpt}, translation between parallel programming models~\cite{dearing2024lassi}, and guiding loop optimization and scheduling decisions~\cite{merouani2025agentic}. Nevertheless, the ability of LLMs to produce code whose performance matches that of expert-written implementations for challenging HPC optimization tasks currently remains an open question.

In our work, we have explored three main questions regarding LLM-directed code optimization in HPC\@:

\begin{itemize}
  \item When implementing the optimized code, does guidance (tutoring) significantly improve the quality (correctness and performance) of the generated code even if the LLM is specifically tasked to provide as efficient code as possible for the target CUDA hardware?~\cite{brabec2025tutoring}
  \item Does combining LLM-directed optimization with traditional code abstractions (e.g., DSLs and libraries) lead to better results than either approach alone?~\cite{klepl2026shifting}
  \item Can LLMs reliably apply optimization techniques in C or \cpp code that are not easily accessible in existing DSLs and frameworks?~\cite{klepl2026shifting}
\end{itemize}


\section{Tutoring approach}\label{sec:tutoring-approach}

In our initial investigation of LLM-directed code generation and optimization for HPC applications~\cite{brabec2025tutoring}, we studied whether contemporary LLMs can generate efficient CUDA code for a sample of kernels representing typical computations in HPC applications and whether providing tutoring (guidance) to the LLM can significantly improve the quality of the generated code. We included three computational kernels presenting different optimization challenges in developing GPU-accelerated applications: \emph{histogram computation}, the \emph{Game of Life} simulation, and a brute-force $k$-Nearest Neighbors search (\emph{$k$NN search}) in the 2D space with the Euclidean distance metric.

For histogram computation, the expected optimization techniques included per-block privatization of the intermediate result in multiple copies in shared memory, avoidance of bank conflicts, and reduction of the privatized histograms into the final global histogram. For the Game of Life simulation, the expected optimization techniques included bit-packing of the grid and utilizing bitwise operations to compute multiple cells in parallel. For the $k$NN search, the expected optimization techniques included buffering the input data in shared memory after filtering out the points that are too far from the query point, and using bitonic sort to efficiently update the intermediate results of the $k$NN search.

The three kernels differ in complexity of their expected implementations, with the histogram computation being the simplest and the $k$NN search being the most complex.
At the time of our experiments, we found that the currently best-performing LLM (o3-mini~\cite{openai2025o3mini}) was able to generate code that was functionally correct for the histogram computation and Game of Life simulation and it was able to generate more efficient code with more detailed instructions --- matching the expected optimization level with the most detailed instructions. However, for the $k$NN search, the LLM was not able to generate functionally correct code regardless of the level of instructions provided.

For each set of instructions, we prepared a reference implementation of the kernel that matched the expected optimization level for the given instructions and mirrored the hints captured in the instructions. We considered the LLM successful if the generated code was functionally correct and its performance was at least as good as the reference implementation for the given instructions.


\subsection{GPT-5 replication}\label{sec:gpt5-replication}

The performance of LLMs is rapidly improving, and so, prior to the presentation of our work on the European Conference on Parallel Processing (Euro-Par) 2025, we have replicated the experiments with the newer GPT-5 LLM\footnote{\url{https://github.com/matyas-brabec/2025-europar-llm/tree/GPT-5-high}}. We have presented the results of this replication alongside the peer-reviewed paper at the conference.

We found that GPT-5 was able to generate functionally correct code for all three kernels, including the $k$NN search (however, at a success rate of around $30\%$ across all levels of instructions; while the success rate for the other two kernels reached almost $100\%$). This suggests a significant improvement in the code generation capabilities of LLMs during the review process of our paper, which is a common occurrence in the rapidly evolving field of LLMs\@

Performance-wise, the more recent LLM generated better code than the older LLM on the histogram computation and Game of Life simulation. For both tasks, the performance of the generated code was almost independent of the detail level of instructions provided to the LLM past the prompt that clearly stated the optimization goal (and slightly negatively correlated for the histogram computation), suggesting that the level of detail of instructions provided to the LLM does not significantly affect the quality of the generated code for problems that are below some complexity threshold, which is dependent on the LLM\@.

In contrast, for the $k$NN search kernel, the performance of the generated code was clearly positively correlated with the level of instructions provided to the LLM\@, reaching the expected optimization level for the most detailed instructions.


\section{Combining with abstractions}\label{sec:combining-with-abstractions}

In our subsequent work~\cite{klepl2026shifting}, we investigated whether combining LLM-directed optimization with traditional code abstractions (DSLs and frameworks) can lead to better results than LLM-directed optimization done without such abstractions --- as such abstractions are designed to make it easier for human developers (and domain experts) to apply certain optimization techniques and improve performance portability across different hardware (as discussed in~\cref{sec:abstractions}). We performed a case study using the GPT-5.1 LLM\footnote{\url{https://openai.com/index/introducing-gpt-5/}} as a representative of the state-of-the-art LLMs at the time of our experiments. The experiments were performed on the PolyBench/C benchmark suite~\cite{pouchet2012polybench}, which consists of 30 computational kernels representing a variety of optimization challenges in HPC\@. The same benchmark suite was used in many previous works on code optimization~\cite{ansel2014opentuner}, including those using LLMs~\cite{nichols2024performance,merouani2025agentic}.

We compared approaches differing in two dimensions: (1) whether the LLM was tasked to optimize the given code without any specific abstractions (i.e., the LLM had to apply all optimization techniques on its own), or whether the LLM was tasked to optimize the code using a specific abstraction (we used the Halide DSL~\cite{ragan2013halide}, Exo DSL~\cite{ikarashi2022exocompilation}, and the Noarr library described in~\cref{chap:noarr}); and (2) whether the LLM was provided with more detailed optimization hints, kernel-specific optimization instructions generated in a separate request, or just a general optimization goal. In all generation approaches, the LLM was prompted five separate times for each kernel, DSL or library, and the given instruction approach; this also applies to the translation tasks from C to the DSLs\@. To ensure a fair comparison and maximize the objectivity of the results, the baseline implementations of the kernels for each DSL or library were selected from the five generated implementations based on their correctness and, out of the equally correct implementations, the one with the performance closest to the C reference implementation was selected (measured across SMALL, MEDIUM, and LARGE input sizes).

The results of our experiments showed that the LLM was able to generate functionally correct and performant code more reliably in C than with the abstractions involved. This was observed across all instruction approaches with the exception of the na\"{\i}ve approach that describes only the target system and the optimization goal (for this specific case, the Exo translations performed generally well). More performant approaches outlined the expected optimization techniques in more detail (loop transformations, data layout transformations, parallelization, etc.), while not providing kernel-specific hints, which resulted in substantially better performance across all frameworks, and globally the best performance was achieved by generating optimized C code without any of the studied abstractions.

Surprisingly, the modified pipeline where multiple kernel-specific optimization plans were generated prior to the final code generation did not lead to better results compared to the approaches with detailed, but non-kernel-specific optimization hints; and only for the C code generation did it significantly outperform the na\"{\i}ve approach.

We have concluded that the prompt specificity plays a significant role in the quality and the reliability of the generated code, and that the state-of-the-art abstractions for human-directed optimization in HPC hinder the LLMs from generating correct and performant code. This suggests that LLMs may require specifically designed abstractions that would cater to their specific capabilities and limitations. Our and a previous work~\cite{merouani2025agentic} also observed that the DSLs and libraries (or simplified
directives requested of the LLMs) often lack expressiveness necessary for the computation transformations necessary to significantly improve the performance. This results from that the DSLs and the frameworks are generally designed to prevent frequent human errors or to simplify autotuning approaches (e.g., by performing formal verification of the attempted transformations).
