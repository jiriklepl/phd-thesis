\section{Cellato Library}\label{chap:cellato}

The Cellato library applies the layout-agnostic design principles of Noarr to the domain of cellular automata --- discrete iterative computations on structured grids, where each cell's state is updated based on the states of its neighbors. In this domain, high-performance implementations often employ highly specialized encodings and data representations that are tightly coupled with the computation logic, making it difficult to experiment with different optimization strategies. Cellato addresses this by providing abstractions that separate the automaton's update rules from the underlying data layout, traversal strategy, and per-cell evaluation method.

In our ongoing research in the area of cellular automata, we have observed that many well-optimized implementations share common design patterns such as bit-packing of cell states, temporal blocking of updates, and bit-level SIMD-style parallelism of cell update computations. Inspired by these observations and layout-agnostic paradigms explored in the Noarr library, we have developed the Cellato library~\cite{brabec2025cellato}, which enables the separation of concerns between the high-level definition of cellular automata and low-level details such as data layouts, parallelization strategies, and computation optimizations.

\subsection{Cellato traversers and evaluators}\label{sec:cellato-evaluators}

% Cellato overview
The Cellato framework is built around the following core abstractions with their relationships depicted in \cref{fig:runtime-arch}:
\begin{description}
  \item[Algorithm:]\label{des:algorithm} an abstract definition of the cellular automaton update rules pertaining to a single cell, depending on its neighborhood.
  \item[Layout:]\label{des:layout} a grid data structure managing the storage of cell states.
  \item[Evaluator:]\label{des:evaluator} a visitor-style abstraction that applies the algorithm to a single cell, given access to its neighborhood via the layout interface.
  \item[Traverser:]\label{des:traverser} a wrapper around the layout that applies the given evaluator to each cell in the grid. This defines the intended evaluation order of the cells, which may improve data locality.
\end{description}

As depicted in the figure, the evaluator and layout abstractions are tightly coupled --- for example, a bit-level encoding has to be paired with an evaluator that defines bit-vector computations.

Traversers define the high-level execution strategy, such as parallelization and temporal blocking, while evaluators encapsulate the low-level cell update logic (for example, interpreting summations of neighboring cells in the algorithm as networks of bitwise operations).

The framework leverages \cpp template meta-programming by encoding the algorithm as a static type consisting of nested nodes representing operations, data accesses, and constants. The evaluator comprises a set of specializations for each node type that, given access to the layout, evaluates to the result of the operation. All these components are further described in detail in our publication~\cite{brabec2025cellato}.

The design consisting of primitive composable building blocks follows the same general principles as the Noarr library, specialized to the domain of discrete iterative stencil computations. We have shown that Cellato can achieve performance comparable to hand-written implementations with less effort. \subsection{Bit-level optimizations}\label{sec:cellato-bit-optimizations}

One of the key results of our research with Cellato is the ability to encode cell states in a compact bit-packed format, allowing for significant memory bandwidth savings as well as enabling bit-level SIMD-style parallelism, speeding up the computations of the update rules. Without need to implement such encodings and computation optimizations directly in the automaton logic, a developer can select a predefined bit-packed layout and an appropriate evaluator, which performs better than byte-level SIMD for automata with a small number of states per cell and simple update rules (on contemporary CPU and GPU architectures).

Since the cell states or the intermediate results of the update computations (such as neighborhood sums) often occupy more than one bit, Cellato provides abstractions for bit-level operations on two representations out-of-the-box. The first is the AoS layout (called \emph{bit arrays} in Cellato terminology), where each cell's bits are stored contiguously and a given machine word encodes multiple consecutive cell states. The second is the SoA layout (called \emph{bit planes} in Cellato terminology)\footnote{AoS and SoA layouts are described in \cref{sec:memory-layout-optimizations}.}, where each bit plane contains bits of the same significance for $w$ cells, where $w$ is a machine word. These two representations are illustrated in \cref{fig:enc-packed} and \cref{fig:enc-linear}, respectively. \Cref{fig:enc-byte} shows a more na\"{\i}ve approach for contrast, each cell is stored in a separate machine word (or any word down to a single byte, the least addressable unit). This encoding is wasteful in terms of memory and bandwidth usage (having $w - k$ unused bits for the stored $k$-bit value), but it also allows for more straightforward implementations of the update rules.

Both representations can store up to $n$ $k$-bit cells in $n k / w$ machine words, where $w$ is the machine word size in bits (typically $32$ or $64$). Each layout comes with its own trade-offs.

The \textbf{bit-array layout} (AoS) is more intuitive to work with compared to the bit planes layout (SoA) and allows operations such as addition and multiplication just like the na\"{\i}ve encoding, provided that the result fits within the available number of bits per cell. However, it can be quite inefficient for storing values that are not powers of two, as each word then contains only $\lfloor w / k \rfloor$ cells with $k$ bits each and has $w \bmod k$ padding bits that are wasted, as shown in \cref{fig:enc-packed}. Compared to the byte-level encoding, computations loading the states of neighboring cells require more complex bit manipulation (shifts and masks) to extract the relevant bits, which can lead to more complex implementations of the update rules. Also note that when SIMD instructions are used, some inner padding may be required so no cell's bits are split across multiple vector-packed words --- if a state or intermediate result occupies more than one vector-packed word, the results of any arithmetic operations can be corrupted as the words do not pass carry information and the border-crossing results are not well-defined.

In contrast, the \textbf{bit-plane layout} (SoA) can store arbitrary bit-width values without any padding, as each plane contains one bit of each cell and the total number of planes corresponds to the number of bits per cell. This makes the encoding more compact in the general case, and it also increases the flexibility of the update rule implementations, as each intermediate result can be represented with as many bits as needed independently. However, hardware-supported operations are limited to bitwise logical operations (AND, OR, XOR, NOT) and bit shifts --- since consecutive bits in a word encode states or intermediate results corresponding to different cells, operations such as addition are not generally useful as any carries would overflow to surrounding cells' contexts. Bitwise operations by themselves can efficiently implement equality checks, but comparisons and arithmetic operations require more complex implementations, potentially increasing the computational complexity of this approach. For example, a summation of $n$ $k$-bit cell states can be efficiently implemented as a binary tree of $n-1$ adders with $\lceil \log_2 n \rceil$ depth, producing results with $1$ more bit than the input states at each new level of the tree, eventually producing a $k + \lceil \log_2 n \rceil$-bit result. Each adder can be implemented as a network of full-adder components, where each full-adder can be implemented with $5$ bitwise operations.

The idea of the bit-plane representation also enables different \textbf{tile-major bit-plane encodings}, as depicted in \cref{fig:enc-tiled}, where each tile contains a small rectangular block of cells instead of one long line. Similarly to the standard bit-plane layout, the set of cells in each tile is encoded in a contiguous set of words. This, more complex encoding has implications for the computation complexity of the update rules, especially if temporal blocking is utilized. Cellato supports various tile sizes $t_x \times t_y = w$, where $w$ is the machine word size in bits, allowing for flexible trade-offs between memory access patterns and implementation complexity.

For all the four encodings in \cref{fig:encodings}, Cellato provides the necessary abstractions to implement the update rules without coupling them to the specific encoding, allowing for rapid experimentation with different optimization strategies. Since these choices can be expressed by selecting different objects or numerical values in their template parameters and the core automaton logic is agnostic to these choices, the experimentation process can use the tuning framework described in \cref{sec:noarr-autotuning}. Which encoding performs best depends on the rules of the specific cellular automaton, the hardware architecture, and the traversal strategy --- for example, the bit-plane layout can be more efficient for automata with simple update rules, while the bit-array layout can be more efficient for automata with more complex update rules if the states fit well within the available bits per cell. The (more complex) tiled bit-plane layout, to be efficient, could require many time steps to be evaluated together, as the halo regions are up to $\min(t_x, t_y)\times$ smaller than in the non-tiled case, making their data reuse more effective.

\xxx{(UNPUBLISHED)} In our ongoing research, we explore the performance effects of using these layouts and different traversal strategies and evaluators on cellular automata from various domains, such as Conway's Game of Life, WireWorld, or lattice gas cellular automata. Compared to other state-of-the-art frameworks for cellular automata~\cite{cagigas2022efficient}, Cellato demonstrates competitive performance while providing a high level of abstraction and flexibility. Compared to hand-optimized solutions that use bit-level computations and bit-packed encodings~\cite{fujita2016fast}, Cellato achieves similar performance with significantly less development effort.


\subsection{Summary}\label{sec:cellato-summary}

Cellato demonstrates that the layout-agnostic and traversal-agnostic design principles explored in the Noarr library can be effectively specialized to the domain of cellular automata. By separating the automaton's update rules from the data layout, traversal strategy, and per-cell evaluation method, Cellato enables rapid experimentation with different optimization strategies --- including bit-packed encodings and various tiling schemes --- without modifying the core automaton logic. This separation of concerns reduces development effort while achieving performance competitive with hand-optimized implementations.
