\chapter{Hardware background}\label{chap:background}

To better understand the motivation behind layout and traversal optimizations, which collectively change the memory access patterns in a program, we first outline the hardware features of modern high-performance systems that are most relevant to our focus on these optimizations.

We target the two main general-purpose hardware platforms used in high-performance computing: multi-core CPUs and GPU accelerators.
CPUs are primarily designed for latency-sensitive task processing, executing a small number of hardware threads per core, while GPUs are optimized for massively data-parallel workloads that run thousands of threads concurrently in SIMT (Single Instruction, Multiple Threads) fashion~\cite{hennessy2019computer,cuda_programming_guide}. A single thread of execution runs a sequence of instructions using a set of registers and other resources (such as caches or arithmetic units).

In typical HPC systems, GPUs are separate accelerator devices attached to the host system, with their own memory and task scheduling. Thus, a computation running on a GPU typically requires transferring input data from system memory to the GPU device memory, and then transferring the results back to system memory after the computation is done. The data-parallel task is typically expressed as a \emph{kernel} function, which represents the computation that would be performed in each iteration of an equivalent massively parallelized loop. Upon \emph{kernel launch} (a modified function call), the kernel function is scheduled to run on the GPU in many threads, independently of the host system. CPU workloads, on the other hand, typically run directly on the host system using the system memory without requiring such transfers, unless the computation is distributed across multiple machines.

% The main difference between code execution on the two platforms is that a CPU core runs one or a few hardware threads at a time, while a GPU streaming multiprocessor runs many lightweight threads concurrently and issues instructions to them in groups. The distinction between them, however, is not strict, as modern CPU cores also support data parallelism through specialized \emph{vector} units that can, in a single instruction, operate on multiple data elements (SIMD) at the same time.

The differences between the two platforms present different challenges and opportunities for optimizing algorithm performance, which we will discuss in more detail in the following sections.


\section{CPU considerations}\label{sec:cpu-considerations}

A simple example that we can use to illustrate the impact of data layouts and traversal orders on CPU performance is the matrix multiplication algorithm. It computes each element of the output matrix ($C$) as a dot product of a row from the first input matrix ($A$) and a column from the second input matrix ($B$), where all matrices are stored in the standard row-major order (row by row). The algorithm can be implemented in \cpp as follows:

\begin{lstlisting}[language=C++, caption={Matrix multiplication}, label={lst:matrix-multiplication}]
float C[M][N]; // M rows, N columns
float A[M][K]; // M rows, K columns
float B[K][N]; // K rows, N columns

// iterating over output matrix C
for (int i = 0; i < M; ++i) {
    for (int j = 0; j < N; ++j) {
        // single dot product
        C[i][j] = 0;

        for (int k = 0; k < K; ++k) {
            C[i][j] += A[i][k] * B[k][j];
        }
    }
}
\end{lstlisting}

When optimizing an algorithm, such as the matrix multiplication example in \cref{lst:matrix-multiplication}, for execution on a CPU, we primarily need to consider caching. Caches are fast memory units that transparently store copies of system-stored data that is likely to be accessed in the near future, under the principle of locality. The principle states that programs tend to access data repeatedly in a short period of time (temporal locality) and access data stored in nearby memory locations (spatial locality)~\cite{hennessy2019computer}.

Many algorithms either naturally exhibit good locality (e.g., traversing a row-major matrix by rows) or can be transformed to have better locality (e.g., by reordering computations in such a way that repeated accesses to the same data are closer together).
% This principle, thus, directly motivates layout and traversal optimizations.

The current implementation of the matrix multiplication algorithm could be made more cache-friendly in two simple ways. First, we can notice that the innermost loop accesses the elements of the input matrix $B$ with a large stride (as it accesses the elements of $B$ column by column, while they are stored in row-major order). If we store the input matrix $B$ in column-major order (column by column), the innermost loop then accesses contiguous memory locations in both input matrices, improving spatial locality and thus performance.

The second way to improve caching is to improve the temporal locality of the algorithm by partitioning the computation into smaller chunks that can fit in the cache. In the current implementation (regardless of the layout of $B$), the innermost loop accesses new elements of the input matrices $A$ and $B$ after each iteration of the outer loops. For an input of sufficient size, this access pattern leads to repeated cache misses, as new data must be fetched from memory into the cache. If we partition the matrices into tiles (sub-matrices) that can fit in the cache, then updating the corresponding elements of the output matrix by computing the dot products of the corresponding rows and columns of the tiles allows for efficient reuse of the data in the input matrices. The reuse scales with the tile dimensions, as long as the tiles fit in the cache.

In practice, this transformation can be expressed as splitting the iteration ranges of the corresponding loops into smaller blocks, iterating over the blocks in the outer loops, and iterating over the elements of blocks in the inner loops, as shown in \cref{lst:matrix-multiplication-tiled}.

\begin{lstlisting}[language=C++, caption={Tiled matrix multiplication}, label={lst:matrix-multiplication-tiled}]

for (int ii = 0; ii < M; ii += i_block) {
  for (int jj = 0; jj < N; jj += j_block) {
    for (int kk = 0; kk < K; kk += k_block) {
      // inner loops (iterating over elements of tiles)
      for (int i = ii; i < min(ii + i_block, M); ++i) {
        for (int j = jj; j < min(jj + j_block, N); ++j) {
          for (int k = kk; k < min(kk + k_block, K); ++k) {

In addition to caching, we need to consider the parallelization and vectorization capabilities of the CPU\@. Modern CPU cores have specialized SIMD vector units that can, in a single instruction, operate on multiple data elements. Efficient use of these vector units can lead to a multiplicative improvement in performance, depending on the width of the vector units (e.g., $256$-bit vector units can operate on $8$ single-precision floating-point numbers at the same time). By changing the data layout of $B$ to column-major order (as with improving spatial locality), the innermost loop accesses data of both input matrices sequentially, allowing us to unroll the loop by the width of the vector units (relative to the data type) and replace the unrolled iterations with vectorized instructions that compute multiple terms of the dot product at the same time.

Finally, to parallelize the algorithm and make use of multiple CPU cores, we can use an approach similar to the tiling transformation we used to improve temporal locality. If we partition the output matrix into tiles (corresponding to blocking loops that iterate over the output matrix dimensions), we can use multiple execution threads to compute different tiles of the output matrix in parallel.
% To minimize the overhead of parallelization, the tiles should be large enough so that the corresponding computation is sufficiently large to amortize the overhead of work scheduling, but also small enough so that the number of tiles can saturate all available CPU cores with work.
Such tiles should have a size that balances the overhead of parallelization with the need to saturate all available CPU cores with work.


\section{GPU considerations}\label{sec:gpu-considerations}

GPU accelerators are among the most widely used hardware platforms in high-performance computing~\cite{top500}. Since NVIDIA GPU architectures represent a large share of accelerator-equipped TOP500 systems~\cite{top500}, we will default to their nomenclature when describing relevant hardware features and use them as a reference point.

As described in the introductory section of this chapter, executing an algorithm on a GPU involves scheduling a \emph{kernel} function. The kernel function is specifically designed to run on the GPU device in many threads and process data stored in the GPU device memory (usually referred to as \emph{global memory}). During a kernel launch, each new execution thread receives its own thread indices, which are used to determine which portion of the data it should process. The threads are organized into \emph{thread blocks}, and thus a global thread index is typically expressed as a combination of the block index and the thread index within the block. The number of thread blocks and the block size are specified by the programmer when launching the kernel --- this grid typically replaces one or multiple parallelized loops in the traversal of the sequential version of the algorithm.

The organization of threads into blocks is meaningful because each block is automatically scheduled on an available \emph{streaming multiprocessor} (SM) of the GPU\@. Thus, to fully utilize the GPU, the number of thread blocks should be large enough to saturate all available SMs with work.

Since all threads in the same thread block run on the same SM, they can also use a user-managed cache called \emph{shared memory} --- it can be used to store data that is reused by multiple threads in the same block, or even to communicate data between them. As the threads in the same block run on the same SM, synchronization between them has very low overhead; thus, many efficient algorithms make use of shared memory and other block-wide synchronization primitives during the computation.

When a thread block is executed on an SM, the threads are executed in groups of 32 in lockstep, meaning that they execute the same instructions concurrently (different threads are generally executed in unspecified order). If threads in the same group diverge into different control-flow paths, those paths may have to be executed separately, so data-dependent branching should be avoided.

Efficient execution also relies on the global memory accesses of the concurrently executing threads on an SM being organized in regular patterns with minimal stride (ideally so that the same memory access instruction executed by the threads leads to consecutive addresses) so that they are \emph{coalesced} into as few memory transactions as possible\footnote{Each global memory transaction reads or writes an aligned memory segment of multiple consecutive machine words. For example, 32 threads can access consecutive \lstinline{int} values in a single 128-byte transaction, but random access can lead to $32$ independent transactions.}, thus significantly reducing memory access latency. This is an especially important factor in memory-bound algorithms. The choice of data layouts and traversal orders that lead to coalesced memory accesses is thus often crucial for ensuring good performance on GPUs.

Since the GPU has its own global memory with limited capacity, some algorithms may require repeated kernel launches on different data batches that can fit in the GPU memory. In such cases, it is important to organize the data and scale the batch size in such a way that the transfer latency of each batch can be hidden by overlapping it with the computation of the previously transferred batch, as the hardware can often perform both operations concurrently.

Returning to the matrix multiplication example in \cref{lst:matrix-multiplication}, we can parallelize the computation of the output matrix $C$ by launching a separate thread for each element of the output matrix. In this case, we can use the tiling transformation described in the previous section. We organize the threads into 2D thread blocks (e.g., $32 \times 32$ threads per block), replacing the four loops in \cref{lst:matrix-multiplication-tiled} iterating over dimensions $M$ and $N$ with a kernel launch and leaving the loops iterating over the $K$ dimension within the kernel. Then, we can both ensure efficient use of shared memory and coalesced memory accesses by cooperatively loading consecutive tiles of the input matrices into shared memory while computing the corresponding tile of the output matrix from the loaded tiles. These two steps may be interleaved using a double-buffering technique, where one tile is loaded into shared memory while the previously loaded tile is used for computation.

In this chapter, we have outlined the main considerations for optimizing algorithms for execution on modern high-performance CPU-based and GPU-based systems. Many of these considerations are directly related to the organization of data or the order of computations, which motivates layout and traversal optimizations. It is important to note that the list of presented hardware features is not exhaustive, and both CPU and GPU architectures have additional features that further complicate the performance of algorithms and their behavior with respect to layout and traversal optimizations.
