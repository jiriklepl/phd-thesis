As discussed in \cref{chap:code-optimization}, code optimization is crucial for achieving efficient execution of programs on modern hardware architectures such as multi-core CPUs and GPUs. In this chapter, we outline several prominent optimization methods and frameworks that have been developed to facilitate (automated) code optimization in high-performance computing applications, putting particular emphasis on those that are relevant to our work targeting data layout and traversal optimizations.

Code optimization methods can target different points in the compilation and execution pipeline --- some methods operate above the source code level, providing high-level abstractions or domain-specific languages (DSLs) that allow developers to express computations in a way that is amenable to more powerful optimizations. Other methods perform optimizations at the source code level, possibly using annotations or pragmas to guide the optimization process. More low-level methods operate on intermediate representations (IRs) or directly on the generated machine code, applying transformations to improve performance based on static analysis or empirical measurements. Some methods may also involve runtime systems that adaptively optimize code during execution based on observed performance characteristics; in such cases, methods like just-in-time (JIT) compilation techniques may be employed to generate optimized code on-the-fly based on the current execution patterns.

We primarily focus on abstractions and frameworks that operate above or at the source code level, as these are most relevant to our work. However, we also briefly discuss the wider landscape of optimization methods to provide context for our contributions.


\section{Compiler optimizations}\label{sec:compiler-optimizations}

Compiler optimizations are a fundamental aspect of modern compilers. In high-performance computing, compilers such as LLVM~\cite{lattner2004llvm} and GCC~\cite{gcc} implement a wide range of optimization techniques to improve the performance of source code, starting from basic optimizations that remove abstractions and redundant computations, inline functions, perform sub-expression elimination, etc. More advanced optimizations include loop transformations (e.g., loop unrolling, loop fusion, invariant code motion), vectorization, and inter-procedural optimizations that analyze and optimize across function boundaries.

In the context of typical high-performance (scientific computing) applications with quite simple control flow and heavy numerical computations, these optimizations mainly allow using higher-level abstractions (e.g., \cpp templates, mdspan, \ldots) without significant performance penalties (most notably, when using so-called zero-cost abstractions~\cite{stroustrup2012foundations}). They can also optimize arithmetic expressions, eliminate redundant computations, and perform some basic loop transformations. However, these optimizations by themselves are often insufficient to achieve optimal performance on modern hardware architectures, especially for complex loop nests and data access patterns.

Some compilers and frameworks, such as MLIR~\cite{lattner2021mlir}, provide extensible intermediate representations that allow for custom representation and optimization passes to be implemented --- some of them targeting specific domains or hardware architectures. This is particularly useful for domain-specific languages (DSLs) that can leverage MLIR to implement their own optimization pipelines, including polyhedral optimizations, autotuning, and other transformations that are not typically part of general-purpose compilers. While it is built on top of traditional SSA-based IRs, it allows for defining custom dialects, and facilitates all boilerplate such as parsing, code generation, and so on.


\subsection{Polyhedral optimization}\label{sec:polyhedral-optimization}

Workloads comprising nested loops with affine bounds and affine memory accesses (Static Control Parts, or SCoPs) are common in high-performance computing applications (see, e.g., \citeauthor{bacon1994compiler}~\cite{bacon1994compiler}). To target such applications, \citeauthor{feautrier1992some}~\cite{feautrier1992some} and others pioneered the use of the polyhedral model to represent and optimize computations in loop nests. Polyhedral optimization frameworks, such as Polly~\cite{grosser2012polly}, GRAPHITE~\cite{trifunovic2010graphite}, and PLuTo~\cite{bondhugula2008pluto}, use the powerful mathematical framework of polyhedral model (provided by libraries such as ISL~\cite{verdoolaege2010isl}) to represent the computations in loops in a more compact and analyzable form compared to traditional compiler IRs such as Static Single Assignment (SSA) forms. Polyhedra offer a way to represent data layouts, loop iteration spaces, and dependencies between computations in a unified manner.

Polyhedral optimization is application of integer linear algebra to optimize loop nests with affine bounds and affine memory accesses. The main idea is to represent the iteration space of loops, as well as memory accesses and dependencies, using polyhedra. This representation allows, for example, to find hyperplanes orthogonal to data dependencies, that can represent parallelizable loops; or to find transformations of the iteration space that improve data locality or enable vectorization. There are works that apply theory of polyhedra and integer linear programming to optimize data layouts to improve cache performance, such as the work by \citeauthor{clauss2000automatic}~\cite{clauss2000automatic} that uses Ehrhart polynomials to change accesses to arrays into consecutive memory accesses, effectively optimizing the data layout for better cache performance.

Many works iterate on the basic polyhedral model to extend its applicability or improve the optimization results by combining it with cost models, heuristics, or machine learning techniques (e.g.,\citeauthor{baghdadi2021deep}~\cite{baghdadi2021deep}). Some works show benefits of combining polyhedral optimization based on cost models or heuristics with autotuning~\cite{chelini2020automatic} or human insights~\cite{zinenko2014clint,bagneres2016opening}.

Many DSL compilers (e.g., Halide~\cite{ragan2013halide}, Tiramisu~\cite{baghdadi2019tiramisu}) that will be discussed in \cref{sec:abstractions} use polyhedral optimization techniques (or derived versions) as part of their optimization pipelines. These DSLs often provide higher-level abstractions that allow developers to guide the optimization process using directives that can be mapped to polyhedral transformations.

\textbf{Polygeist}~\cite{moses2021polygeist} is a tool that translates \cpp code to MLIR\@. It combines traditional compiler optimizations on SSA-based IRs with polyhedral optimizations on the affine dialect of MLIR\@, outperforming both Polly and PLuTo on the PolyBench~\cite{pouchet2012polybench} benchmark suite. \xxx{Continue from here.}

Since polyhedral optimizations are powerful tools that can totally change the structure of the code, some works have focused on improving the interpretability of the transformations and their results, such as the work by \citeauthor{bagneres2016opening}~\cite{bagneres2016opening} that translates the scheduling decisions of polyhedral optimizers into a human-readable set of transformation directives --- e.g., loop interchange, strip-mine (tiling), \ldots --- that describe the transformations in a more intuitive way.


\section{Autotuning}\label{sec:autotuning}

Autotuning techniques are powerful methods for optimizing performance of applications based on empirical performance measurements or cost models. They involve performance-cost model-based and empirical search methods for exploring large parameter spaces (\emph{search space}s) to find optimal configurations. They can control various parameters, such as algorithmic choices, data layouts, tiling sizes, unrolling factors, and parallelization strategies; or even tune build configurations and compiler flags.

They usually involve a search algorithm that explores the search space, performing local or global optimization. Many such algorithms have been proposed, including simple methods such as grid search and random search that can be effective for search spaces with a small number of parameters or hill climbing methods that greedily explore the search space by iteratively moving towards better configurations based on performance measurements. These methods are surprisingly effective in many cases, especially when the search space is not too large or when the performance landscape does not have many local minima. Even methods that simply combine random search with local search (e.g., by performing random restarts) can be quite effective in practice. More sophisticated methods include simulated annealing, genetic algorithms, swarm optimization, Bayesian optimization, and many other methods. Many of these methods balance exploration and exploitation in different ways, and their effectiveness can depend on the specific characteristics of the search space and the performance landscape.

\textbf{OpenTuner}~\cite{ansel2014opentuner} is the first framework that combines multiple search techniques (e.g., genetic algorithms, simulated annealing, etc.) in ensembles (based on multi-armed bandits) with a flexible API for defining the search space and the objective function. It is a general-purpose autotuning framework in Python that allows users to define their own search spaces and objective functions, and the black-box running of the target application with different configurations from the search space. \textbf{ATF}~\cite{rasch2018atf} is a C++ framework that builds on top of OpenTuner and a domain-specific autotuner CLTune and provides options for pruning the search space by defining constraints on the parameters (e.g., divisibility constraints for tiling sizes) as well as employing parallelism when generating the search space.

Tools such as \textbf{Hyperopt}~\cite{bergstra2015hyperopt} and \textbf{Optuna}~\cite{akiba2019optuna} are general-purpose optimization frameworks (albeit built for optimizing hyperparameters of machine learning models) that use Bayesian optimization techniques to efficiently explore large search spaces with a limited number of evaluations --- Bayesian optimization involves building a surrogate model of the performance landscape based on the observed performance measurements, and using this model to guide the search towards promising regions of the search space. They can be used for autotuning by defining the search space and objective function in a way that is suitable for optimizing code performance. Optuna stands out for its define-by-run API, which allows for dynamic construction of the search space during the optimization process, which can be particularly useful for complex optimization problems where the search space may not be known a priori, cannot be efficiently represented in a static manner, or is too large to be exhaustively explored.

% There are many autotuning frameworks that are specific to certain domains, such as AutoTVM~\cite{chen2018tvm} for deep learning workloads, Kernel Tuner~\cite{van2019kernel} for GPU kernels

Autotuning techniques can be used in combination with other optimization methods, such as polyhedral optimization or DSLs\@. They are particularly useful for optimizing performance in cases where the performance landscape is complex and difficult to model analytically.

\subsection{Domain-specific languages (DSLs)}\label{sec:dsls}

\textbf{Halide}~\cite{ragan2013halide} is a \cpp-embedded DSL with a custom compiler and runtime system that primarily targets image and array processing applications (including regular stencil computations). It is based on defining pipelines of processing stages, where each stage represents a computation that can be optimized independently. The resulting computation pipeline is a directed acyclic graph (DAG) of stages that are subject to various transformations, such as tiling, fusion, and parallelization. These transformations can be guided by the developer using a scheduling language or by autotuning techniques. The Halide compiler performs various checks to ensure that each transformation preserves the semantics of the original computation. It uses interval analysis, which is a less expressive but more powerful (for the target domain) representation than the polyhedral model. Halide's design allows for a high degree of optimization at the cost of expressivity, as it is not suitable for more complex computations, such as those that contain imperfectly nested loops or data-dependent control flow, or non-rectangular iteration spaces.

\begin{lstlisting}[language=C++]
#include <Halide.h>
using namespace Halide;

ImageParam A(Float(32), 2, "A"), B(Float(32), 2, "B"), C(Float(32), 2, "C");
Param<float> alpha("alpha"), beta("beta");

Func gemm("gemm");
Var i("i"), j("j");
RVar k("k", 0, A.dim(1).extent());

gemm(i, j) = beta * C(i, j);
gemm(i, j) += alpha * A(i, k) * B(k, j);

// Schedule
gemm.tile(i, j, i0, j0, i1, j1, 64, 64)
    .reorder(i1, j1, i0, j0)
    .parallel(i0)
    .vectorize(i1);
\end{lstlisting}


The above example shows how to express the matrix multiplication (GEMM) kernel in Halide. \lstinline{Param} and \lstinline{ImageParam} are used to define the input parameters and input data, respectively. The computation is defined in the \lstinline{Func} object using \lstinline{Var} (or \lstinline{RVar} for reduction variables) objects to represent dimensions involved in the computation. This computation (possibly appearing in a larger pipeline) is then subject to various transformations that can be expressed using the scheduling language. The \lstinline{gemm} computation then is, in the scheduling language, tiled with tile sizes of $64 \times 64$, the loops are then reordered to improve data locality, the outer loop is parallelized, and the inner loop is vectorized.

\textbf{Tiramisu}~\cite{baghdadi2019tiramisu} is a \cpp-embedded DSL superficially similar to Halide that targets a wider range of applications, including those with more complex control flow and data access patterns. Unlike Halide, Tiramisu is more closely based on the polyhedral model, which allows it to represent a broader class of computations, including those with imperfectly nested loops or skewed and non-rectangular iteration spaces. Its primary domains include image processing, deep learning, and general scientific computing applications, and the framework also supports sparse computations. Similarly to Halide, Tiramisu provides its own scheduling language and a compiler that performs various checks to ensure that the transformations preserve the semantics of the original computation. It can target various hardware architectures, including multi-core CPUs and GPUs. Unlike Halide, Tiramisu also supports distributed computing over multiple nodes using MPI\@.

The matrix multiplication example in Tiramisu is shown below.

\begin{lstlisting}[language=C++]
#include <tiramisu/tiramisu.h>
using namespace tiramisu;

tiramisu::init("gemm");
input C("C", {M, N}, p_float32),
      A("A", {M, K}, p_float32), B("B", {K, N}, p_float32);
input alpha("alpha", p_float32), beta("beta", p_float32);

computation gemm("gemm", {i, j, k}, p_float32);
gemm.set_expression(beta * C(i, j) + alpha * A(i, k) * B(k, j));

// Schedule
gemm.tile(i, j, 64, 64, i0, j0, i1, j1);
gemm.reorder(i1, j1, i0, j0);
gemm.parallelize(i0);
gemm.vectorize(i1);
\end{lstlisting}

\textbf{Exo}~\cite{ikarashi2022exocompilation} is Python-embedded DSL that generates C code for specialized hardware. The target-specific instructions and optimization transformations performed on them are all defined in extensible user-level libraries. Similarly to Halide and Tiramisu, the transformations are guided by the developer using a scheduling language. Exo then performs various checks based on effect analysis to ensure program equivalence and memory safety throughout the transformations.

In Exo, the \lstinline{@instr} decorator is used to define target-specific instructions as Python functions that specify the semantics of the instruction in terms of its inputs and outputs. The \lstinline{@proc} decorator is used to define procedures that can be called from the generated code and can be subject to various transformations. The transformations in Exo are defined as Python functions that take the procedures or instructions as input and produce transformed versions of them, while ensuring that the transformations preserve the semantics of the original code. If a function transformation relies on a certain invariant (e.g., that a certain dimension of an array is divisible by a certain value), the user can specify this invariant using python assertions.

The matrix multiplication example in Exo is shown below with the same transformations as in the Halide example.

% TODO: check whether the syntax is correct
\begin{lstlisting}[language=Python]
from exo import *

@proc
def gemm(M: size, N: size, K: size,
         alpha: float, A: f32[M, K], B: f32[K, N],
         beta: float, C: f32[M, N]):
  assert M % 64 == 0 and N % 64 == 0 and K % 64 == 0
  for i in range(M):
    for j in range(N):
      C[i][j] *= beta
      for k in range(K):
        C[i][j] += alpha * A[i][k] * B[k][j]

# Schedule
gemm = tile(gemm, 'i', 64)
gemm = tile(gemm, 'j', 64)
gemm = reorder(gemm, 'i', 'j')
gemm = parallel(gemm, 'i')
gemm = vectorize(gemm, 'i')
\end{lstlisting}

The framework then generates C code for the target hardware that can be integrated into a larger application. The generated code does not rely on any runtime system.


\subsection{Annotation-based tools}\label{sec:annotation-based-tools}

\textbf{OpenMP}~\cite{openmp_6.0_spec} is a widely used API for parallel programming in C, C++, and Fortran\@. It provides a set of compiler directives, library routines, and environment variables that allow developers to specify parallelization and synchronization of code regions, as well as to control data sharing or privatization between threads. It supports various loop transformations such as loop unrolling, tiling, and vectorization via \lstinline{#pragma omp} directives, with varying levels of support across different compilers. GPUs can be targeted using the \lstinline{#pragma omp target} directive along the \lstinline{teams} construct to control warps/wavefronts and threads within them. The advantage of OpenMP is that it is widely supported by a wide range of compilers and hardware architectures, and its implementations follow a well-defined shared specification. The specification is continually evolving to support new features and optimizations.

The main limitation of OpenMP is that it is primarily focused on parallelization and does not provide a rich set of directives; nevertheless, the matrix multiplication example can be expressed in OpenMP as follows:

\begin{lstlisting}[language=C++]
void gemm(int M, int N, int K,
          float alpha, float A[M][K], float B[K][N],
          float beta, float C[M][N]) {
  #pragma omp parallel for collapse(2) schedule(static)
  for (int i = 0; i < M; i++) {
    for (int j = 0; j < N; j++) {
      C[i][j] *= beta;
      for (int k = 0; k < K; k++) {
        C[i][j] += alpha * A[i][k] * B[k][j];
      }
    }
  }
}
\end{lstlisting}

\lstinline{collapse(2)} is used to indicate that the two outer loops should be collapsed into a single loop for parallelization, which allows for better load balancing and performance on multi-core CPUs. However, this code does not include any other transformations such as tiling or vectorization, which would require additional directives that are not widely supported or manual code modifications.

For tiling, OpenMP provides the \lstinline{#pragma omp tile} directive that can be used to specify tiling transformations for loops, and the vectorization can be achieved using the \lstinline{#pragma omp simd} directive. The matrix multiplication step of the above code can be tiled and vectorized as follows:

\begin{lstlisting}[language=C++]
#pragma omp tile sizes(64, 64)
#pragma omp parallel for collapse(2) schedule(static)
for (int i = 0; i < M; i++) {
  for (int j = 0; j < N; j++) {
    float temp = 0.0f;

    #pragma omp simd reduction(+:temp)
    for (int k = 0; k < K; k++) {
      temp += alpha * A[i][k] * B[k][j];
    }

    C[i][j] = beta * C[i][j] + temp;
  }
}
\end{lstlisting}

Some efforts have been made to extend OpenMP with directives for more complex, composable transformations. One example is the work by \citeauthor{kruse2018user}~\cite{kruse2018user} that extends the OpenMP API in the Clang compiler with directives for loop transformations such as tiling, reversal (the loop is executed in reverse order), interchange, and array packing (some subset of the accessed array is copied to a temporary buffer).

\subsection{Native tools and libraries}\label{sec:native-tools}

\textbf{CuTe} from the Cutlass~\cite{thakkar2023cutlass} framework is a collection of \cpp template abstractions that can hierarchically represent multidimensional layouts of threads and data. They are specifically designed for representing and optimizing computations on NVIDIA GPUs\@. The multidimensional layouts can represent a wide range of dense linear algebra computations, and they also allow for functional composition of layouts like in Noarr\@, which is particularly useful for common transformations such as tiling or partitioning~\cite{nvidia-cute}.

CuTe stands out for the expressiveness of its layout abstractions, including the algebraic composition of layouts. The most basic primitives are dynamic \lstinline|int{N}| and static \lstinline|Int<N>{}| integer values, possibly in tuples (\lstinline|make_tuple(int{M}, int{N})|) that can be constructed recursively --- all those collectively are called \emph{IntTuple}s.

A CuTe layout is defined as a tuple $(\text{Shape}, \text{Stride})$ (written as \lstinline{shape:stride}) where both \text{Shape} and \text{Stride} are IntTuples. Since IntTuples can be hierarchical, $(2, (2, 2)) : (1, (2, 4))$ is a valid layout that represents a two-dimensional layout of shape $2 \times 4$ where the second dimension can be indexed as a tuple of two dimensions of size $2 \times 2$ --- this describes a tiled layout where the second dimension of size $4$ is tiled into two tiles of size $2$. Each layout (or equivalently, each multidimensional dimension) can be indexed either using a tuple of appropriate shape, or using a linear index that is upper-bounded by the product of the dimensions of the shape.

CuTe defines layout compatibility (partial order between layouts): a layout $A$ is compatible with a layout $B$ if their shapes have the same size and if indices of $A$ are valid indices of $B$. This effectively means that a linear dimension of size $N$ in $A$ can be replaced by a tuple with the same total size $N$ in $B$, producing a compatible layout. For example, the layout with shape $(2, 6)$ is compatible with the layout with shape $(2, (2, 3))$ (second dimension of size $6$ has been broken into two dimensions of size $2$ and $3$).

The compatibility relation is the basis for defining layout algebra that is based on functional composition of layouts: $R = A \circ B$ is defined as $R(x) = A(B(x))$ where $B$ is applied first and then $A$ is applied to the result (this is well-defined thanks to the ability to index layouts using linear indices). $B$ is compatible with the resulting layout $R$. The abstraction then uses the functional composition of layouts to define transformations (but only showcases tiling).

This functional composition of layouts follows the same principle as Noarr. Most notably, that the right-hand-side input of the composition can be thought of as a partial function that transforms the input index space into a new index space.

\textbf{GridTools}~\cite{afanasyev2021gridtools} is a \cpp-embedded DSL that targets stencil computations on structured grids, primarily in the context of weather and climate modeling. The stencil computations are represented as a composition of abstract stages implemented as \cpp functors. The framework supports backends for various hardware architectures, including many-core CPU systems and GPUs\@. Since the stencil stages are represented in a high-level manner, the framework can apply various hardware-specific optimizations depending on the target backend.

\textbf{MDSpans}~\cite{trott2022mdspan} are a \cpp abstraction for representing multidimensional arrays with flexible data layouts. The mapping of multidimensional indices to linear memory addresses and the element access policy that translates the resulting linear index to element references are both customizable, which allows for representing a wide range of data layouts and special memory types. The predefined layouts include row-major, column-major, and generic strided layouts, but the abstraction itself allows for defining custom memory layouts as well --- however, it does not provide any built-in mechanism for hierarchical composition of layouts or their analysis beyond recognizing the predefined ones and retrieving their strides and extents.

MDSpans are sufficient for representing simple data layouts, and the user-definable policies allow for using them beyond that as well. However, in such cases, they do not provide any benefits other than providing a uniform interface for accessing elements, which is not much different from using raw pointers and manual index calculations. In particular, they do not introduce any type safety or correctness guarantees and their interface is reliant on the user to correctly implement the access policies and communicate the intended semantics of the layout dimensions and the mapping to memory addresses by other means if they are not using the small set of predefined layouts. This is usually sufficient as long as the design of an optimized computation performs transformations such as tiling or transposition of the dimensions, which are supported by the \lstinline{submdspan} constructor and the predefined \lstinline{layout_transpose} policy adaptor.

\textbf{Kokkos}~\cite{trott2021kokkos} is a \cpp library that provides abstractions for parallel execution and data management across different hardware architectures, its primary focus is providing a performance-portable programming model for multi-core CPUs and GPUs\@. It provides the \lstinline{Kokkos::View} abstraction for representing multidimensional arrays with flexible data layouts and memory spaces (e.g., host memory, device memory, \ldots). The expressiveness of the \lstinline{Kokkos::View} abstraction, when it comes to representing data layouts, is similar to that of MDSpans\@, with the same predefined layouts and user-definable mapping policies --- and the two abstractions can be easily inter-converted. However, Kokkos views also allow specifying the memory space where the data is allocated, and they provide automatic data movement between memory spaces when necessary. Kokkos views also support shared ownership semantics similar to \cpp shared pointers. Kokkos provides a set of parallel algorithms (e.g., \lstinline{parallel_for}, \lstinline{parallel_reduce}, \ldots) that can run the user-defined computations in parallel on the target backend.

To support multidimensional parallelism, Kokkos provides the \lstinline{MDRangePolicy} abstraction, which allows for defining parallel execution policies over multidimensional index spaces. The \lstinline{MDRangePolicy} parallelizes the execution of a user-defined computation in tiles of configurable sizes. To support more flexible parallelization strategies, Kokkos also provides the \lstinline{TeamPolicy}, which allows for defining teams of threads that can cooperate on executing a user-defined computation with synchronization and shared memory capabilities (team scratch memory). The \lstinline{ThreadVectorRange} can be used to express vector-level parallelism within a team (or warp/wavefront on GPU\@). These policies are composable, allowing for expressing multilevel parallelism. Furthermore, the computation can be queued to a specific execution stream on the target backend, which allows for overlapping computation and data movement.

\textbf{RAJA}~\cite{beckingsale2019raja} is another \cpp library that provides abstractions for platform portability for high-performance computing applications. It abstracts data layouts via the \lstinline{RAJA::Layout} class, which represents a dense multidimensional array layout, defaulting to row-major order but allowing for arbitrary permutations of the dimensions. The library also provides the \lstinline{RAJA::OffsetLayout} class, which differs in that it represents layouts with arbitrary integer offsets for each dimension --- this simplifies, for example, definition of stencil computations that expect padding around the data. Both of these layout abstractions can be used to define a \lstinline{RAJA::View}, which is a multidimensional array abstraction that provides an interface for accessing elements based on the defined layout. The expressiveness of these abstractions is lower than that of MDSpans or Kokkos views, but they allow for the inverse mapping of linear indices to multidimensional indices.

While RAJA provides much weaker abstractions for data layouts, it provides more flexible abstractions for parallel execution compared to Kokkos\@. In particular, it allows for defining representing complex loop nests via the \lstinline{RAJA::kernel} abstraction that can be applied to a kernel execution policy that is defined as a composition of compile-time constructs representing statements via template metaprogramming. The two main statement building blocks for defining the kernel execution policies are \lstinline{RAJA::For} and \lstinline{RAJA::Lambda} constructs, which represent a single loop level and a computation to be executed at that loop level, respectively. RAJA provides a wide range of statement building blocks that can represent tiling, running the nested statements in a CUDA or HIP kernel, or performing reductions, among others. These building blocks can be given an execution policy that defines how the represented loop level is parallelized (e.g., sequentially, via OpenMP, mapping to a CUDA block or grid dimension, \ldots). The resulting kernel execution policy represents a complex loop nest parallelized according to the specified execution policies, that is then used by the \lstinline{RAJA::kernel} abstraction to execute user-defined computations with the supplied parameters as shown in the following example:

% https://raja.readthedocs.io/en/develop/sphinx/user_guide/tutorial/kernel_nested_loop_reorder.html
\begin{lstlisting}[morekeywords={RAJA}]
RAJA::TypedRangeSegment<KIDX> KRange(kmin, kmax);
RAJA::TypedRangeSegment<JIDX> JRange(jmin, jmax);
RAJA::TypedRangeSegment<IIDX> IRange(imin, imax);

RAJA::OffsetLayout<3> layout = RAJA::make_permuted_offset_layout
  ({{imin, imax}, {jmin, jmax}, {kmin, kmax}}, {2, 0, 1});
RAJA::View<double, RAJA::OffsetLayout<3>> view(data, layout);

using KJI_EXECPOL =
  RAJA::KernelPolicy<
    RAJA::statement::For<2, RAJA::seq_exec,     // 2: k
      RAJA::statement::For<1, RAJA::seq_exec,   // 1: j
        RAJA::statement::For<0, RAJA::seq_exec, // 0: i
          RAJA::statement::Lambda<0>
  > > > >;

RAJA::kernel<KJI_EXECPOL>(
  RAJA::make_tuple(/*0*/ IRange, /*1*/ JRange, /*2*/ KRange),
  [=] (/*0*/ IIDX i, /*1*/ JIDX j, /*2*/ KIDX k) {
    view(i, j, k) = i + j + k;
  });
\end{lstlisting}

In the above example, we define a 3D loop nest with iteration spaces defined by the \lstinline{KRange}, \lstinline{JRange}, and \lstinline{IRange} segments that operates on a 3D array represented by the \lstinline{RAJA::View} abstraction with a custom layout defined by the \lstinline{RAJA::OffsetLayout} class with a specific permutation of the dimensions. The view is a multidimensional array that can be accessed using the indices defined by $($\lstinline{IRange}$\times$\lstinline{JRange}$\times$\lstinline{KRange}$)$; $k$ is the majormost dimension, followed by $i$ and $j$ as the minor dimensions.


\section{Machine learning and LLMs for optimization}\label{sec:ml-and-llms-for-optimization}

% TURNING POINT: the year 2020 (introduction of GPT-3)

Recently, machine learning (ML) techniques, including large language models (LLMs), have been increasingly applied to various aspects of code optimization. The main motivation for using these techniques is their flexibility and ability to learn complex patterns from data, which can overcome limitations of traditional optimization methods that rely on hand-crafted heuristics or analytical models. We have already discussed autotuning techniques in Section~\ref{sec:autotuning} that can be used to tune various compiler flags and options to optimize performance based on empirical measurements, so we will focus on methods that use ML techniques that are not better categorized as autotuning techniques. What characterizes these methods is that they make decisions based on learned patterns, applying them to new code or new optimization problems without relying on empirical measurements of the target code, which would be the case for autotuning techniques (such as Bayesian optimization methods).

Some older works have applied ML techniques as surrogate models for performance prediction, such as the work by \citeauthor{fursin2011milepost}~\cite{fursin2011milepost}. Recent additions to this direction in the area of HPC includes works such as \citeauthor{baghdadi2021deep}~\cite{baghdadi2021deep} that uses deep learning methods as cost models in a polyhedral optimization framework (the Tiramisu compiler) or \citeauthor{adams2019learning}~\cite{adams2019learning} that uses a learned cost model to guide the search in the Halide autotuning framework.

More recently, LLMs have emerged as a powerful tool for code optimization, with the ability to learn from large codebases and generate optimized code based on natural language descriptions or code snippets. Various works have explored the use of off-the-shelf LLMs or fine-tuned (or even trained from scratch) LLMs for generating directives used to optimize code, such as OpenMP directives for parallelization, scheduling directives for frameworks such as Halide or Tiramisu, or even generating optimized code directly.

Works that use LLMs for generating optimization directives include PragFormer~\cite{harel2025pragformer} that trains a transformer-based model to identify \lstinline{for} loops in C code that can be parallelized and even identify the need for privatization or reduction variables. Works such as OMPify~\cite{kadosh2023advising}, Graph2Par~\cite{chen2023learning}, and AutoParLLM~\cite{mahmud2023autoparllm} then use GNN-based models to generate OpenMP directives for parallelization with even higher accuracy.

HPC-Coder~\cite{nichols2024hpc} shows that fine-tuning LLMs on HPC code can enable them to generate OpenMP directives for parallelization with high accuracy as well as generate parallel code or MPI-based distributed code directly. The MPI code generation is further studied by works such as MPI-RICAL~\cite{schneider2023mpi} and MPI{rigen}~\cite{schneider2024mpirigen}.

Works that use LLMs or other deep learning methods for generating scheduling directives ComPilot~\cite{merouani2025agentic} that uses a LLM agent as a search driver when exploring the search space of transformation directives, and LOOPer~\cite{merouani2025looper} that uses LSTM-based solution inspired by the work of \citeauthor{baghdadi2021deep}, both solutions achieve autoscheduling in the Tiramisu compiler.

Using ML techniques as surrogate models or requesting them to propose optimization directives has the benefit of enabling formal verification of the optimized code, as the model acts simply as a search driver in a solution that would otherwise work as an autotuning solution, trying semi-random configurations and adjusting on-the-fly heuristics for selecting each next configuration based on the observed performance measurements. Direct generation of optimized code goes beyond and allows the model to make more fundamental changes to the optimized code --- some solutions even use the machine learning model to generate the entire optimized code directly from a natural language description (or from another high-level representation of the expected behavior of the code)~\cite{godoy2024large}.

Since LLMs are generally trained on large codebases, and only handful of the code falls into the HPC domain, the performance of off-the-shelf LLMs on generating optimized code for HPC applications starts to be competitive only very recently, perhaps with the introduction of Codex~\cite{chen2021evaluating}. This challenge was earlier addressed by fine-tuning the LLMs on HPC code~\cite{nichols2024performance} or by using smaller models that are trained from scratch on HPC code~\cite{xu2022systematic}. Obviously, such work has to be accompanied by standardized benchmarks and datasets of HPC code, such as PolyBench~\cite{pouchet2012polybench}, ParEval~\cite{nichols2024can}, KernelBench~\cite{ouyang2025kernelbench}, HPCorpus~\cite{kadosh2023quantifying}, or HeCBench~\cite{jin2023benchmark}.

Since the proficiency of LLMs as of the beginning of 2026 is still not sufficient for generating optimized code without supervision or verification, most works rely on using LLMs for translating between better interpretable language and a programming model such as CUDA~\cite{palkowski2024gpt,dearing2024lassi}. One of these works, LASSI, defines self-correcting pipeline where the LLM proposes a solution similarly to an autotuning solution with the added benefit of being able to respond to the feedback from the compiler or the verifier. This direction is used in various state of the art solutions such as ComPilot~\cite{merouani2025agentic}.
