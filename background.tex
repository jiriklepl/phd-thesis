\chapter{Interactions between Hardware Features and Memory Access Patterns}\label{chap:background}

To better understand the motivation behind layout and traversal optimizations, which collectively change the memory access patterns in a program, we first outline the hardware features of modern high-performance systems that are most relevant to our focus on these optimizations.

We target the two main general-purpose architectures used in high-performance computing: multi-core CPUs and GPU accelerators.

CPUs are primarily designed for task processing, executing each active thread on an independent core, while GPUs are optimized for massively data-parallel workloads that run thousands of threads concurrently in SIMT (Single Instruction, Multiple Threads) fashion~\cite{hennessy2019computer,cuda_programming_guide}. A single thread of execution runs a sequence of instructions (a task) using a set of registers and other resources (such as caches or arithmetic units).

GPUs are devices \xxx{separated} from the host system, with their own memory and task scheduling. Thus, a computation running on a GPU typically requires transferring data from the system memory to the GPU device memory, and then transferring the results back to the system memory after the computation is done. The data-parallel task is typically expressed as a \emph{kernel function} that is then scheduled to run on the GPU independently of the host system. CPU workloads, on the other hand, typically run directly on the host system using the system memory without necessitating any data transfer, unless the computation is distributed across multiple machines.

The main difference between code execution on the two architectures is that in CPUs, a single core can run one thread at a time (or a few threads in the case of hyper-threading), while in GPUs, many threads run concurrently on the same core in lockstep, executing the same instruction at the same time on different data. The distinction between them, however, is not strict, as modern CPU cores also support data parallelism through using specialized vector units that can, in a single instruction, operate on multiple data elements (SIMD) at the same time.

The differences between the two architectures present different challenges and opportunities for optimizing the performance of algorithms, which we will discuss in more detail in the following sections.

\xxx{Both CPUs and GPUs have hierarchies of memory units with different latencies and bandwidths. In both architectures, a computation directly operates on a limited amount of register memory, which is the fastest, but also the most limited memory unit --- for example, it does not allow for indirect accesses to data. On the opposite end of the hierarchy, both architectures have access to a large global memory that can be accessed by all active threads, but with high latency (compared to other memory units).}

% In between these two extremes, both CPUs and GPUs have multiple levels (layers) of cache memory that offer better latency and bandwidth depending on how close the caches are to the computation units the computation is running on --- generally, there is at least one cache level dedicated to each core, and one shared cache level for all cores. The main goal of caches is the same regardless of the architecture or their levels: to store data that is likely to be accessed in the near future, so that such accesses are served faster and, for the closest cache levels, with less interference with other threads.

A simple example that will help us illustrate the impact of data layouts and traversal orders on performance of execution on the two architectures is the matrix multiplication algorithm, which computes each element of the output matrix ($C$) as a dot product of a row from the first input matrix ($A$) and a column from the second input matrix ($B$), where all matrices are stored in the standard row-major order (row by row). The algorithm can be implemented in \cpp as follows:

\begin{lstlisting}[language=C++, caption={Matrix multiplication}, label={lst:matrix-multiplication}]
float C[M][N]; // M rows, N columns
float A[M][K]; // M rows, K columns
float B[K][N]; // K rows, N columns

// iterating over output matrix C
for (int i = 0; i < M; ++i) {
    for (int j = 0; j < N; ++j) {
        // single dot product
        float sum = 0;
        for (int k = 0; k < K; ++k) {
            sum += A[i][k] * B[k][j];
        }
        C[i][j] = sum;
    }
}
\end{lstlisting}

We will use this example in the following sections as a running example to illustrate the impact of different algorithm design choices on the performance on CPUs and GPUs.

\section{CPU considerations}\label{sec:cpu-considerations}

When optimizing an algorithm such as the matrix multiplication example in \cref{lst:matrix-multiplication} for execution on a CPU, we primarily need to consider caching. Caches are memory units that transparently store data that is likely to be accessed in the near future under the principle of locality, which states that programs tend to access data repeatedly in a short period of time (temporal locality) and access data stored in nearby memory locations (spatial locality)~\xxx{(cite)}.

Many algorithms either naturally exhibit good locality (e.g., traversing a row-major matrix by rows) or can be transformed to have better locality (e.g., by reordering computations in such a way that repeated accesses to the same data are closer in time).
% This principle, thus, directly motivates layout and traversal optimizations.

The current implementation of the matrix multiplication algorithm could be made more cache-friendly in two simple ways. First, we can transpose the layout of the input matrix $B$ to column-major (column by column) order, so that the innermost loop accesses contiguous memory locations in both input matrices, improving spatial locality and thus performance.

The second way to improve caching is to improve the temporal locality of the algorithm by partitioning the computation into smaller tiles that can fit into the cache. In the current implementation (after transposing $B$), the innermost loop accesses unique elements of the input matrices $A$ and $B$ in each iteration. For an input of sufficient size, this access pattern leads to repeated cache misses (necessity to update the cache with new data from memory). If we partition the matrices into tiles (sub-matrices) that can fit in the cache, then updating the corresponding elements of the output matrix by computing the dot products of the corresponding rows and columns of the tiles allows for efficient reuse of the data in the input matrices (scaling linearly with the tile dimensions, as long as the tiles fit in the cache).

In practice, this transformation can be, in high-level, expressed as splitting the loops into smaller blocks, iterating over the blocks in the outer loops and iterating over the elements of the blocks in the inner loops, as shown in \cref{lst:matrix-multiplication-tiled}.

\begin{lstlisting}[language=C++, caption={Tiled matrix multiplication}, label={lst:matrix-multiplication-tiled}]
for (int ii = 0; ii < M; ii += i_block)
  for (int jj = 0; jj < N; jj += j_block)
    for (int kk = 0; kk < K; kk += k_block)
      // multiply tile of A and tile of B,
      //  accumulate into tile of C
\end{lstlisting}

In addition to caching, we also need to consider the parallelization and vectorization capabilities of the CPU\@.

CPU cores have specialized vector units that can, in a \emph{single instruction}, operate on \emph{multiple data} elements at the same time (SIMD). If this can be performed efficiently, it can lead to a multiplicative improvement in performance depending on the width of the vector units (e.g., $256$-bit wide vector units can operate on $8$ single-precision floating-point numbers at the same time). By changing the data layout of $B$ to column-major order (as with improving spatial locality), the innermost loop accesses data of both input matrices sequentially, allowing us to unroll the loop by the width of the vector units (relative to the data type) and replace the unrolled iterations with vectorized instructions that compute multiple iterations at the same time.

% , which reduce memory access latency; parallelization capabilities, which allow for computing multiple parts of the output matrix in parallel using multiple computation cores; and vectorization capabilities, which allow for processing multiple consecutive data elements at the same time on a single core.

% To improve caching, we can apply tiling (also called blocking), which involves splitting the loops into smaller partitions (tiles) such that one or more loops are replaced with a group of outer loops that iterate over the tiles and inner loops that iterate over the elements of the tiles. The goal is to choose a tile size such that the data accessed within the inner loops can fit in the target cache, thus improving temporal locality and reducing memory access latency as all data are fetched from the cache instead of the global memory (data are loaded from the global memory just once, then they are cached).

% Parallelization is typically achieved similarly --- the computation is partitioned into tiles (ideally so that the data dependencies between the computations of different tiles are minimized; i.e., so that computing one tile affects the computation of others as little as possible). Then, the outer loops that iterate over the tiles are parallelized --- replacing their iteration with spawning multiple threads of execution, which are then automatically scheduled on the available CPU cores.

To parallelize the algorithm, we can use a similar approach that we used for improving temporal locality. If we partition the output matrix into tiles, we can then create multiple execution threads that compute different tiles of the output matrix in parallel. To minimize the overhead of parallelization, the tiles should be large enough so that the corresponding computation is sufficiently large to amortize the overhead of spawning and scheduling threads, but also small enough so that the number of tiles can saturate all available CPU cores with work.

% Vectorization is typically achieved by ensuring that the innermost loop accesses contiguous data elements. In the particular case of \cref{lst:matrix-multiplication}, this can be achieved by changing the data layout of the input matrix $B$ to column-major (transposing it). This way, the physical data of both input matrices are accessed in a contiguous way and the compiler can automatically generate vectorized instructions that computes multiple iterations of the innermost loop at the same time using the vector units of the CPU\@. These vectorized instructions (SIMD instructions, for Single Instruction, Multiple Data) perform the same operation on multiple data elements at the same time and thus the loop needs lesser number of iterations to be executed, improving performance.

% Changing the data layout of $B$ can also improve spatial locality, as the innermost loop will access contiguous memory locations in both input matrices and caches commonly fetch data in blocks of contiguous memory (cache lines). This shows that one change in memory access patterns can affect multiple hardware features and thus have a complex interaction with the benefits of other optimizations.


\section{GPU considerations}\label{sec:gpu-considerations}

% GPU accelerators are among the most widely used hardware platforms in high-performance computing~\cite{top500}. Their importance has further increased with the rise of large language models and other deep learning workloads~\xxx{(CITE)}.

% Since NVIDIA GPU architectures currently dominate the high-performance computing landscape~\cite{top500}, we will default to their nomenclature when describing the relevant hardware features and use them as a reference point.

% \xxx{GPUs have their own global memory, so efficient execution of an algorithm on a GPU requires optimizing the transfer of data between the CPU and GPU\@. This is yet another case where data partitioning (into tiles or blocks) can be useful, so this is another motivation for layout and traversal optimizations.}

% The execution model of GPUs is based on a virtual hierarchy of threads organized into (possibly 3-dimensional) grids of thread blocks. This organization is important because a common practice is to manually replace each parallelized loop in the algorithm with a dimension of the thread grid --- this may be done after applying other optimizations, such as tiling (so that each thread block maps to a tile of the output matrix, for example).

% The grid is specified by the programmer when launching a GPU kernel (a function that runs on the GPU) and then each thread block is automatically scheduled on available streaming multiprocessors (SMs) of the GPU\@ until all blocks are fully executed. Each SM then runs the threads of the block in consecutive groups of 32 (called warps) in lockstep (executing same instructions). Since all threads in a warp execute on the same computation unit, it is important to ensure that they do not diverge in their execution paths as well as to ensure that they access memory in regular patterns --- while GPUs can handle some divergence and irregular memory access patterns, they can lead to significant performance degradation.

% This makes the choice of data layout and traversal order even more important on GPUs, as its execution model is tightly coupled with the traversal loops replaced by the thread grid dimensions.

% Grouping threads into blocks also enables programmers to use shared memory, which is a user-managed cache shared by all threads in the same block (running on the same SM core), as well as fast synchronization primitives between the threads. For the threads in the same warps, gpus also provide warp-wide communication primitives that allow threads to exchange data even faster.

GPU accelerators are among the most widely used hardware platforms in high-performance computing~\cite{top500}. Since NVIDIA GPU architectures currently dominate the high-performance computing landscape~\cite{top500}, we will default to their nomenclature when describing the relevant hardware features and use them as a reference point.

When GPU-accelerating an algorithm, we need to consider its execution model, which is based on a hierarchy of threads organized into grids of thread blocks. Each block is then automatically scheduled on hundreds or thousands of streaming multiprocessors (SMs) until all blocks are fully executed. This grid is specified by the programmer when launching a GPU kernel (a function that is to be run on the GPU) and typically replaces the parallelized loops in the algorithm. As such, the number of thread blocks should be large enough so all SMs are saturated with work.

Each SM then runs consecutive groups of 32 threads (called warps) from the assigned block in lockstep, meaning that the threads execute the same instructions at the same time. This detail has few important implications for the choice of data layout and traversal order. First, the computation should be organized in such a way that there are no divergences in the execution paths of threads in the same warp. Second, accesses to memory should be organized in regular patterns (ideally so that the same memory access instruction executed by the warp threads leads to consecutive addresses) --- the GPU hardware can then \emph{coalesce} such accesses and serve them with significantly lower latency.

Another important consideration is that the GPU has its own global memory that is separate from the system memory available to the CPU\@. This memory may be too small to hold all the data processed by the algorithm, so another important consideration is to organize the data in such a way that the algorithm can overlap GPU-accelerated computation with memory transfers between the system memory and the GPU device memory. In particular, the data should be partitioned into blocks and then processed sequentially in such a way that the transfer latency of each block can fully overlap with the computation of the previously transferred block. In the case of matrix multiplication, this is easily achievable as the computation workload scales cubically (with all three dimensions of the matrices), while the data size scales quadratically (with pairs of dimensions).


\section{Summary}\label{sec:background-summary}

We have outlined the hardware features of modern high-performance systems that are most relevant in the context of layout and traversal optimizations. Each architecture has further features and implementation details that we have not covered here, but the amount of different features and their complex interactions often make it difficult to predict the performance of an algorithm without collecting empirical data from representative runs.

Thus, it is important to have tools that help apply optimizations that either heuristically or empirically improve the performance of an algorithm. Our work addresses this need via two routes easily accessible and interpretable by users. First, we explore and develop abstractions that allow users to express their algorithms and data structures in a way that applying transformations to data layouts and traversal orders does not require changing the algorithmic code itself. Second, we explore use of large language models to automatically optimize the code of algorithms for better performance on modern hardware, which can be used as a complementary tool to the first route as well as a standalone tool.
