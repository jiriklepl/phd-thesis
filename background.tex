\chapter{Hardware background}\label{chap:background}

To better understand the motivation behind layout and traversal optimizations, which collectively change the memory access patterns in a program, we first outline the hardware features of modern high-performance systems that are most relevant to our focus on these optimizations.

We target the two main general-purpose architectures used in high-performance computing: multi-core CPUs and GPU accelerators.
CPUs are primarily designed for task processing, executing each active thread on an independent core, while GPUs are optimized for massively data-parallel workloads that run thousands of threads concurrently in SIMT (Single Instruction, Multiple Threads) fashion~\cite{hennessy2019computer,cuda_programming_guide}. A single thread of execution runs a sequence of instructions (a task) using a set of registers and other resources (such as caches or arithmetic units).

GPUs are devices \xxx{separated} from the host system, with their own memory and task scheduling. Thus, a computation running on a GPU typically requires transferring input data from system memory to the GPU device memory, and then transferring the results back to system memory after the computation is done. The data-parallel task is typically expressed as a \emph{kernel} function (in CUDA, a function with the \lstinline|__global__| modifier). Upon \emph{kernel launch} (a modified function call), the kernel function is scheduled to run on the GPU independently of the host system. CPU workloads, on the other hand, typically run directly on the host system using the system memory without necessitating any data transfer, unless the computation is distributed across multiple machines.

The main difference between code execution on the two architectures is that in CPUs, a single core runs just one thread at a time (or a few threads in the case of hyper-threading), while in GPUs, many threads run concurrently on the same core in lockstep, executing the same instruction at the same time on different data. The distinction between them, however, is not strict, as modern CPU cores also support data parallelism through using specialized \emph{vector} units that can, in a single instruction, operate on multiple data elements (SIMD) at the same time.

The differences between the two architectures present different challenges and opportunities for optimizing the performance of algorithms, which we will discuss in more detail in the following sections.


\section{CPU considerations}\label{sec:cpu-considerations}

A simple example that helps illustrate the impact of data layouts and traversal orders on CPU performance is the matrix multiplication algorithm. It computes each element of the output matrix ($C$) as a dot product of a row from the first input matrix ($A$) and a column from the second input matrix ($B$), where all matrices are stored in the standard row-major order (row by row). The algorithm can be implemented in \cpp as follows:

\begin{lstlisting}[language=C++, caption={Matrix multiplication}, label={lst:matrix-multiplication}]
float C[M][N]; // M rows, N columns
float A[M][K]; // M rows, K columns
float B[K][N]; // K rows, N columns

// iterating over output matrix C
for (int i = 0; i < M; ++i) {
    for (int j = 0; j < N; ++j) {
        // single dot product
        C[i][j] = 0;

        for (int k = 0; k < K; ++k) {
            C[i][j] += A[i][k] * B[k][j];
        }
    }
}
\end{lstlisting}

When optimizing an algorithm, such as the matrix multiplication example in \cref{lst:matrix-multiplication}, for execution on a CPU, we primarily need to consider caching. Caches are memory units that transparently store data that is likely to be accessed in the near future under the principle of locality. The principle states that programs tend to access data repeatedly in a short period of time (temporal locality) and access data stored in nearby memory locations (spatial locality)~\xxx{(cite)}.

Many algorithms either naturally exhibit good locality (e.g., traversing a row-major matrix by rows) or can be transformed to have better locality (e.g., by reordering computations in such a way that repeated accesses to the same data are closer together).
% This principle, thus, directly motivates layout and traversal optimizations.

The current implementation of the matrix multiplication algorithm could be made more cache-friendly in two simple ways. First, we can transpose the layout of the input matrix $B$ to column-major order (column by column), so that the innermost loop accesses contiguous memory locations in both input matrices, improving spatial locality and thus performance.

The second way to improve caching is to improve the temporal locality of the algorithm by partitioning the computation into smaller chunks that can fit into the cache. In the current implementation (regardless of transposing $B$), the innermost loop accesses unique elements of the input matrices $A$ and $B$ in each iteration. For an input of sufficient size, this access pattern leads to repeated cache misses (necessity to update the cache with new data from memory). If we partition the matrices into tiles (sub-matrices) that can fit in the cache, then updating the corresponding elements of the output matrix by computing the dot products of the corresponding rows and columns of the tiles allows for efficient reuse of the data in the input matrices. The reuse scales linearly with the tile dimensions, as long as the tiles fit in the cache.

In practice, this transformation can be expressed as splitting the iteration ranges of the corresponding loops into smaller blocks, iterating over the blocks in the outer loops, and iterating over the elements of blocks in the inner loops, as shown in \cref{lst:matrix-multiplication-tiled}.

\begin{lstlisting}[language=C++, caption={Tiled matrix multiplication}, label={lst:matrix-multiplication-tiled}]

      // inner loops (iterating over elements of tiles)
      for (int i = ii; i < min(ii + i_block, M); ++i) {
        for (int j = jj; j < min(jj + j_block, N); ++j) {
          for (int k = kk; k < min(kk + k_block, K); ++k) {

In addition to caching, we also need to consider the parallelization and vectorization capabilities of the CPU\@.

CPU cores have specialized vector units that can, in a single instruction, operate on multiple data elements at the same time (SIMD). Efficient use of these vector units can lead to a multiplicative improvement in performance depending on the width of the vector units used (e.g., $256$-bit wide vector units can operate on $8$ single-precision floating-point numbers at the same time). By changing the data layout of $B$ to column-major order (as with improving spatial locality), the innermost loop accesses data of both input matrices sequentially, allowing us to unroll the loop by the width of the vector units (relative to the data type) and replace the unrolled iterations with vectorized instructions that compute multiple iterations at the same time.

To parallelize the algorithm, we can use an approach similar to the tiling transformation that we used for improving temporal locality. If we partition the output matrix into tiles (corresponding to blocking loops iterating over the output matrix dimensions), we can then create multiple execution threads that compute different tiles of the output matrix in parallel. To minimize the overhead of parallelization, the tiles should be large enough so that the corresponding computation is sufficiently large to amortize the overhead of spawning and scheduling threads, but also small enough so that the number of tiles can saturate all available CPU cores with work.


\section{GPU considerations}\label{sec:gpu-considerations}

GPU accelerators are among the most widely used hardware platforms in high-performance computing~\cite{top500}. Since NVIDIA GPU architectures currently dominate the high-performance computing landscape~\cite{top500}, we will default to their nomenclature when describing the relevant hardware features and use them as a reference point.

As described in the introductory section of this chapter, executing an algorithm on a GPU involves scheduling a \emph{kernel} function that is specifically designed to run on the GPU device and processes data stored in the GPU device memory (usually referred to as \emph{global memory}). A single invocation of the function typically processes a small portion of the data (as it is designed to be run in parallel by many threads). During a kernel launch, each new execution thread gets its own unique thread ID, which is used to determine which portion of the data the thread should process. The threads are organized into \emph{thread blocks}, and thus the unique thread ID is typically expressed as a combination of the block ID and the thread ID within the block. The number of thread blocks and the block size are specified by the programmer when launching the kernel --- this grid typically replaces one or multiple parallelized loops in the traversal of the sequential version of the algorithm.

The organization of threads into blocks is meaningful because each block is automatically scheduled on an available streaming multiprocessor (SM) of the GPU\@. Thus, to fully utilize the GPU, the number of thread blocks should be large enough to saturate all available SMs with work. Since all threads in the same thread block run on the same SM, they can also use a user-managed cache called \emph{shared memory} --- it can be used to store data that is reused by multiple threads in the same block, or even to communicate data between them. As the threads in the same block run on the same SM, synchronization between them has very low overhead, and thus many efficient algorithms make use of the shared memory and block-wide synchronization primitives during the computation.

When a thread block is executed on an SM, the threads are executed in groups of 32 (called \emph{warps}) in lockstep, meaning that they execute the same instructions at the same time (different warps are generally executed in unspecified order). While the GPU hardware can handle some divergence in the execution paths of different threads in the same warp quite well, efficient execution relies on that their global memory accesses are organized in regular patterns with minimal stride (ideally so that the same memory access instruction executed by the warp threads leads to consecutive addresses) so that they are \emph{coalesced} into as few memory transactions as possible\footnote{Each global memory transaction reads or writes an aligned 32-, 64-, or 128-byte memory segment (e.g., 32 threads can access consecutive \lstinline{int} values in a single transaction).}, thus significantly reducing memory access latency. This is an especially important factor in memory-bound algorithms. The choice of data layouts and traversal orders that lead to coalesced memory accesses is thus often crucial for ensuring good performance on GPUs.

\xxx{The threads in the same warp have minimal overhead for communication and synchronization, so highly efficient algorithms often utilize warp-wide communication primitives that allow threads to exchange data even faster than using shared memory.}

Since the GPU has its own global memory, some algorithms may require repeated kernel launches on different batches that can fit in the GPU memory. In such cases, it is important to organize the data and scale the batch size in such a way that the transfer latency of each batch can fully overlap with the computation of the previously transferred batch, as the hardware can perform both operations concurrently.

\section{Summary}\label{sec:background-summary}

% We have outlined the hardware features of modern high-performance systems that are most relevant in the context of layout and traversal optimizations. Each architecture has further features and implementation details that we have not covered here, but the amount of different features and their complex interactions often make it difficult to predict the performance of an algorithm without collecting empirical data from representative runs.

% Thus, it is important to have tools that help apply optimizations that either heuristically or empirically improve the performance of an algorithm. Our work addresses this need via two routes easily accessible and interpretable by users. First, we explore and develop abstractions that allow users to express their algorithms and data structures in a way that applying transformations to data layouts and traversal orders does not require changing the algorithmic code itself. Second, we explore use of large language models to automatically optimize the code of algorithms for better performance on modern hardware, which can be used as a complementary tool to the first route as well as a standalone tool.

In this chapter, we have outlined the main considerations for optimizing algorithms for execution on modern high-performance CPU-based and GPU-based systems. Many of these considerations are related to the organization of data or the order of computations, which motivates layout and traversal optimizations.

It is important to note that the hardware features we have outlined are not exhaustive. For example, CPU features such as out-of-order execution, branch prediction, and prefetching can further affect the performance of an algorithm based on its memory access patterns and control flow.
