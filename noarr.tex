The Noarr library, first introduced in~\cite{vsmelko2022astute}, is a C++ library that provides layout-agnostic abstractions for representing and manipulating multidimensional data structures and their traversals.

Formally, the abstractions are based on partial functions on the index space and memory space of multidimensional arrays. Each such partial function is represented by a primitive building block called a \emph{proto-structure} --- examples of proto-structures include \texttt{scalar} that represents a single value, \texttt{array} that represents a contiguous array of elements represented by another structure, or \texttt{into\_blocks} that represents a view of another structure that divides one of its dimensions into blocks of a given size.

The composable design of Noarr bears resemblance to views in the ranges library in C++20 (TODO cite); however, while being composable in a hierarchical manner, Noarr structures allow better flexibility and type-safety for multidimensional data structures by representing the index space using named dimensions that are resolved at compile time.

Since the index space is represented using named dimensions, all queries on the structure, such as obtaining the size of a dimension, or the memory offset of an element at a given index, are type-safe and checked at compile time. In contrast to traditional positional indexing of multidimensional arrays (e.g., \lstinline{data[i][j]}) that is prone to errors due wrong pairing of indices to dimensions, type-safe indexing using named dimensions (e.g., \lstinline{data[idx<'x'>(i) + idx<'y'>(j)]}) ensures that the indices are paired with the correct dimensions. This also ensures that the API of memory accesses is self-documenting and independent of the actual layout of the data in memory.

Noarr structures are immutable abstractions representing multidimensional data structures built by composing primitive proto-structures in a hierarchical manner as depicted in \cref{fig:noarr-structure-composition}. Each proto-structure represents a transformation of the index space and memory space of the nested \emph{sub-structure}; thus, if the sub-structure represents a multidimensional array with dimensions \lstinline{'y'} and \lstinline{'z'}, then wrapping it in an \texttt{array} proto-structure with dimension \lstinline{'x'} results in a three-dimensional array with dimensions \lstinline{'x'}, \lstinline{'y'}, and \lstinline{'z'}. The composition in this example simply adds a new dimension to the index space, extending it from two to three dimensions accordingly; however, other proto-structures may perform more complex transformations of the index space, such as splitting a dimension into multiple dimensions (e.g., \texttt{into\_blocks}, which consumes one dimension and produces two new dimensions) or reordering the logical hierarchy of dimensions (e.g., \texttt{hoist}).

The composition of proto-structures is done using C++ template meta-programming and, in the Noarr library, it is represented by the \lstinline{^} operator. Since each proto-structure represents a partial function on the index space and memory space of the sub-structure, the composition of proto-structures is naturally associative. This is a powerful property that allows defining more complex transformations from simpler ones, and applying them simultaneously, and possibly to multiple data structures.

Querying a specific feature of a Noarr structure, such as obtaining the memory offset of an element at a given index, is expressed as a function that takes the formal arguments of the query and a \emph{state} argument representing the index space, i.e., the lengths of the dimensions and the input indices (thus, an offset query takes no formal arguments, only the state). The proto-structure defines how the state is propagated to the sub-structure (\emph{sub-state}) and the result of the query is dependent on the formal arguments and the contents of the state, and further queries on the sub-structure using the sub-state (if needed). Some proto-structures generalize this idea by having multiple sub-structures (e.g., the \texttt{tuple} proto-structure), choosing the appropriate sub-structure based on the state.

For example, querying the offset of an element in an \texttt{array} proto-structure with size~$N$, dimension~\lstinline{'x'}, and a sub-structure~$S$, given an index state $s$, depicted in \cref{fig:noarr-structure-offset} proceeds as follows:

\begin{enumerate}
  \item Extract the index~$i$ for dimension~\lstinline{'x'}
  \item Compute the sub-state~$s'$ by removing dimension~\lstinline{'x'} from~$s$
  \item Query the size~$sz$ of the sub-structure~$S$ using the sub-state~$s'$
  \item Compute the offset as $i \cdot sz + \text{offset}_S(s')$, where $\text{offset}_S(s')$ is a query of the offset on the sub-structure~$S$ using the sub-state~$s'$
\end{enumerate}

\xxx{Since sub-structure queries always use sub-states, we can conceptually define each query on a Noarr structure as a composition of the features of the sub-structure (the propagation of the sub-state is implicit), formal arguments, and the contents of the state. The sub-state is defined as a transformation of the state.}

The notion of sub-structure and (sub-)state provides a clean framework for defining all queries on Noarr structures. In the Noarr library, most of the queries are implemented as templated member functions of the structure classes.

\xxx{Many proto-structures define only the sub-state, and just pass the queries to their sub-structure(s) without any additional logic. Examples include \texttt{set\_length} that defines the length of a dimension, \texttt{rename} that renames a dimension of the sub-structure, \texttt{span} that restricts the iteration space of a dimension to a given range. Some proto-structures, like \texttt{into\_blocks} that divides a dimension into blocks of a given size, define only some queries, and pass the rest to the sub-structure (\texttt{into\_blocks} defines custom logic only for length queries).}

The second main feature of Noarr structures is their \emph{signature}. A signature is a representation of the hierarchy of the dimensions of the structure. It is a necessary component for specifying intended traversals of the structures and they also allow for improved type-safety of the structures.
A signature can be interpreted as a tree where each node represents a dimension and its children represent nested dimensions.
The signature of a given Noarr structure results from a transformation of the signature of its sub-structure(s) based on the semantics of the proto-structure. For example, the signature of an \texttt{array} structure is represented by a root node representing the array dimension, with a single child representing the signature of the sub-structure.

Noarr traversers are wrapper abstractions over one or multiple Noarr structures that provide an interface for performing actions over their index spaces. In the simplest case, creating a Noarr traverser over a single Noarr structure and invoking its \texttt{for\_each} method with a callable object results in invoking the callable for each point in the index space of the structure. The single argument passed to the callable is a state object (TODO ref) containing the named indices for all dimensions of the structure. The traverser follows the signature of the structure to determine the order of iteration over the dimensions; thus, for signatures that form non-linear hierarchies (there are at least two child sub-signatures for some parent dimension), the callable is invoked in a depth-first manner for all points corresponding to the leaf nodes of the signature tree. % TODO: break this paragraph into two

Similarly to Noarr structures, traversers have an index space and a signature that specifies the linear order of traversal over the dimensions (TODO: refactor signatures in the structures section).

Noarr traversers have a similar relationship to Noarr structures as iterators and range algorithms in the C++20 ranges library (TODO cite) have to ranges. The main difference is that Noarr traversers operate on multidimensional index spaces inferred from the Noarr structures, while range algorithms operate on one-dimensional sequences of elements.

% TODO: ref/picture/snippet
Similarly to iterators in C++ algorithms, Noarr traversers can be used to run the given callable objects in parallel using the given backend. Noarr currently supports parallel execution using OpenMP, Intel TBB, C++ standard threads, and CUDA\@.

In (TODO ref) our work, we have shown that careful use of Noarr structures and traversers can be used to express the code logic in PolyBench/C kernels in a layout-agnostic and traversal-agnostic manner, without sacrificing performance compared to the original implementations. We have shown similar results for parallel implementations of the kernels using \xxx{OpenMP, TBB, and CUDA backends}. The main advantage of using Noarr in this context is the ability to easily change the data layouts and traversal orders without having to modify the computation logic or memory access expressions. A secondary advantage is that all memory accesses are type-safe and checked at compile time, preventing many common programming errors related to multidimensional array indexing.

\subsection{Noarr MPI extension}\label{sec:noarr-mpi}

\xxx{This will probably cite MPI layouts~\cite{klepl2024abstractions}.}

\xxx{Introducing layout-agnostic abstractions to distributed communication over MPI proved to be an interesting avenue of research.} The MPI type system is compatible with layout-agnosticism, since MPI datatypes are for the purposes of communication equivalent whenever their signatures\footnote{MPI datatype signature is a sequence of base element types in the semantic order, disregarding their displacements in memory.} are the same. This characteristic is similar to the notion of layout-agnosticism in Noarr structures, where semantic order of elements is specified by the named dimensions; thus, given a linearization of the named dimensions in a Noarr structure, a Noarr structure corresponds to a specific MPI datatype (disregarding different ways of constructing it). As described in (TODO ref), such linearization can be represented by a Noarr signature. % TODO: choose a different term than linearization

In our work (TODO ref), we have introduced the Noarr MPI extension that leverages that traversers can be created over multiple Noarr structures simultaneously. This provides a clean API that builds on top of the Noarr traversers to express communication patterns involving multiple Noarr structures that may have different layouts, allowing each computation step connected by communication with other computation steps to use its own preferred layout without having to modify the communication logic. We showcase the proposed approach on a distributed matrix multiplication example, with \lstinline{broadcast} and \lstinline{scatter}/\lstinline{gather} communication patterns. Experimental evaluation shows that the automatized generation of MPI datatypes from Noarr structures and traversers introduces negligible overhead compared to hand-crafted MPI datatype definitions over the same layouts regardless of the data layout used.

Since two corresponding Noarr structures at the sender and receiver side (with same dimensions, but possibly different layouts) correspond to many different MPI datatypes depending on the linearization of the dimensions, some possibly performing better than others, using Noarr traversers to express the semantic order of the communicated data brings the opportunity to explore different MPI datatype linearizations by adjusting the traverser signatures --- Noarr offers proto-structures, such as \texttt{hoist} (TODO ref), that can be used to safely reorder the dimensions of the traverser signature without affecting the correctness of the communication.

In our work, we have also applied the layout-agnostic MPI datatype construction approach to Kokkos views (TODO ref) and mdspan (TODO ref), that offer efficient multidimensional array abstractions. However, as these abstractions do not provide named dimensions or otherwise encode the semantic order of elements in their type system, such application relies on careful pairing of positional indices to appropriate dimensions. The tuning capability available in the approach leveraging Noarr traversers may be used in this context by providing a permutation of the positional dimensions that controls the layout linearization; however, such approach, without named dimensions, generalizes poorly to more intricate data structures and communication patterns.
