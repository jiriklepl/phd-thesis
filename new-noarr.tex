\chapter{Noarr Library}\label{chap:noarr}

Our work on abstractions for high-performance computing introduced layout-agnostic and traversal-agnostic abstractions that enable separation of concerns between data representation, data traversal, and algorithm implementation. We have developed two main abstractions: Noarr~\cite{vsmelko2022astute,klepl2024pure,klepl2024abstractions,klepl2025layout} and Cellato~\cite{brabec2025cellato} as experimental testbeds for exploring and showcasing these ideas. % TODO: resolve the disbalance between Noarr and Cellato


\section{Noarr Structures}\label{sec:noarr-structures}

Noarr structures, introduced in our initial work~\cite{vsmelko2022astute}, are the fundamental abstraction in the Noarr library used for modeling multi-dimensional data layouts according to the principles of layout agnosticism and hierarchical composition of data layouts.

\subsection{Layout-agnostic design}\label{sec:layout-agnostic-design}

Layout-agnostic design separates the logical structure of the data (the index space defined by the dimension names) from the physical layout of the data in memory. Consider \cref{lst:non-agnostic-copy} as an example of a non-layout-agnostic copy algorithm for 2D arrays in \cpp. This implementation of the algorithm assumes a specific layout of the data in memory, and special care must be taken to ensure that the indexing logic correctly reflects the layout of the data. This is usually not desirable and, in general, the explicit indexing expressions (e.g., \texttt{i*N + j} and \texttt{j*M + i}) are replaced with abstractions of the data layouts (e.g., \lstinline{source(i, j)} and \lstinline{destination(i, j)}).

\begin{lstlisting}[style=C++, caption={A non-layout-agnostic copy algorithm in \cpp.}, label={lst:non-agnostic-copy}]
float* source = /*...*/; // an M by N array in column-major layout
float* destination = /*...*/; // an M by N array in row-major layout

for (size_t i = 0; i < M; ++i) {
  for (size_t j = 0; j < N; ++j) {
    destination[i*N + j] = source[j*M + i];
  }
}
\end{lstlisting}

\begin{defn}[Data layout]\label{def:data-layout} A data layout is a mapping from a (multi-dimensional) index space to an offset in a linear memory layout. Usually, a data layout has well-defined properties such as the length of each dimension,
% commonly referred to as (individually) extent or (collectively) shape,
the total buffer size, or the type of each element.
\end{defn}

The logic of the copy algorithm does not actually rely on the individual physical layouts of the source and destination data --- it simply copies the elements from one representation of the data to another; as such, it requires the two data structures to share the same logical structure (index space; in this case, a 2D space with size $M \times N$). \Cref{lst:layout-agnostic-copy} shows a layout-agnostic version of the copy algorithm that is implemented using Noarr structures. The algorithm does not encode specific assumptions about the physical layout of the data in memory (both data structures are indexed using the same logical index), and thus it can work with any data structure that shares the $M \times N$ logical structure. The logical structure (encoding the index space) is the definition domain of the data layout, if we consider the data layout as a mapping as defined in \cref{def:data-layout}.

\begin{lstlisting}[style=C++, caption={A layout-agnostic copy algorithm using Noarr structures.}, label={lst:layout-agnostic-copy}]
// defining Noarr structures will be covered later
auto source = /*...*/;
auto destination = /*...*/;

for (size_t i = 0; i < M; ++i) {
  for (size_t j = 0; j < N; ++j) {
    // a point in the M by N index space
    auto point = idx<'M', 'N'>(i, j);

    destination[point] = source[point];
  }
}
\end{lstlisting}

Syntactically, the logical layout of the data can be expressed multiple ways --- for example, the \lstinline{std::mdspan} abstraction encodes different dimensions as positional arguments (e.g., \lstinline{my_mdspan(i, j)} passes $i$ as the index of the first dimension and $j$ as the index of the second dimension), while Noarr structures encode different dimensions as named arguments --- for example, \lstinline{idx<'M', 'N'>(i, j)} explicitly associates $i$ with the dimension \lstinline{'M'} and $j$ with the dimension \lstinline{'N'}.
%, with an alternative form of \lstinline{idx<'N', 'M'>(j, i)}.
While the latter form is generally more verbose, it can prevent many indexing mistakes, as any association between an index and a dimension is explicit. Furthermore, the approach of encoding dimensions as named arguments is more intuitive in cases where different data structures have unrelated index spaces, which will be discussed in more detail in \cref{sec:composing-noarr-structures}. In \cref{sec:transforming-noarr-structures}, we will show that the points in the index space can be defined implicitly, inferring the indices from the iterated index space of an algorithm, reducing the verbosity overhead.

\Cref{fig:data-layouts} illustrates multiple data layouts. \Cref{fig:row-major} and \cref{fig:column-major} show two different physical layouts for the same logical structure (a 2D array) --- row-major and column-major layouts, respectively. These two layouts can be understood hierarchically; the row-major layout can be viewed as a grid of $M$ rows of $N$ elements, while the column-major layout can be viewed as a grid of $N$ columns of $M$ elements. Thus, aligning with the principles of layout-agnostic algorithms, both compositions result in the same index space (a 2D space with dimensions \lstinline{'M'} and \lstinline{'N'}) and thus the same logical structure of the data, while the physical layout of the data in memory is different.

Both layouts can be expressed using the same basic building block: introducing a new dimension to the layout and creating a grid of the original layout (now sub-layout) along the new dimension. This building block is present in many data layout abstractions, such as C arrays (in \lstinline{float matrix[M][N]}, each bracket represents this building block), or MPI datatypes (\lstinline{MPI_Type_contiguous} exactly matches this building block). In the Noarr library, this building block is represented by \lstinline{vector<dim>(length)}.

In most general terms, these building blocks are functions $\mathcal{L}^n \to \mathcal{L}$, where $\mathcal{L}$ represents a data layout and $n$ is the number of sub-layouts that the building block takes as input. For the above example, $n = 1$. But there are also building blocks with $n > 1$ --- for example, \lstinline{std::tuple} in \cpp (or \lstinline{MPI_Type_struct} in MPI) takes multiple sub-layouts and combines them into a single layout.


\subsection{Composing Noarr Structures}\label{sec:composing-noarr-structures}

Similarly to C types or MPI datatypes, Noarr structures are designed to be composed hierarchically. The individual building blocks of Noarr structures are called \emph{proto-structures}. We use \lstinline{scalar<T>()} to denote a Noarr structure representing a dimensionless data layout comprising a single element of type \texttt{T}. A more complex Noarr structure can be constructed by using the \lstinline{operator^} and proto-structures such as \lstinline{vector<'M'>(N)} as shown in \cref{lst:composing-noarr-structures}.

\begin{lstlisting}[style=C++, caption={Composing Noarr structures using proto-structures.}, label={lst:composing-noarr-structures}]
auto scalar = noarr::scalar<float>();
auto row = scalar ^ noarr::vector<'N'>(N);
auto matrix = row ^ noarr::vector<'M'>(M);
\end{lstlisting}

The resulting \texttt{matrix} Noarr structure in \cref{lst:composing-noarr-structures} represents a 2D array with dimensions \lstinline{'M'} and \lstinline{'N'} in the row-major layout as shown in \cref{fig:row-major}. Naturally, the composition \lstinline{scalar ^ noarr::vector<'M'>(M) ^ noarr::vector<'N'>(N)} results in the corresponding column-major layout.

% This approach to composition allows for a clear separation between the logical layout of the data (the index space defined by the dimension names) and the physical layout of the data in memory, since the both row-major and column-major layouts can be indexed using the same points in the index space (e.g., \lstinline{idx<'M', 'N'>(i, j)}).

The Noarr library implements this composition using powerful template metaprogramming techniques, encoding layout information in the type system to enable compile-time optimizations and zero-overhead interpretation of the Noarr structures. Only runtime parameters (e.g., the lengths of the dimensions) are stored as physical data members of the Noarr structures. Each Noarr structure is a first-class citizen in the \cpp type system, and its properties are fully transparent to the compiler, which allows for aggressive optimizations of their interpretation.

% Furthermore, since each dimension is associated with a semantically meaningful name, the composition can also perform compile-time checks to ensure that the resulting Noarr structure is valid (e.g., it does not contain duplicate dimension names).

As mentioned before, the order of composition matters, and changing the order of the proto-structures can define different layouts. As such, the composition of Noarr structures is not commutative; however, it is fully associative, which allows for preparing reusable building blocks, as shown in \cref{lst:associative-composition}.

\begin{lstlisting}[style=C++, caption={Associative composition of Noarr structures.}, label={lst:associative-composition}]
auto column_major = noarr::vector<'M'>(M) ^ noarr::vector<'N'>(N);
auto matrix = noarr::scalar<float>() ^ column_major;
\end{lstlisting}

In \cref{lst:associative-composition}, we define a new reusable building block \texttt{column\_major} that can be used to construct different layouts as grids of $M$ rows and $N$ columns of a given sub-layout (e.g., \lstinline{scalar<float>()} in case of defining a matrix layout). \lstinline{column_major} itself is considered a proto-structure.


\subsection{Transforming Noarr Structures}\label{sec:transforming-noarr-structures}

The composition of Noarr structures using proto-structures allows for defining transformations of Noarr structures using the same mechanism. For example, consider a sub-matrix. A sub-matrix layout results from any 2D (matrix) layout by restricting the index space to a contiguous sub-region (2D interval) of the original space. This is yet another example of a layout transformation of the form $\mathcal{L} \to \mathcal{L}$; or, equivalently, two transformations, for each dimension separately. In the Noarr library, this transformation is represented by the \lstinline{span<dim>(start, end)} proto-structure shown in \cref{lst:transforming-noarr-structures}.

\begin{lstlisting}[style=C++, caption={Transforming Noarr structures using proto-structures.}, label={lst:transforming-noarr-structures}]
auto sub_matrix = matrix
    ^ noarr::span<'M'>(start_i, end_i)
    ^ noarr::span<'N'>(start_j, end_j);
\end{lstlisting}

Notice that this transformation satisfies the principle of layout agnosticism: it is applicable to a matrix of any physical layout (e.g., row-major or column-major) as long as the index space contains the dimensions \lstinline{'M'} and \lstinline{'N'}. Since we do not use positional syntax, the transformation can be actually applied to any layout with the appropriate dimensions.

% In \cref{lst:transforming-noarr-structures}, we define new dimension variables (e.g., \texttt{i\_outer} and \texttt{i\_inner}) to show that the set of dimension names can be arbitrarily extended and that it also allows for more readable names (instead of just one-letter constants). The resulting \texttt{tiled\_matrix} Noarr structure represents the tiled layout shown in \cref{fig:tiled} --- it has $\lfloor M / tile\_size\_i \rfloor \times \lfloor N / tile\_size\_j \rfloor$ tiles (the product of the inferred lengths for \texttt{i\_outer} and \texttt{j\_outer}). This time, contrasting the previous example of composition, the transformation changes the logical layout of the data (the index space defined by the dimension names) while keeping the physical layout of the data in memory unchanged.

The \lstinline{span} proto-structure is an example of a transformation that changes the logical layout of the data while preserving the physical layout of the data in memory. This contrasts with the \lstinline{vector} proto-structure, which changes the physical layout as well. The category of transformations that preserve the physical layout will be especially relevant in the later discussion of traversal order transformations (since, in traversal order transformations, a change to the physical layout is not desirable).

% There are many other proto-structures with the property of preserving the physical layout of the data, such as \lstinline{rename<old_dim, new_dim>()} for renaming dimensions, which can be used to translate between different semantic conventions (e.g., from \lstinline{'M'} and \lstinline{'N'} to \lstinline{'x'} and \lstinline{'y'}), and \lstinline{span<dim>(start, end)} for slicing dimensions, which can be used to define sub-layouts of the original layout.

In \cref{sec:layout-agnostic-design}, we have asserted that naming dimensions is more intuitive in cases where different data structures have unrelated index spaces. This situation is shown in \cref{lst:layout-agnostic-matmul}, which exemplifies a layout-agnostic implementation of the na\"{\i}ve matrix multiplication algorithm.


\begin{lstlisting}[style=C++, caption={A layout-agnostic matrix multiplication algorithm using Noarr structures.}, label={lst:layout-agnostic-matmul}]
auto matrixC = /*...*/; // an M by N array
auto matrixA = /*...*/; // an M by K array
auto matrixB = /*...*/; // a K by N array

for (size_t i = 0; i < M; ++i) {
 for (size_t j = 0; j < N; ++j) {
  auto mn_point = idx<'M', 'N'>(i, j);
  matrixC[mn_point] = 0;

  for (size_t k = 0; k < K; ++k) {
   auto mnk_point = mn_point + idx<'K'>(k);
   matrixC[mnk_point] += matrixA[mnk_point] * matrixB[mnk_point];
  }
 }
}
\end{lstlisting}

The algorithm is, again, layout-agnostic because it does not rely on the specific physical layouts of the data in memory --- each data structure can be stored in any physical layout. However, there seemingly appears to be a noticeable issue: the algorithm relies on the fact that the three data structures have been defined with the dimensions \lstinline{'M'}, \lstinline{'N'}, and \lstinline{'K'} in a specific way that directly corresponds to the semantics of the matrix multiplication algorithm, which is not always the case in practice. This issue can be easily solved using yet another transformation of a layout, which is represented by the \lstinline{rename<old_dim, new_dim>} proto-structure --- this proto-structure simply renames a dimension in the layout without introducing any changes to the physical layout or the computation of an offset from a point in the index space.


\subsection{Noarr bags}\label{sec:noarr-bags}

So far, we have only discussed Noarr structures as abstractions for modeling data layouts. However, as shown in \cref{lst:layout-agnostic-matmul}, a reasonable use case requires a full-fledged data structure that can be indexed to access references to actual data in memory. Similarly to how the CuTe framework defines a rich algebra of layouts and then defines data structures called \emph{Tensors} as the combination of a layout and an actual data buffer, the Noarr library defines \emph{Noarr bags} as the combination of a Noarr structure and a data buffer.

\begin{lstlisting}[style=C++, caption={Defining a Noarr bag as the combination of a Noarr structure and a data buffer.}, label={lst:defining-noarr-bag}, basicstyle=\ttfamily\scriptsize]
auto matrix_layout = noarr::scalar<float>() ^ noarr::vectors<'M', 'N'>(M, N);

// manually allocating a data buffer (in special memory space)
float* data_buffer = CudaMalloc(M * N * sizeof(float));
auto matrix_bag = noarr::bag(matrix_layout, data_buffer);

// defining a bag that manages its own data buffer
auto matrix_bag = noarr::bag(matrix_layout);

// getting a view bag from an existing bag
auto matrix_view_bag = matrix_bag.get_ref();
\end{lstlisting}

\Cref{lst:defining-noarr-bag} shows the three most common ways to define a Noarr bag. The first case is especially useful if the data buffer is managed by another library or lives in a special memory space (e.g., GPU device memory or shared memory). The second case (owning bag) is the most convenient way to define a Noarr bag; it automatically allocates a data buffer of the appropriate size and manages its lifetime. The third case (view bag) is useful for passing a Noarr bag to a function so that regardless of whether the original bag is owning or a view, the function can work with a view bag as a trivially copyable and movable reference to the original bag.

The bags extend the interface of the underlying Noarr structure (such as \lstinline{get_length<'M'>()} or \lstinline{get_size()}) and also provide the indexing operator (i.e., \lstinline{operator[]}) to access references to the actual data in memory, as shown in \cref{lst:layout-agnostic-matmul}.


\subsection{Generalizing the separation of concerns}\label{sec:generalizing-separation-of-concerns}

% In \cref{def:data-layout}, we have defined a layout as a mapping from a multi-dimensional index space to a linear memory layout. This definition is usually sufficient for most use cases and for describing layout agnosticism. If $\mathcal{L}$ represents a data layout, each proto-structure can be viewed as a function $\mathcal{L}^n \to \mathcal{L}$ (transformation of layouts), as discussed in \cref{sec:hierarchical-view}.

Consider a situation where we want to parallelize the matrix multiplication algorithm on a cluster organized in a 2D grid of nodes so that each node computes a tile of the output matrix (a similar situation can be imagined for a GPU with a 2D grid of thread blocks). This is an application of data parallelism, requiring no communication between the nodes during the computation. To achieve such tiling, we would compute the appropriate tile sizes (for each dimension, the size would be the total size of the dimension divided by the number of nodes in that dimension) and then apply a tiling transformation to the layout of the data. Computing the tile sizes is a common practice in parallelizing algorithms, especially on GPUs. In Noarr, the resulting tiled layout can be defined by applying the \lstinline{into_blocks<old_dim, grid_dim, tile_dim>(tile_size)} proto-structure.

% Sometimes it is desirable to separate concerns even further by decoupling the layout of the data from specific lengths of its dimensions. For example, in the case of matrix multiplication, the algorithm operates on three matrices with potentially different layouts but shared dimensions (e.g., the dimension \lstinline{'K'} is shared between the two input matrices). In such cases, we can define the layouts as shown in \cref{lst:further-separating-concerns}.

This approach is simple enough on a small scale, but it can be quite annoying and error-prone to maintain (especially in the context of a larger pipeline of computations). If we look at the example of tiling a matrix multiplication from the perspective of the tiled layout (defined by the original dimensions and the manually computed tile sizes), the number of tiles of the is implicitly determined by dividing the lengths of the original dimensions and the tile sizes --- thus, we have made a redundant work as the number of tiles is exactly equal to the number of nodes in the cluster. It would be much more convenient to infer the size of the tiles from the number of nodes directly.

In Noarr, this can be achieved by breaking the \lstinline{into_blocks<old_dim, grid_dim, tile_dim>(tile_size)} proto-structure into two separate proto-structures: \lstinline{into_blocks<old_dim, grid_dim, tile_dim>()} and \lstinline{set_length<tile_dim>(tile_size)}. By replacing the latter with \lstinline{set_length<grid_dim>(num_nodes)}, we can spare ourselves from the redundant work.

% \begin{lstlisting}[style=C++, caption={Separating layout from dimension lengths.}, label={lst:further-separating-concerns}, basicstyle=\ttfamily\scriptsize]
% // using the shortcut vectors<dims...>() for (... ^ vector<dims>())
% auto A_layout = noarr::scalar<float>() ^ noarr::vectors<'M', 'K'>();
% auto B_layout = noarr::scalar<float>() ^ noarr::vectors<'K', 'N'>();
% auto C_layout = noarr::scalar<float>() ^ noarr::vectors<'M', 'N'>();

% auto lengths = noarr::set_lengths<'M', 'N', 'K'>(M, N, K);

% auto matrixA = A_layout ^ lengths;
% auto matrixB = B_layout ^ lengths;
% auto matrixC = C_layout ^ lengths;
% \end{lstlisting}

% In \cref{lst:further-separating-concerns}, the layouts of the matrices are defined independently, possibly in a different part of the codebase. The lengths of the dimensions are defined separately and applied to the layouts (usually in the part of the code where the data structures are actually instantiated). This has many benefits, such as allowing for the dimension lengths of the sub-layouts to be inferred --- for example, if the layout of \texttt{matrixC} was used to define \texttt{tiled\_matrix} in \cref{lst:transforming-noarr-structures} and the lengths of \texttt{i\_outer} and \texttt{j\_outer} were set explicitly instead of \lstinline{'M'} and \lstinline{'N'}.

% Separating the layout from the dimension lengths is useful for multiple reasons. The two main reasons that we have explored in our work were (1) to define the layouts separately as tunable parameters of the algorithm, and (2) to infer some of the dimension lengths from the data structures themselves, from run-time parameters, or hardware properties (such as the cache size or the number of available threads). \xxx{(cite the relevant papers)}

This approach does not fit the original definition of a data layout. Na\"{\i}vely, if just one of the transformations represented by proto-structures \lstinline{set_length<tile_dim>(tile_size)} and \lstinline{set_length<grid_dim>(num_nodes)} would be supported, the \lstinline{into_blocks<old_dim, grid_dim, tile_dim>()} transformation could be defined as a layout that has a dimension emulating the tile or grid size parameter. This would fit the original definition, but it would not allow for the flexibility of inferring one or the other from the known relationship between the two parameters.

\begin{defn}[Generalized data layout]\label{def:generalized-data-layout} A generalized data layout is a set of arithmetic relationships between the properties of the data layout and additional parameters. The properties of the data layout include the length of each dimension, the total buffer size, offset calculation, and type of the accessed element. The set of additional parameters includes lengths of dimensions and indexes in the index space. A property has a defined value if and only if there is exactly one way to infer the value from the known parameters and the defined relationships.
\end{defn}

Noarr is a more general model of \cref{def:generalized-data-layout} (and encodes the index and length parameters as objects type-parameterized by the dimension names). The generalized definition differs from \cref{def:data-layout}, which defines just a single property (the offset in a linear memory layout) in two main ways. First, it allows for multiple definitions of a property as long as only one of them can be inferred from the known parameters. Second, it allows for breaking the computation into multiple steps.


\subsection{Noarr structure interpretation}

The Noarr library implements the interpretation of Noarr structures using \cpp template metaprogramming. Each query to a Noarr structure (e.g., \lstinline{get_offset()} that represents retrieving the linear offset as per~\cref{def:data-layout}) is transformed into a hierarchical static traversal of the Noarr structure --- recursively querying the proto-structures that compose the Noarr structure until reaching the base case of a \lstinline{scalar} proto-structure. A single level of the recursive traversal is shown in \cref{fig:noarr-query}.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=.8\linewidth]{img/noarr-structure-offset.eps}
  \caption{The principle of querying a property of a Noarr structure. The query propagates the set of query parameters (state) through the hierarchy of proto-structures from the top-most level to the base case and then the computed properties are propagated back to the top-most level.}%
  \label{fig:noarr-query}
\end{figure}

% The intermediate state of the traversal is represented by a \emph{state} object that is passed through the hierarchy of proto-structures. At the top-most level, the state object directly relates to the point in the index space (e.g., \lstinline{idx<'M', 'N', 'K'>(i, j, k)}). Each proto-structure in the hierarchy then does the following three things:

% \begin{itemize}
%   \item Transforms the state object into the appropriate sub-state(s) passed to its sub-structure(s) according to the semantics of the proto-structure.
%   \item Queries the sub-structure(s) with the calculated sub-state(s) to retrieve their properties.
%   \item Combines the results from the sub-structure(s) according to the semantics of the proto-structure and returns the result to the caller.
% \end{itemize}

% In case of offset calculations inside a \lstinline{vector<dim>(length)} proto-structure, the actual steps are as follows:

% \begin{itemize}
%   \item The sub-state results from removing the dimension \texttt{dim} from the state object.
%   \item The inner offset and the size of the sub-structure are retrieved by querying the sub-structure with the calculated sub-state.
%   \item The final offset is calculated as $\text{inner\_offset} + \text{get\_index<dim>(state)} \times \text{inner\_size}$, where \texttt{get\_index<dim>(state)} retrieves the index of the dimension \texttt{dim} from the state object.
% \end{itemize}

% This schema is a powerful and flexible tool for implementing any proto-structure. The Noarr library also implements various checks on top of this mechanism to fail at compile time if the queries are invalid (e.g., if the queried dimension is not present in the Noarr structure). These checks are exposed to the user and usable in static assertions or \lstinline{if constexpr} statements --- for example, \lstinline{structure | has_length<'M'>()} can be used to check if the dimension \lstinline{'M'} has a defined length in the Noarr structure (optionally, the user can provide a state variable to the \lstinline{has_length} query to check if the structure has a defined length for the dimension \lstinline{'M'} in the context of the provided state variable). In simple terms, the user can use this mechanism to check whether a query to a Noarr structure depends on indexing a specific dimension or not.

The set of parameters of the query (e.g., the point in the index space) is called the \emph{state} in the Noarr library and we call the Noarr structure that defines the sub-layout transformed by the proto-structure the \emph{sub-structure}.

In Noarr, the layout properties are encoded as class methods (i.e., member functions) parametrized by the state variable. The hierarchy of the proto-structures is similarly represented by encapsulation of the sub-structures as class members.

To ensure some level of type safety, the properties of each layout (\cref{def:generalized-data-layout}) live in a separate name space represented by the object of the given Noarr structure, and each proto-structure removes the parameters specific to it from the state variable before passing it to the sub-structure (the passed variable is referred to as the \emph{sub-state}) --- for example, as shown in \cref{fig:noarr-query}, the \lstinline{vector<'M'>(length)} proto-structure removes the index of the dimension \lstinline{'M'}. Similarly, derived parameters (e.g., the inferred length parameters) are added to the sub-state variable passed to the sub-structure.

The properties of the layout defined by the proto-structure are calculated from the properties of the sub-layout defined by the sub-structure and the parameters of the proto-structure in the state variable. For the \lstinline{vector<'M'>(length)} proto-structure, the offset is calculated as $$\text{\lstinline{sub_struct.offset(sub_state)}} + \text{\lstinline{get_index<'M'>(state)}} \times \text{\lstinline{sub_struct.size(sub_state)}}$$ where \lstinline{get_index<'M'>(state)} retrieves the index of the dimension \lstinline{'M'} from the state variable.


\section{Noarr Traversals}\label{sec:noarr-traversals}

Noarr traversers~\cite{klepl2024pure} are wrapper abstractions over one or multiple Noarr structures that provide an interface for performing actions over their index spaces. In the simplest case, creating a Noarr traverser over a single Noarr structure and invoking its \lstinline{for_each} method with a callable results in invoking the callable for each point in the index space of the structure.

\begin{lstlisting}[language=C++, caption={Creating and using a Noarr traverser over a single structure.}, label=lst:noarr-traverser-single-structure, basicstyle=\ttfamily\scriptsize]
auto matrix = bag(scalar<int>() ^ vector<'M'>(M) ^ vector<'N'>(N));
traverser(matrix).for_each([&](auto state) {
  auto [i, j] = get_indices<'M', 'N'>(state);
  matrix[state] = i + j;
});
\end{lstlisting}

The single argument passed to the callable is a state object containing the named indices for all dimensions of the structure. The traverser iteration, in this case, is equivalent to the nested loop defined by the hierarchical order of the proto-structures in the Noarr structure --- the outer loop iterates over the dimension \lstinline{'N'} and the inner loop iterates over the dimension \lstinline{'M'} (the inner/outer relationship is the same as the order of the proto-structures in the composition of the Noarr structure). Drawing on the example in \cref{lst:layout-agnostic-copy}, the similar principle applies to the case of multiple Noarr structures sharing the same index space, simplifying the implementation of layout-agnostic copy algorithm into the following.

\begin{lstlisting}[language=C++,basicstyle=\ttfamily\scriptsize]
auto source = bag(scalar<int>() ^ vector<'M'>(M) ^ vector<'N'>(N));
auto target = bag(scalar<int>() ^ vector<'N'>(N) ^ vector<'M'>(M));

traverser(source, target).for_each([&](auto state) {
  target[state] = source[state];
});
\end{lstlisting}

The traverser in the above example iterates over the shared index space of the two Noarr structures, which is a 2D space with dimensions \lstinline{'M'} and \lstinline{'N'}. The order of iteration is in this case determined by the order of the proto-structures in the first Noarr structure as its index space already covers the index space of the second Noarr structure.

A more complex example of using Noarr traversers is shown in \cref{lst:layout-agnostic-matmul-traverser}, which implements the layout-agnostic matrix multiplication algorithm from \cref{lst:layout-agnostic-matmul} using Noarr traversers.

\begin{lstlisting}[language=C++, caption={A layout-agnostic matrix multiplication algorithm using Noarr traversers}, label=lst:layout-agnostic-matmul-traverser,basicstyle=\ttfamily\scriptsize]
auto matrixC = bag(scalar<float>() ^ vector<'M'>(M) ^ vector<'N'>(N));
auto matrixA = bag(scalar<float>() ^ vector<'M'>(M) ^ vector<'K'>(K));
auto matrixB = bag(scalar<float>() ^ vector<'K'>(K) ^ vector<'N'>(N));

traverser(matrixC, matrixA, matrixB).for_sections<'M', 'N'>([&](auto inner) {
  matrixC[inner] = 0;

  inner.for_each([&](auto state) {
    matrixC[state] += matrixA[state] * matrixB[state];
  });
});
\end{lstlisting}

In this example, the index spaces of the input data structures do not match --- the traverser is constructed first from the index space of the (first supplied) \lstinline{matrixC} and then extended to cover the index space of \lstinline{matrixA}. The newly added dimensions are added as outer relative to the existing dimensions (i.e., the order of the dimensions outermost to the innermost is $\text{\lstinline{'K'}} \to \text{\lstinline{'N'}} \to \text{\lstinline{'M'}}$). \lstinline{matrixB} triggers no change to the traverser index space as its index space is already covered by the traverser. Since the loop nest is imperfect, a different method of traversal is used --- the \lstinline{for_sections} method is used to iterate over the given list of dimensions (in this case, \lstinline{'M'} and \lstinline{'N'}) and for each such section of the index space, the provided callable is invoked with a new (inner) traverser that represents the inner loop nest. The \lstinline{inner} traverser is then used to finalize the traversal on each section through the \lstinline{'K'} dimension.


\subsection{traversal order transformations}\label{sec:traversal-order-transformations}

Similarly to Noarr structures, Noarr traversers can be further transformed using proto-structures that modify the index space and the signature. Let us imagine a scenario where the computation is performed by a cluster of $x \times y$ computation nodes organized in a 2D grid and the code runs on a node with rank \texttt{(r, s)} for the respective dimensions of the grid (ranks are zero-indexed).

\begin{lstlisting}[language=C++, caption={Applying a tiling transformation to a Noarr traverser}, label=lst:tiling-traverser,basicstyle=\ttfamily\scriptsize]
auto tiled_traverser = traverser(matrixC, matrixA, matrixB)
    ^ into_blocks<'M', 'x', 'M'>() ^ set_length<'x'>(x)
    ^ into_blocks<'N', 'y', 'N'>() ^ set_length<'y'>(y)
    ^ fix<'x'>(r) ^ fix<'y'>(s); // fixing the index in the given dimension

tiled_traverser.for_sections<'M', 'N'>([&](auto inner) {
  // same as in the previous example
});
\end{lstlisting}

In \cref{lst:tiling-traverser}, the iteration is split into tiles with the grid dimensions named \lstinline{'x'} and \lstinline{'y'} and tile dimensions named \lstinline{'M'} and \lstinline{'N'} to match the expected semantics of the matrix multiplication algorithm (i.e., the $M\times N$ tile of the traversal represents the computed tile of the output matrix). The lengths of the grid dimensions are then set to the number of nodes in the respective dimensions of the cluster. Finally, the indices of the traversal grid dimensions are set to the rank of the node in the respective dimensions of the cluster, which results in each node iterating over a different tile of the output matrix. The resulting tiled traverser is then used in the same way as in \cref{lst:layout-agnostic-matmul-traverser}.
